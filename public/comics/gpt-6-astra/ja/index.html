01

GPT-6 Astra とはINTRODUCTION

GPT-6 Astra は OpenAI 史上もっとも賢いモデルで、コンピュータ操作（computer use）、Web ブラウジング、ソフトウェアエンジニアリング、科学研究、専門的な業務において最先端の性能を発揮します。コード、ブラウザ、専門ソフトをまたいだマルチステップのワークフローが得意です。

多くのベンチマークで、Astra ははるかに少ない出力トークンでより高いスコアを出しています。トークン単価は上がっていますが、タスクあたりの推定 API コストはむしろ以前のモデルより低くなります。

Astra は同時にアラインメントの面でも最高のモデルです。慎重に動き、タスクの境界を守り、透明性のあるコミュニケーションをします。指示に解釈の余地があるときは、手元のコンテキストから通常のギャップを自分で埋め、答えによって結果が変わりうるときだけ的を絞った質問をします。新しい要件を取り込む、求められれば方向転換する、脇道の質問に答える、といったことを本来のタスクを見失わずにこなせます。

Responses API のリクエストでは、こう指定して呼び出します：

model = "gpt-6-astra"
02

新しくなったところは？WHAT'S NEW

新機能
ASYNC TOOL CALLING

非同期ツール呼び出し

アプリ側がツールを実行している間も、Astra は推論を続けたり、別のツールを呼んだり、リクエストのうち独立した部分に先に答えたりできます。function / custom tool に async: true を設定し、準備ができたら元の call_id で結果を返すだけ。ツールの実行と保留中の作業の管理は、引き続きアプリ側の仕事です。

新機能
MID-TURN STEERING

途中からの軌道修正（割り込み）

モデルが作業している最中に、新しいユーザー指示を追加できます。たとえば修正や要件の変更など。WebSocket 接続では、Responses API が完了済みの作業を保持したまま、その更新を続きの生成に反映します。

新機能
CONFIGURATION UPDATE

セッション途中で推論強度を変更

configuration_update の入力アイテムを 1 つ追加するだけで、難しいタスクでは reasoning effort を上げ、ふつうの追加質問では下げられます。しかも元のプロンプトのプレフィックスを書き換えないので、キャッシュはそのまま保持されます。この設定は次の configuration_update で上書きされるまで有効です。

安全性
MISALIGNMENT MONITORING

ミスアラインメント監視

Astra の安全対策強化の一環として、OpenAI のシステムがミスアラインメント（misalignment）の挙動を非同期で監視し、必要に応じてアラートを出します。

注意
LIMITATIONS

制限

Astra は推論強度 none をサポートしません。また EU データレジデンシー（EU data residency）下では Fast モードが使えません。

継承
GPT-5.6 CAPABILITIES

既存の機能はすべてそのまま

computer use、Structured Outputs、ストリーミング出力、Programmatic Tool Calling、マルチエージェントのオーケストレーション、プロンプトキャッシュ、永続的な推論、compaction、pro モード。GPT-5.6 にあるものは、Astra でもすべて使えます。

03

Astra の「性格」と調教の全体像PROMPTING BEST PRACTICES

Astra は GPT-5.6 Sol などの前世代より賢く、仕事もできます。同時に、プロンプトで狙って調整できるいくつかの行動パターンも見せます：

  • 主体性とやり抜く力 —— より効率的な協働者として設計されているため、追加の入力で結果が大きく変わりそうなときは立ち止まって質問しがちです。あなたとしては、妥当な仮定を置いてそのまま進んでほしい場面でも。
  • 指示への追従 —— 汎用的な指示追従はこれまで以上に強く、挙動をより細かくコントロールできます。その反面、skills や AGENTS.md などのファイルにある指示にも敏感です。モデルがアクセスできる skills やファイルに、挙動を左右しかねない指示がないか監査することを強くおすすめします。
  • 個性と文体 —— 詳細で書式の多い回答になりがちで、セッションをまたいで同じ決まり文句を繰り返すこともあります。アプリに必要な文体と構成を明示してください。
  • サブエージェントへの委任 —— 委任の頻度が、あなたのワークフローが求める水準より低いことがあります。いつ、どの程度 subagents を並列で使うかを指定してください。
  • テストと検証 —— コードを書くとき、タスク完了と判断する前に徹底的にテストしようとします。小さなタスクでは、テストの範囲が必要以上に広がることがあります。
04

5 つの調教呪文（Prompt 原文 + 解説）PROMPT SPELLS

★呪文その一：もっと自律的に動かせる INITIATIVE & FOLLOW-THROUGH

Astra は長いタスクでも一貫性を保つ力が前世代より高い一方で、「前世代なら勝手に仮定して進んだ」ところで確認を求めやすくなっています。もっと自律的に動かしたいなら、まずはこのプロンプトから：

PROMPT 
You should infer the user's intent and task scope from the instructions and prior conversation context. Your job is to bias towards action and carry the user's intended task to completion.

When the user expresses intent to perform new work or fix an existing issue, persist until the user's intended goal is complete. Progress autonomously towards the user's goal (e.g. creating isolated worktrees / checkouts if needed, resolving merge conflicts, read-only actions, creating draft PRs etc.) unless they are clearly destructive or irreversible.
モデルにコンテキストからユーザーの意図とタスクの範囲を推測させ、質問より行動を優先して、最後までやり切らせます。明らかに破壊的・不可逆な操作でなければ（worktree の作成、コンフリクト解消、読み取り専用の操作、ドラフト PR の作成など）、自律的に進めるべき、という指示です。

ユーザーの意図がはっきりしないと、モデルは確認を求めやすくなります。言い回しの中にすでに許可が含まれているなら、この一文で実行まで持っていかせましょう：

PROMPT 
When the user's prompt indicates a request for action, such as "can you...", "I want to...", "help me..." and similar expressions, treat these as instructions to do the work and take action. Do not stop at acknowledging capability (e.g. "Yes…"), proposing a plan, or offering to continue. Do not settle for a partial or "helpful enough" solution that does not fully satisfy the user's task to save time, effort or tokens. If a task requires sustained work, complete all the necessary work until the intended outcome is fulfilled.
ユーザーが「〜できる？」「〜したい」「〜を手伝って」と言ったら、そのまま実行指示として扱う。「できますよ」で止まらない、計画だけ出さない、「続けますか？」と聞かない。時間やトークンを節約するために「まあ十分」な中途半端な成果物を出すのもダメで、期待された結果に届くまでやり切る、という内容です。

具体的でレビューできる成果物を用意してから承認を求めるようにして、着手前に止まってしまうのを防ぎます：

PROMPT 
Before asking the user clarifying questions, you should complete the work that is already authorized from context and necessary to make the proposed action concrete and reviewable. The user should be approving a concrete, reviewable result. For example, before deploying a change, writing to an external application, merging a PR or publishing a site, do all the required work first so that user approval is the final step. You don't need user permission for reversible tasks, read-only actions, reviews or fixes, or anything for which authorization is provided earlier in the session or strongly implied from the task instruction.

Do not introduce unsolicited warnings, disclaimers, approval flows, or safety/compliance checklists due to hypothetical risk.
デプロイ、外部アプリへの書き込み、PR のマージ、サイト公開の前に、先にできることはすべて済ませ、ユーザーの承認を最後の一手にします。可逆な操作、読み取り専用の操作、レビューや修正には許可は不要。仮想的なリスクを理由に、警告や免責事項、承認フローを勝手に持ち出すのもなし。ちなみにモデルはデフォルトで、作業しながら「ブロックしない」質問を投げたがります。アプリに必要な自律性の度合いに合わせて、これらのプロンプトを調整してください。

★呪文その二：指示の優先順位をはっきりさせる INSTRUCTION FOLLOWING

Astra はより長い指示に従えますが、コンテキスト内の情報にも敏感です。たとえば skill ファイルにあいまいな指針や矛盾する指針があると、早すぎる段階で止まって作業がブロックされることがあります。ユーザー指示と skills の優先順位を明示しておきましょう：

PROMPT 
The user's instructions take precedence over guidelines provided in a skill. If explicit user instructions conflict with a skill's instructions, prioritize the user's instructions.
一文でルールを決めます：ユーザー指示 > skill の指針。ぶつかったらユーザー優先。

アプリが大量の skills や AGENTS.md のような指示ファイルを読み込んでいるなら、どの skill のどの指示のせいで止まったり方向を変えたりしたのかをモデルに「白状」させると、挙動の透明性がぐっと上がります：

PROMPT 
If a skill causes you to ask for permission or confirmation, pause, leave requested work unfinished, or diverge from the user's intent, name and link to the exact SKILL.md file you read, quote the relevant instruction, and briefly explain how it applies. Distinguish explicit skill requirements from your interpretation of guidelines.
skill が原因で止まる・許可を求める・意図から外れるときは、該当する SKILL.md ファイルを名指しでリンクし、関係する指示の原文を引用して、なぜ当てはまるのかを簡潔に説明させます。さらに「skill の明示的な要求」と「モデル自身の解釈」を区別させる。隠れた矛盾する指針を洗い出すのにうってつけの一文です。

★呪文その三：文体を手なずける PERSONALITY & WRITING STYLE

Astra はリスト、表、Markdown を使って回答を「ざっと読みやすく」したがります。アプリが書式少なめの流れる段落を求めるなら、はっきり書いておきましょう：

PROMPT 
Default to using clear, concise paragraphs, each developing one main idea. Use lists only when the information is genuinely parallel, sequential, or easier to compare, and avoid nested lists unless the hierarchy cannot be expressed clearly in prose. Use plain, simple language: familiar words, concrete examples, and precise verbs. Prefer active voice and direct statements.

Make sure to state the main point clearly and early, then develop it with the explanation and detail the reader needs. Let each sentence build on what came before. Develop the points that matter and provide enough support to be useful.
デフォルトは明快で簡潔な段落（1 段落に 1 つの主旨）。リストは情報が本当に並列・順序あり・比較向きのときだけ。平易な言葉と能動態で、まず結論を示してから展開し、各文は前の文を受けて進める、という指示です。

技術的なやり取りでは、この一文が「明快で一貫している」と「専門的で的確」のバランスを取ってくれます：

PROMPT 
Use plain language over jargon, and reference technical details only to the degree that it helps illustrate an idea or your work to the user. Communicate complex concepts in a clear and cohesive manner, and calibrate your writing to the level of background knowledge assumed from the user's prompt and context.
専門用語を積み上げず、技術的な詳細は説明の助けになるときだけ引く。そしてユーザーの知識レベルに合わせて書き方の深さを調整します。

決まり文句や「AI っぽい」言い回しを減らしたいなら、ここから：

PROMPT 
Avoid using slop words or phrases like "Bottom Line:" in conclusions, "delve," "foster," "leverage," "it's worth noting," "importantly," "Question? Answer." or "This isn't about X. It's about Y.", "genuinely" or hyphenated compound descriptions and adjectives. Do not use concluding summary statements such as "In short:..", "The simplest mental model is:...".

State the intended action directly. Avoid adding what you won't do, what will remain unchanged, or how you'll separate or categorize results. Do not use contrastive framing such as "X, not Y" or "X—not Y" that introduces an unprompted alternative that the user didn't ask about. Avoid invented compound labels like "exact-head checks" and "editorial-row layouts", vague qualifiers, and canned transitions; use plain verbs and prepositions to state the actual relationship directly.
いわば「AI 常套句ブラックリスト」。"delve" "leverage" "it's worth noting" のような使い古された語、"In short:" 型のまとめ、「X ではなく Y」型の対比フレーム、でっち上げの複合ラベル、中身のないつなぎ言葉を禁止します。やることを直接述べ、素朴な動詞と前置詞で実際の関係を説明する、という指示です。

★呪文その四：サブエージェント委任の加減 SUBAGENT DELEGATION

Astra は「作業を分割して並列のサブエージェントに委任する」訓練を受けています。ハーネスにマルチエージェントの仕組みがあるなら、この一文で委任の強さを調整します：

PROMPT 
If at any point you can parallelize work by delegating tasks to another agent (no matter if you are the root or subagent), you should do so using collaboration tools if it could save time or improve quality.
モデルがルートでもサブエージェントでも、委任によって並列化でき、時間の節約や品質向上につながるなら、コラボレーションツールを使って委任すべき、という内容です。モデルは「いつ、どう委任するか」のプロンプトによく反応するので、自分のマルチエージェント実装に合わせて調整できます。

エージェント間のメッセージには文法やスペースの誤りが出ることがあります。この一文で読みやすくします：

PROMPT 
Messages that you send to other agents and your final answer may be read by a human, so ensure they are legible. Always put proper spaces between words and/or numbers.
他のエージェントに送るメッセージや最終回答は人間が読むかもしれないと念押しし、単語や数字の間に正しくスペースを入れて、読みやすさを保たせます。

★呪文その五：テストの強度を調整する TESTING & VERIFICATION

コーディングのタスクで「1 つの変更にどれだけのテストと検証が要るか」を調整しておくと、小さな変更に無駄なテストや重複チェックをさせずに済みます：

PROMPT 
Do not write tests for reversible, low-impact changes that mirror the implementation. If you do choose to verify your work with tests, make sure that the tests are meaningful and necessary to verify implementation.

Run tests appropriate to the change and complete required checks. Once those pass, broaden or repeat testing only when new changes, failures, or unresolved concerns justify it; otherwise, continue toward completing the task.
可逆で影響の小さい変更に「実装をなぞるだけ」のテストは書かない。書くなら意味のあるものを。まず変更に見合ったテストと必須チェックを走らせ、通ったら、新しい変更・失敗・未解決の懸念がない限りタスクを前に進める。テスト範囲を際限なく広げない、という指示です。

移行クイックリファレンスMIGRATION QUICKSTART

Codex でワンコマンド移行

Codex は OpenAI Docs skill を使って、このガイドの推奨変更を適用できます：

$openai-docs migrate this project to GPT-6 Astra

他のコーディングエージェントでこの skill を使いたい場合は、OpenAI の skills リポジトリからダウンロードできます。

手動で移行するなら：model を gpt-6-astra にして、次の項目を順に確認します：

  • 推論強度：いま none や minimal を使っているなら、まず low から始めて結果を比べます。それ以外は、現在うまくいっている推論強度を維持。Responses では reasoning.effort、Chat Completions では reasoning_effort です。
  • ツール呼び出し：Responses API を使います。Astra は Chat Completions にも対応していますが、ツール呼び出しは Responses 経由が必須です。
  • 非対応パラメータ：temperature、top_p、top_logprobs を削除。Chat Completions ではさらに logprobs を削除し、Responses では include から message.output_text.logprobs を外します。
  • Fast モード：EU データレジデンシーでは Standard 処理を使います。Astra は EU データレジデンシー下で service_tier: "fast" と "priority" をサポートせず、また Astra の Fast モードにはレイテンシ SLA が含まれません。
  • 推論強度の変更：回答の合間に強度を変える必要があるなら、標準的なシングルエージェントのリクエストで configuration_update 入力アイテムを使います。リクエストレベルの reasoning.effort は固定のままにして、キャッシュ用にプロンプトのプレフィックスを保ちます。採用前に互換性の制限を確認してください。
  • プロンプトキャッシュ：GPT-5.5 以前から移行する場合は、prompt_cache_retention を prompt_cache_options.ttl に置き換えて "30m" を設定します。キャッシュ境界やキャッシュ書き込みの課金などの変更点も確認を。
  • 不要な承認待ち：モデルが進む前に何度も承認を求めてくるなら、「呪文その一」の主体性の指針で自律的な実行度を上げましょう。
💡 ひとことまとめ： Astra はより賢く、そしてより「慎重」。全力で走らせたいなら、プロンプトではっきり伝えること：どれだけ自律的に動くか、誰の指示が優先か、どう書くか、いつ委任するか、どこまでテストするか。
