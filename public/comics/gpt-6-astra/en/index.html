GPT-6 ASTRA Model usage guide · comic excerpt in English

VOL.01 Source: developers.openai.com Prompts kept in the original English + English explanation
📖 How to read this: This page is a comic-style excerpt of the OpenAI official docs page "Model guidance — Using GPT-6 Astra". The body text is a plain-English retelling; every prompt is quoted verbatim in its original English (copy it straight into your app), and each one comes with an "English explanation" underneath so you know exactly what it does.
01

Meet GPT-6 AstraINTRODUCTION

GPT-6 Astra is OpenAI's most intelligent model to date, with state-of-the-art performance in computer use, web browsing, software engineering, scientific research, and professional work. It shines at running multi-step workflows across code, browsers, and professional software.

Across a range of evaluations, Astra scores higher while using noticeably fewer output tokens. Even though each token costs more, the estimated API cost per task comes out lower than on earlier models.

Astra is also the best-aligned model so far: it acts carefully, respects task boundaries, and communicates transparently. When instructions leave room for interpretation, it uses the context it already has to fill routine gaps on its own, and asks a focused question only when the answer could change the outcome. It can take in new requirements, change direction when asked, and answer side questions without losing track of the main task.

Call it like this in a Responses API request:

model = "gpt-6-astra"
02

So what's new?WHAT'S NEW

New
ASYNC TOOL CALLING

Async tool calling

While your app is still running a tool, Astra can keep reasoning, call other tools, or answer the parts of the request that don't depend on it. Set async: true on a function or custom tool, then return the result under the original call_id once it's ready. Your app still owns tool execution and any pending work.

New
MID-TURN STEERING

Mid-turn steering (cutting in)

While the model is working, you can add new user instructions, say a correction or a change of requirements. Over a WebSocket connection, the Responses API keeps the work already done and folds the update into what comes next.

New
CONFIGURATION UPDATE

Change reasoning effort mid-session

Add a configuration_update input item to raise reasoning effort for hard tasks and lower it for routine follow-ups, all without rewriting the original prompt prefix, so your cache stays intact. The setting stays in effect until the next configuration_update overrides it.

Safety
MISALIGNMENT MONITORING

Misalignment monitoring

As part of Astra's strengthened safety measures, OpenAI's systems monitor for misalignment asynchronously and raise alerts when needed.

Heads-up
LIMITATIONS

Limitations

Astra does not support the none reasoning effort, and Fast mode is unavailable under EU data residency.

Inherited
GPT-5.6 CAPABILITIES

Everything from before, still here

Computer use, Structured Outputs, streaming, Programmatic Tool Calling, multi-agent orchestration, prompt caching, persistent reasoning, compaction, pro mode: whatever GPT-5.6 could do, Astra supports too.

03

Its "personality" and how to tune itPROMPTING BEST PRACTICES

Astra is smarter and more capable than predecessors like GPT-5.6 Sol, and it also shows a few behavior patterns you can tune with targeted prompting:

  • Initiative and follow-through — It's designed to be a more efficient collaborator, so when extra input could materially change the outcome it leans toward stopping to ask, where you might rather have it make a reasonable assumption and push on.
  • Instruction following — General instruction following is stronger than ever, which gives you more control over its behavior. It's also more sensitive to instructions in skills and files like AGENTS.md. Auditing is strongly recommended for any skills and files the model can reach that might steer its behavior.
  • Personality and writing style — It tends toward detailed, heavily formatted replies and may reuse certain stock phrases across sessions. Spell out the writing style and structure your app needs.
  • Subagent delegation — It may delegate less often than your workflow calls for. Say when, and how much, it should use subagents to work in parallel.
  • Testing and verification — When writing code, it likes to test thoroughly before calling a task done; on small tasks that can mean testing well beyond what the task needs.
04

Five prompt spells (original prompts + explanation)PROMPT SPELLS

★Spell one: get it to work more autonomously INITIATIVE & FOLLOW-THROUGH

Astra holds together over long tasks better than earlier models, but it's also more likely to ask for clarification where a predecessor would simply have assumed. To make it more autonomous, start with this prompt:

PROMPT 
You should infer the user's intent and task scope from the instructions and prior conversation context. Your job is to bias towards action and carry the user's intended task to completion.

When the user expresses intent to perform new work or fix an existing issue, persist until the user's intended goal is complete. Progress autonomously towards the user's goal (e.g. creating isolated worktrees / checkouts if needed, resolving merge conflicts, read-only actions, creating draft PRs etc.) unless they are clearly destructive or irreversible.
Have the model infer the user's intent and task scope from context, bias toward action over asking, and carry the task through to the end. Anything that isn't clearly destructive or irreversible (creating worktrees, resolving merge conflicts, read-only actions, opening draft PRs) should go ahead on its own.

When the user's intent is unclear, the model is more likely to ask for clarification. If the user's wording already implies authorization, use this one to make it follow through:

PROMPT 
When the user's prompt indicates a request for action, such as "can you...", "I want to...", "help me..." and similar expressions, treat these as instructions to do the work and take action. Do not stop at acknowledging capability (e.g. "Yes…"), proposing a plan, or offering to continue. Do not settle for a partial or "helpful enough" solution that does not fully satisfy the user's task to save time, effort or tokens. If a task requires sustained work, complete all the necessary work until the intended outcome is fulfilled.
When the user says "can you...", "I want to...", or "help me...", treat it as an instruction to do the work. Don't stop at "Sure, I can", don't just hand over a plan, don't ask "want me to continue?". And don't deliver a "good enough" half-finished result to save time or tokens; keep going until the intended outcome is actually reached.

Have the model ask for approval only after it has a concrete, reviewable result ready, so it doesn't get stuck before the work even starts:

PROMPT 
Before asking the user clarifying questions, you should complete the work that is already authorized from context and necessary to make the proposed action concrete and reviewable. The user should be approving a concrete, reviewable result. For example, before deploying a change, writing to an external application, merging a PR or publishing a site, do all the required work first so that user approval is the final step. You don't need user permission for reversible tasks, read-only actions, reviews or fixes, or anything for which authorization is provided earlier in the session or strongly implied from the task instruction.

Do not introduce unsolicited warnings, disclaimers, approval flows, or safety/compliance checklists due to hypothetical risk.
Before deploying, writing to an external app, merging a PR, or publishing a site, finish everything that can be finished first, so user approval is the final step. Reversible actions, read-only actions, reviews and fixes need no permission. Don't volunteer warnings, disclaimers, or approval flows over hypothetical risk either. One more thing: by default the model likes to ask "non-blocking" questions while it works. Tune these prompts to the level of autonomy your app needs.

★Spell two: set the instruction hierarchy INSTRUCTION FOLLOWING

Astra can follow longer instructions, but it's also more sensitive to what's in its context. Vague or conflicting guidance in a skill file, for example, can make it pause too early and block the work. State explicitly that user instructions outrank skills:

PROMPT 
The user's instructions take precedence over guidelines provided in a skill. If explicit user instructions conflict with a skill's instructions, prioritize the user's instructions.
One sentence lays down the rule: user instructions > skill guidelines. When they conflict, the user wins.

When your app loads lots of skills and instruction files like AGENTS.md, asking the model to "name names" (which skill, which line made it pause or change course) is a solid way to make its behavior more transparent:

PROMPT 
If a skill causes you to ask for permission or confirmation, pause, leave requested work unfinished, or diverge from the user's intent, name and link to the exact SKILL.md file you read, quote the relevant instruction, and briefly explain how it applies. Distinguish explicit skill requirements from your interpretation of guidelines.
Whenever a skill makes the model pause, ask for permission, or drift from the user's intent, require it to name and link the exact SKILL.md file and quote the relevant instruction verbatim, briefly explain why it applies, and separate "what the skill explicitly requires" from "its own reading of the guidelines". Great for flushing out hidden conflicting guidance.

★Spell three: rein in its writing style PERSONALITY & WRITING STYLE

Astra loves lists, tables, and Markdown that make replies "skimmable". If your app wants flowing paragraphs with less formatting, say so explicitly:

PROMPT 
Default to using clear, concise paragraphs, each developing one main idea. Use lists only when the information is genuinely parallel, sequential, or easier to compare, and avoid nested lists unless the hierarchy cannot be expressed clearly in prose. Use plain, simple language: familiar words, concrete examples, and precise verbs. Prefer active voice and direct statements.

Make sure to state the main point clearly and early, then develop it with the explanation and detail the reader needs. Let each sentence build on what came before. Develop the points that matter and provide enough support to be useful.
Default to clear, concise paragraphs (one main idea each); use lists only when the information is genuinely parallel, sequential, or easier to compare; keep the language plain and in the active voice; lead with the main point, then develop it, with each sentence building on the last.

For technical communication, this one helps you balance "clear and cohesive" with "appropriately technical":

PROMPT 
Use plain language over jargon, and reference technical details only to the degree that it helps illustrate an idea or your work to the user. Communicate complex concepts in a clear and cohesive manner, and calibrate your writing to the level of background knowledge assumed from the user's prompt and context.
Go easy on the jargon, bring in technical detail only where it helps make a point, and calibrate the depth of the writing to the user's background knowledge.

Want fewer stock phrases and less "AI-speak"? Start here:

PROMPT 
Avoid using slop words or phrases like "Bottom Line:" in conclusions, "delve," "foster," "leverage," "it's worth noting," "importantly," "Question? Answer." or "This isn't about X. It's about Y.", "genuinely" or hyphenated compound descriptions and adjectives. Do not use concluding summary statements such as "In short:..", "The simplest mental model is:...".

State the intended action directly. Avoid adding what you won't do, what will remain unchanged, or how you'll separate or categorize results. Do not use contrastive framing such as "X, not Y" or "X—not Y" that introduces an unprompted alternative that the user didn't ask about. Avoid invented compound labels like "exact-head checks" and "editorial-row layouts", vague qualifiers, and canned transitions; use plain verbs and prepositions to state the actual relationship directly.
An "AI slop blocklist": no overused words like "delve", "leverage", "it's worth noting", no "In short:" wrap-ups, no "not X, but Y" contrastive framing, no invented compound labels or hollow transitions. State the intended action directly, and use plain verbs and prepositions to say what the real relationship is.

★Spell four: dial subagent delegation up or down SUBAGENT DELEGATION

Astra is trained to split work up and hand it to parallel subagents. If your harness implements a multi-agent system, use this one to adjust how aggressively it delegates:

PROMPT 
If at any point you can parallelize work by delegating tasks to another agent (no matter if you are the root or subagent), you should do so using collaboration tools if it could save time or improve quality.
Whether the model is the root agent or a subagent, if delegating would parallelize the work and save time or improve quality, it should use the collaboration tools to delegate. The model responds well to prompts about when and how to delegate, so tune this to your multi-agent setup.

Messages between agents can come out with grammar or spacing errors. This one keeps agent-to-agent messages readable:

PROMPT 
Messages that you send to other agents and your final answer may be read by a human, so ensure they are legible. Always put proper spaces between words and/or numbers.
A reminder that messages to other agents and the final answer may be read by a human: put proper spaces between words and numbers and keep everything legible.

★Spell five: calibrate testing intensity TESTING & VERIFICATION

On coding tasks, calibrating "how much testing and verification does this change need" avoids pointless tests and repeated checks for small changes:

PROMPT 
Do not write tests for reversible, low-impact changes that mirror the implementation. If you do choose to verify your work with tests, make sure that the tests are meaningful and necessary to verify implementation.

Run tests appropriate to the change and complete required checks. Once those pass, broaden or repeat testing only when new changes, failures, or unresolved concerns justify it; otherwise, continue toward completing the task.
Don't write tests for reversible, low-impact changes that just mirror the implementation; if you do test, make it meaningful. Run the tests that fit the change plus the required checks, and once they pass, keep moving on the task unless new changes, failures, or open concerns justify more. Don't let the test scope balloon.
05

Migration cheat sheetMIGRATION QUICKSTART

One-shot migration with Codex

Codex can apply the recommended changes from this guide through the OpenAI Docs skill:

$openai-docs migrate this project to GPT-6 Astra

To use the skill in other coding agents, download it from OpenAI's skills repository.

Manual migration: set model to gpt-6-astra, then work through this checklist:

  • Reasoning effort: If you're on none or minimal today, start from low and compare results; otherwise keep whatever reasoning effort already works for you. Responses uses reasoning.effort, Chat Completions uses reasoning_effort.
  • Tool calling: Use the Responses API. Astra does support Chat Completions, but tool calling has to go through Responses.
  • Unsupported parameters: Remove temperature, top_p, and top_logprobs; on Chat Completions also remove logprobs; on Responses remove message.output_text.logprobs from include.
  • Fast mode: Under EU data residency, use Standard processing. Astra doesn't support service_tier: "fast" or "priority" with EU data residency, and Astra's Fast mode comes with no latency SLA.
  • Changing reasoning effort: If your app needs to adjust effort between replies, use the configuration_update input item in standard single-agent requests; leave the request-level reasoning.effort alone so the prompt prefix stays cacheable. Check the compatibility limits before adopting it.
  • Prompt caching: When migrating from GPT-5.5 or earlier, replace prompt_cache_retention with prompt_cache_options.ttl set to "30m". Also check the changes to cache boundaries and cache-write billing.
  • Unnecessary approval pauses: If the model keeps asking for approval before moving forward, use the initiative guidance from "Spell one" to raise its level of autonomous execution.
💡 In one sentence: Astra is smarter and also more "cautious". To unleash it fully, use your prompts to tell it plainly: how autonomous to be, who's in charge, how to write, when to delegate, and how much to test.
