01

GPT-6 Astra를 만나다INTRODUCTION

GPT-6 Astra는 OpenAI가 지금까지 내놓은 가장 똑똑한 모델로, 컴퓨터 조작(computer use), 웹 브라우징, 소프트웨어 엔지니어링, 과학 연구, 전문 업무 전반에서 최고 수준의 성능을 보여줍니다. 코드, 브라우저, 전문 소프트웨어를 넘나드는 다단계 워크플로를 특히 잘 해냅니다.

여러 벤치마크에서 Astra는 눈에 띄게 적은 출력 토큰으로 더 좋은 점수를 냈습니다. 토큰당 단가는 더 높지만, 작업 하나당 추정 API 비용은 오히려 이전 모델보다 낮습니다.

Astra는 동시에 정렬(alignment)이 가장 잘 된 모델이기도 합니다. 신중하게 움직이고, 작업 범위를 존중하며, 투명하게 소통합니다. 지시에 해석의 여지가 있으면 이미 주어진 맥락으로 흔한 빈틈을 스스로 메우고, 답에 따라 결과가 달라질 수 있을 때는 핵심을 짚는 질문을 던집니다. 새 요구사항을 받아들이고, 요청에 따라 방향을 틀고, 곁가지 질문에 답하면서도 본래 작업을 놓치지 않습니다.

Responses API 요청에서는 이렇게 호출하면 됩니다:

model = "gpt-6-astra"

03

Astra의 「성격」과 길들이기 개요PROMPTING BEST PRACTICES

Astra는 GPT-5.6 Sol 같은 이전 세대보다 더 똑똑하고 유능하지만, 동시에 prompt로 콕 집어 다듬을 수 있는 몇 가지 행동 패턴도 보여줍니다:

  • 주도성과 끝까지 밀고 가기 —— 더 효율적인 협업자가 되도록 설계된 탓에, 추가 입력이 결과를 실질적으로 바꿀 수 있다 싶으면 멈추고 질문하는 쪽으로 기울어집니다. 당신은 알아서 합리적으로 가정하고 밀고 나가길 바랐을 수도 있는데 말이죠.
  • 지시 따르기 —— 전반적인 지시 이행 능력이 이전보다 강해져 행동을 더 세밀하게 통제할 수 있습니다. 다만 skills나 AGENTS.md 같은 파일 속 지시에도 더 민감하게 반응합니다. 모델이 접근할 수 있는 skills와 파일에 행동을 좌우할 만한 지시가 있는지 꼭 점검해 보길 권합니다.
  • 성격과 문체 —— 자세하고 서식이 들어간 답변을 선호하며, 세션을 넘나들며 특정 표현을 되풀이할 수 있습니다. 앱에 필요한 글쓰기 스타일과 구조를 명확히 지정해 주세요.
  • 서브에이전트 위임 —— 위임 빈도가 워크플로에 필요한 수준보다 낮을 수 있습니다. 언제, 어느 정도로 subagents를 병렬로 쓸지 지정해 주세요.
  • 테스트와 검증 —— 코드를 쓸 때 작업이 끝났다고 판단하기 전에 철저히 테스트하려는 경향이 있습니다. 작은 작업이라면 테스트 범위가 필요 이상으로 커질 수 있습니다.
04

다섯 가지 길들이기 주문(Prompt 원문 + 해설)PROMPT SPELLS

★주문 하나: 더 알아서 일하게 만들기 INITIATIVE & FOLLOW-THROUGH

Astra는 긴 작업에서 일관성을 유지하는 능력이 이전 세대보다 낫지만, 「이전 모델이라면 그냥 가정하고 넘어갔을」 지점에서 확인을 요청하기도 더 쉽습니다. 더 자율적으로 움직이게 하려면 이 prompt부터 시작하세요:

PROMPT 
You should infer the user's intent and task scope from the instructions and prior conversation context. Your job is to bias towards action and carry the user's intended task to completion.

When the user expresses intent to perform new work or fix an existing issue, persist until the user's intended goal is complete. Progress autonomously towards the user's goal (e.g. creating isolated worktrees / checkouts if needed, resolving merge conflicts, read-only actions, creating draft PRs etc.) unless they are clearly destructive or irreversible.
모델이 맥락에서 사용자의 의도와 작업 범위를 추론하고, 묻기보다 행동하는 쪽으로 기울어 작업을 끝까지 완수하게 합니다. 명백히 파괴적이거나 되돌릴 수 없는 작업이 아니라면(worktree 만들기, 충돌 해결, 읽기 전용 작업, 초안 PR 만들기 등) 스스로 밀고 나가야 합니다.

사용자 의도가 불분명하면 모델은 확인을 요청할 가능성이 높아집니다. 사용자의 말투에 이미 승인이 담겨 있다면, 이 문장으로 바로 실행하게 하세요:

PROMPT 
When the user's prompt indicates a request for action, such as "can you...", "I want to...", "help me..." and similar expressions, treat these as instructions to do the work and take action. Do not stop at acknowledging capability (e.g. "Yes…"), proposing a plan, or offering to continue. Do not settle for a partial or "helpful enough" solution that does not fully satisfy the user's task to save time, effort or tokens. If a task requires sustained work, complete all the necessary work until the intended outcome is fulfilled.
사용자가 「~할 수 있어?」「~하고 싶어」「~좀 도와줘」라고 말하면 곧바로 실행 지시로 받아들이게 합니다. 「네, 가능해요」에서 멈추지 말고, 계획만 내놓지 말고, 「계속할까요?」라고 묻지도 말 것. 시간이나 토큰을 아끼려고 「이 정도면 됐지」 수준의 반쪽짜리 결과물을 내지 말고, 기대한 결과가 나올 때까지 해내야 합니다.

구체적이고 검토 가능한 결과물을 준비한 뒤에야 승인을 요청하게 해서, 시작도 하기 전에 막히는 일을 막습니다:

PROMPT 
Before asking the user clarifying questions, you should complete the work that is already authorized from context and necessary to make the proposed action concrete and reviewable. The user should be approving a concrete, reviewable result. For example, before deploying a change, writing to an external application, merging a PR or publishing a site, do all the required work first so that user approval is the final step. You don't need user permission for reversible tasks, read-only actions, reviews or fixes, or anything for which authorization is provided earlier in the session or strongly implied from the task instruction.

Do not introduce unsolicited warnings, disclaimers, approval flows, or safety/compliance checklists due to hypothetical risk.
배포, 외부 앱에 쓰기, PR 머지, 사이트 게시 전에 할 수 있는 일은 전부 먼저 끝내, 사용자 승인이 마지막 단계가 되게 합니다. 되돌릴 수 있는 작업, 읽기 전용 작업, 리뷰와 수정 등에는 허락이 필요 없습니다. 가상의 위험 때문에 먼저 나서서 경고, 면책 문구, 승인 절차를 내밀지도 말 것. 덧붙여 모델은 기본적으로 일하면서 「비차단형」 질문을 던지길 좋아하니, 앱에 필요한 자율성 수준에 맞춰 이 prompt들을 조절하세요.

★주문 둘: 지시의 우선순위 못 박기 INSTRUCTION FOLLOWING

Astra는 더 긴 지시도 따를 수 있지만, 맥락 속 정보에도 그만큼 민감합니다. 예를 들어 skill 파일의 모호하거나 서로 충돌하는 지침 때문에 너무 일찍 멈춰 서서 작업이 막힐 수 있습니다. 사용자 지시와 skills의 우선순위를 명시적으로 선언하세요:

PROMPT 
The user's instructions take precedence over guidelines provided in a skill. If explicit user instructions conflict with a skill's instructions, prioritize the user's instructions.
한 문장으로 규칙 정하기: 사용자 지시 > skill 지침. 충돌하면 사용자가 우선입니다.

앱이 많은 skills와 AGENTS.md 같은 지시 파일을 불러오는 경우, 어떤 skill의 어떤 지시 때문에 멈추거나 방향을 틀었는지 모델이 「실토」하게 하면 행동의 투명성이 크게 올라갑니다:

PROMPT 
If a skill causes you to ask for permission or confirmation, pause, leave requested work unfinished, or diverge from the user's intent, name and link to the exact SKILL.md file you read, quote the relevant instruction, and briefly explain how it applies. Distinguish explicit skill requirements from your interpretation of guidelines.
skill 때문에 멈추거나, 권한을 요청하거나, 의도에서 벗어날 때 해당 SKILL.md 파일을 이름과 링크로 지목하고 관련 지시 원문을 인용하며, 왜 적용되는지 짧게 설명하고, 「skill의 명시적 요구」와 「자기 해석」을 구분하게 합니다. 숨어 있는 충돌 지침을 찾아내기에 아주 좋은 문장입니다.

★주문 셋: 문체 단속하기 PERSONALITY & WRITING STYLE

Astra는 목록, 표, Markdown으로 답변을 「훑어보기 쉽게」 만들길 좋아합니다. 앱에 서식이 적은 이어지는 문단이 필요하다면 분명히 적어 주세요:

PROMPT 
Default to using clear, concise paragraphs, each developing one main idea. Use lists only when the information is genuinely parallel, sequential, or easier to compare, and avoid nested lists unless the hierarchy cannot be expressed clearly in prose. Use plain, simple language: familiar words, concrete examples, and precise verbs. Prefer active voice and direct statements.

Make sure to state the main point clearly and early, then develop it with the explanation and detail the reader needs. Let each sentence build on what came before. Develop the points that matter and provide enough support to be useful.
기본은 명확하고 간결한 문단(한 문단에 한 가지 요지). 정보가 정말로 병렬이거나 순서가 있거나 비교가 필요할 때만 목록을 쓰고, 쉬운 말과 능동태로 씁니다. 요점을 먼저 꺼낸 뒤 풀어 가고, 각 문장이 앞 문장을 이어받게 합니다.

기술적인 소통 상황에서는 이 문장이 「명확하고 일관됨」과 「전문적이고 적절함」 사이에서 균형을 잡아 줍니다:

PROMPT 
Use plain language over jargon, and reference technical details only to the degree that it helps illustrate an idea or your work to the user. Communicate complex concepts in a clear and cohesive manner, and calibrate your writing to the level of background knowledge assumed from the user's prompt and context.
전문용어를 쌓지 말고, 기술 세부사항은 설명에 도움이 될 때만 끌어옵니다. 그리고 사용자의 배경지식에 맞춰 글의 깊이를 조절합니다.

상투어와 「AI 말투」 단어를 줄이고 싶다면 여기서 시작하세요:

PROMPT 
Avoid using slop words or phrases like "Bottom Line:" in conclusions, "delve," "foster," "leverage," "it's worth noting," "importantly," "Question? Answer." or "This isn't about X. It's about Y.", "genuinely" or hyphenated compound descriptions and adjectives. Do not use concluding summary statements such as "In short:..", "The simplest mental model is:...".

State the intended action directly. Avoid adding what you won't do, what will remain unchanged, or how you'll separate or categorize results. Do not use contrastive framing such as "X, not Y" or "X—not Y" that introduces an unprompted alternative that the user didn't ask about. Avoid invented compound labels like "exact-head checks" and "editorial-row layouts", vague qualifiers, and canned transitions; use plain verbs and prepositions to state the actual relationship directly.
일종의 「AI 상투어 블랙리스트」입니다. "delve" "leverage" "it's worth noting" 같은 남용 단어, "In short:"식 마무리 요약, "X가 아니라 Y"식 대비 프레임, 지어낸 복합 라벨, 공허한 전환어를 금지합니다. 할 일을 바로 서술하고, 담백한 동사와 전치사로 실제 관계를 설명하게 합니다.

★주문 넷: 서브에이전트 위임 조절하기 SUBAGENT DELEGATION

Astra는 「작업을 쪼개 병렬 서브에이전트에 위임」하도록 훈련받았습니다. 하네스에 멀티 에이전트 시스템이 구현돼 있다면 이 문장으로 위임 강도를 조절하세요:

PROMPT 
If at any point you can parallelize work by delegating tasks to another agent (no matter if you are the root or subagent), you should do so using collaboration tools if it could save time or improve quality.
모델이 루트 에이전트든 서브에이전트든, 위임으로 병렬화해서 시간을 아끼거나 품질을 높일 수 있다면 협업 도구로 위임해야 합니다. 「언제, 어떻게 위임할지」에 대한 prompt에 모델이 잘 반응하니, 자신의 멀티 에이전트 구현에 맞춰 조정하면 됩니다.

에이전트끼리 주고받는 메시지에 문법이나 띄어쓰기 오류가 생길 수 있습니다. 이 문장은 에이전트 간 메시지를 더 읽기 좋게 만듭니다:

PROMPT 
Messages that you send to other agents and your final answer may be read by a human, so ensure they are legible. Always put proper spaces between words and/or numbers.
다른 에이전트에게 보내는 메시지와 최종 답변은 사람이 읽을 수도 있으니, 단어와 숫자 사이를 제대로 띄어 명확하고 읽기 쉽게 만들라고 일깨워 줍니다.

★주문 다섯: 테스트 강도 맞추기 TESTING & VERIFICATION

코딩 작업에서 「변경 하나에 테스트와 검증이 얼마나 필요한가」를 맞춰 주면, 작은 변경에 쓸데없는 테스트나 반복 점검을 하는 일을 피할 수 있습니다:

PROMPT 
Do not write tests for reversible, low-impact changes that mirror the implementation. If you do choose to verify your work with tests, make sure that the tests are meaningful and necessary to verify implementation.

Run tests appropriate to the change and complete required checks. Once those pass, broaden or repeat testing only when new changes, failures, or unresolved concerns justify it; otherwise, continue toward completing the task.
되돌릴 수 있는 저영향 변경에는 「구현을 그대로 베낀」 테스트를 쓰지 말 것. 쓴다면 의미 있는 것만 씁니다. 먼저 변경 규모에 맞는 테스트와 필수 검사를 돌리고, 통과하면 새 변경이나 실패, 미해결 문제가 없는 한 작업을 계속 진행합니다. 테스트 범위를 끝없이 넓히지 않도록.

다른 코딩 에이전트에서 이 skill을 쓰고 싶다면 OpenAI의 skills 저장소에서 내려받으세요.

수동 마이그레이션: model을 gpt-6-astra로 바꾼 뒤 항목별로 확인하세요:

  • 추론 강도: 지금 none이나 minimal을 쓰고 있다면 low부터 시작해 효과를 비교하고, 아니라면 현재 잘 작동하는 추론 강도를 유지하세요. Responses는 reasoning.effort, Chat Completions는 reasoning_effort를 씁니다.
  • 도구 호출: Responses API를 사용하세요. Astra가 Chat Completions도 지원하긴 하지만, 도구 호출은 반드시 Responses를 거쳐야 합니다.
  • 지원하지 않는 매개변수: temperature, top_p, top_logprobs를 제거하세요. Chat Completions에서는 logprobs도 제거해야 하고, Responses에서는 include에서 message.output_text.logprobs를 빼야 합니다.
  • Fast 모드: EU 데이터 레지던시에서는 Standard 처리를 사용하세요. Astra는 EU 데이터 레지던시에서 service_tier: "fast"나 "priority"를 지원하지 않으며, Astra의 Fast 모드에는 지연 시간 SLA가 포함되지 않습니다.
  • 추론 강도 변경: 앱이 응답 사이에 강도를 조절해야 한다면, 표준 단일 에이전트 요청에서 configuration_update 입력 항목을 사용하세요. 요청 수준의 reasoning.effort는 그대로 두어 prompt 접두부를 캐시용으로 보존합니다. 도입 전에 호환성 제약을 먼저 확인하세요.
  • Prompt 캐싱: GPT-5.5 이하 버전에서 옮겨 온다면 prompt_cache_retention을 prompt_cache_options.ttl로 바꾸고 "30m"으로 설정하세요. 캐시 경계와 캐시 쓰기 과금 등 바뀐 내용도 확인해 두세요.
  • 불필요한 승인 대기: 모델이 진행하기 전에 자꾸 승인을 요청한다면, 「주문 하나」의 주도성 지침으로 자율 실행 수준을 끌어올리세요.
💡 한 줄 요약: Astra는 더 똑똑하지만 더 「신중」하기도 합니다. 화력을 최대로 끌어내고 싶다면 prompt로 분명히 말해 주세요: 얼마나 알아서 할지, 누구 말이 우선인지, 어떻게 쓸지, 언제 위임할지, 얼마나 테스트할지.
