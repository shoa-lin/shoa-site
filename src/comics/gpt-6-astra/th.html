ทำความรู้จัก GPT-6 AstraINTRODUCTION

GPT-6 Astra คือโมเดลที่ฉลาดที่สุดของ OpenAI จนถึงตอนนี้ ทำผลงานได้ระดับแนวหน้าทั้งด้านการควบคุมคอมพิวเตอร์ (computer use) การท่องเว็บ วิศวกรรมซอฟต์แวร์ งานวิจัยวิทยาศาสตร์ และงานสายอาชีพ มันถนัดทำเวิร์กโฟลว์หลายขั้นตอนข้ามโค้ด เบราว์เซอร์ และซอฟต์แวร์เฉพาะทาง

ในหลายเกณฑ์มาตรฐาน Astra ทำคะแนนได้ดีกว่าโดยใช้โทเคนเอาต์พุตน้อยลงอย่างเห็นได้ชัด แม้ราคาต่อโทเคนจะสูงขึ้น แต่ต้นทุน API โดยประมาณต่อหนึ่งงานกลับต่ำกว่าโมเดลรุ่นก่อน ๆ

Astra ยังเป็นโมเดลที่สอดคล้องกับเจตนาผู้ใช้ (aligned) มากที่สุดด้วย: ทำงานอย่างระมัดระวัง เคารพขอบเขตของงาน และสื่อสารอย่างโปร่งใส เมื่อคำสั่งมีช่องให้ตีความ มันจะใช้บริบทที่มีอยู่เติมช่องว่างทั่วไปเอง แต่ถ้าคำตอบอาจเปลี่ยนผลลัพธ์ มันจะถามคำถามที่ตรงประเด็น มันรับความต้องการใหม่ได้ เปลี่ยนทิศทางตามที่ขอ และตอบคำถามแทรกได้โดยไม่หลุดจากงานหลัก

เรียกใช้ในคำขอ Responses API แบบนี้:

model = "gpt-6-astra"

“นิสัย” ของมันและภาพรวมวิธีปรับจูนPROMPTING BEST PRACTICES

Astra ฉลาดและเก่งกว่ารุ่นก่อนอย่าง GPT-5.6 Sol แต่ก็มีรูปแบบพฤติกรรมบางอย่างที่ปรับจูนให้ตรงจุดได้ด้วย prompt:

  • ความคิดริเริ่มและการทำต่อจนจบ — มันถูกออกแบบให้เป็นผู้ร่วมงานที่มีประสิทธิภาพกว่าเดิม ดังนั้นเมื่ออินพุตเพิ่มเติมอาจเปลี่ยนผลลัพธ์อย่างมีนัยสำคัญ มันมีแนวโน้มจะหยุดถามมากขึ้น ทั้งที่คุณอาจอยากให้มันตั้งสมมติฐานที่สมเหตุสมผลแล้วลุยต่อเอง
  • การทำตามคำสั่ง — ความสามารถทำตามคำสั่งทั่วไปแข็งแกร่งกว่าที่ผ่านมา ให้คุณควบคุมพฤติกรรมได้มากขึ้น แต่มันก็ไวต่อคำสั่งใน skills และไฟล์อย่าง AGENTS.md มากขึ้นด้วย แนะนำอย่างยิ่งให้ตรวจสอบ skills และไฟล์ที่โมเดลเข้าถึงได้ ว่ามีคำสั่งอะไรที่อาจส่งผลต่อพฤติกรรมของมันบ้าง
  • บุคลิกและสไตล์การเขียน — มักตอบยาว ละเอียด มีการจัดรูปแบบ และอาจใช้วลีเดิม ๆ ซ้ำข้ามเซสชัน ควรระบุสไตล์และโครงสร้างการเขียนที่แอปของคุณต้องการให้ชัดเจน
  • การมอบหมายงานให้ subagent — มันอาจมอบหมายงานน้อยกว่าที่เวิร์กโฟลว์ของคุณต้องการ ให้ระบุว่าเมื่อไหร่และมากแค่ไหนที่ควรใช้ subagents ทำงานแบบขนาน
  • การทดสอบและการตรวจสอบ — เวลาเขียนโค้ด มันมักทดสอบอย่างละเอียดก่อนจะถือว่างานเสร็จ ซึ่งกับงานเล็ก ๆ อาจทำให้ขอบเขตการทดสอบเกินกว่าที่งานต้องการ
04

ห้าคาถาปรับจูน (Prompt ต้นฉบับ + คำอธิบาย)PROMPT SPELLS

★คาถาที่หนึ่ง: ให้มันทำงานเองได้มากขึ้น INITIATIVE & FOLLOW-THROUGH

Astra รักษาความต่อเนื่องในงานยาว ๆ ได้ดีกว่ารุ่นก่อน แต่ก็มีแนวโน้มขอความชัดเจนในจุดที่ “รุ่นก่อนจะตั้งสมมติฐานเอง” มากกว่า ถ้าอยากให้มันทำงานเองมากขึ้น เริ่มจาก prompt นี้:

PROMPT 
You should infer the user's intent and task scope from the instructions and prior conversation context. Your job is to bias towards action and carry the user's intended task to completion.

When the user expresses intent to perform new work or fix an existing issue, persist until the user's intended goal is complete. Progress autonomously towards the user's goal (e.g. creating isolated worktrees / checkouts if needed, resolving merge conflicts, read-only actions, creating draft PRs etc.) unless they are clearly destructive or irreversible.
ให้โมเดลอนุมานเจตนาของผู้ใช้และขอบเขตงานจากบริบท เอนเอียงไปทางลงมือทำมากกว่าถาม แล้วทำงานให้จบ ตราบใดที่ไม่ใช่การกระทำที่ทำลายล้างหรือย้อนกลับไม่ได้อย่างชัดเจน (เช่น สร้าง worktree, แก้ merge conflict, การกระทำแบบอ่านอย่างเดียว, เปิด draft PR) ก็ควรเดินหน้าเองได้เลย

เมื่อเจตนาของผู้ใช้ไม่ชัด โมเดลมีแนวโน้มจะขอความชัดเจนมากขึ้น ถ้าถ้อยคำของผู้ใช้สื่อถึงการอนุญาตอยู่แล้ว ใช้ข้อนี้ให้มันลงมือทำต่อ:

PROMPT 
When the user's prompt indicates a request for action, such as "can you...", "I want to...", "help me..." and similar expressions, treat these as instructions to do the work and take action. Do not stop at acknowledging capability (e.g. "Yes…"), proposing a plan, or offering to continue. Do not settle for a partial or "helpful enough" solution that does not fully satisfy the user's task to save time, effort or tokens. If a task requires sustained work, complete all the necessary work until the intended outcome is fulfilled.
เวลาผู้ใช้พูดว่า “ช่วย…ได้ไหม” “อยากให้…” “ช่วยหน่อย…” ให้ถือเป็นคำสั่งให้ลงมือทำทันที อย่าหยุดแค่ “ได้ครับ” อย่าให้แค่แผน อย่าถามว่า “ให้ทำต่อไหม” และอย่าส่งงานครึ่ง ๆ กลาง ๆ แบบ “พอใช้ได้” เพื่อประหยัดเวลาหรือโทเคน ต้องทำจนได้ผลลัพธ์ตามที่ตั้งใจ

ให้โมเดลขออนุมัติก็ต่อเมื่อเตรียมผลงานที่เป็นรูปธรรมและรีวิวได้พร้อมแล้วเท่านั้น จะได้ไม่ติดค้างตั้งแต่ยังไม่เริ่มงาน:

PROMPT 
Before asking the user clarifying questions, you should complete the work that is already authorized from context and necessary to make the proposed action concrete and reviewable. The user should be approving a concrete, reviewable result. For example, before deploying a change, writing to an external application, merging a PR or publishing a site, do all the required work first so that user approval is the final step. You don't need user permission for reversible tasks, read-only actions, reviews or fixes, or anything for which authorization is provided earlier in the session or strongly implied from the task instruction.

Do not introduce unsolicited warnings, disclaimers, approval flows, or safety/compliance checklists due to hypothetical risk.
ก่อนจะ deploy, เขียนลงแอปภายนอก, merge PR หรือเผยแพร่เว็บไซต์ ให้ทำทุกอย่างที่ทำได้ให้เสร็จก่อน เพื่อให้การอนุมัติของผู้ใช้เป็นขั้นตอนสุดท้าย งานที่ย้อนกลับได้ การอ่านอย่างเดียว การรีวิวและแก้ไข ไม่ต้องขออนุญาต และอย่าโยนคำเตือน ข้อจำกัดความรับผิดชอบ หรือขั้นตอนอนุมัติเพิ่มเองเพราะความเสี่ยงที่แค่สมมติขึ้นมา อีกอย่าง โดยค่าเริ่มต้นโมเดลชอบถามคำถามแบบ “ไม่บล็อกงาน” ไประหว่างทำงาน ให้ปรับ prompt เหล่านี้ตามระดับความอิสระที่แอปของคุณต้องการ

★คาถาที่สอง: กำหนดลำดับความสำคัญของคำสั่งให้ชัด INSTRUCTION FOLLOWING

Astra ทำตามคำสั่งที่ยาวขึ้นได้ แต่ก็ไวต่อข้อมูลในบริบทมากขึ้นด้วย เช่น คำแนะนำที่คลุมเครือหรือขัดแย้งกันในไฟล์ skill อาจทำให้มันหยุดก่อนเวลาและบล็อกงาน ให้ประกาศลำดับความสำคัญระหว่างคำสั่งผู้ใช้กับ skills อย่างชัดเจน:

PROMPT 
The user's instructions take precedence over guidelines provided in a skill. If explicit user instructions conflict with a skill's instructions, prioritize the user's instructions.
กฎข้อเดียวจบ: คำสั่งผู้ใช้ > คำแนะนำใน skill ถ้าขัดกัน ให้ยึดผู้ใช้เป็นหลัก

เมื่อแอปโหลด skills และไฟล์คำสั่งอย่าง AGENTS.md จำนวนมาก การให้โมเดล “บอกออกมา” ว่า skill ไหน คำสั่งข้อไหน ที่ทำให้มันหยุดหรือเปลี่ยนทิศ ช่วยให้พฤติกรรมโปร่งใสขึ้นมาก:

PROMPT 
If a skill causes you to ask for permission or confirmation, pause, leave requested work unfinished, or diverge from the user's intent, name and link to the exact SKILL.md file you read, quote the relevant instruction, and briefly explain how it applies. Distinguish explicit skill requirements from your interpretation of guidelines.
กำหนดให้โมเดล เมื่อหยุด/ขอสิทธิ์/เบี่ยงจากเจตนาเพราะ skill ต้องระบุชื่อและลิงก์ไปยังไฟล์ SKILL.md ตัวนั้น พร้อมยกข้อความคำสั่งต้นฉบับ อธิบายสั้น ๆ ว่าใช้กับกรณีนี้อย่างไร และแยกให้ชัดระหว่าง “ข้อกำหนดชัดเจนของ skill” กับ “การตีความของมันเอง” ข้อนี้เหมาะมากสำหรับไล่หาคำแนะนำที่ขัดแย้งกันแบบซ่อนอยู่

★คาถาที่สาม: คุมสไตล์การเขียนของมัน PERSONALITY & WRITING STYLE

Astra ชอบใช้ลิสต์ ตาราง และ Markdown เพื่อให้คำตอบ “กวาดตาอ่านง่าย” ถ้าแอปของคุณต้องการย่อหน้าต่อเนื่องที่จัดรูปแบบน้อยกว่านี้ เขียนบอกให้ชัด:

PROMPT 
Default to using clear, concise paragraphs, each developing one main idea. Use lists only when the information is genuinely parallel, sequential, or easier to compare, and avoid nested lists unless the hierarchy cannot be expressed clearly in prose. Use plain, simple language: familiar words, concrete examples, and precise verbs. Prefer active voice and direct statements.

Make sure to state the main point clearly and early, then develop it with the explanation and detail the reader needs. Let each sentence build on what came before. Develop the points that matter and provide enough support to be useful.
ค่าเริ่มต้นให้ใช้ย่อหน้าที่ชัดเจนกระชับ (หนึ่งย่อหน้าหนึ่งใจความ) ใช้ลิสต์เฉพาะเมื่อข้อมูลขนานกัน/เป็นลำดับ/ต้องเปรียบเทียบจริง ๆ ภาษาเรียบง่าย ใช้ประโยคกรรตุวาจก บอกประเด็นหลักก่อนแล้วค่อยขยายความ ให้แต่ละประโยคต่อยอดจากประโยคก่อนหน้า

ในการสื่อสารเชิงเทคนิค ข้อนี้ช่วยให้สมดุลระหว่าง “ชัดเจนต่อเนื่อง” กับ “ดูเป็นมืออาชีพ”:

PROMPT 
Use plain language over jargon, and reference technical details only to the degree that it helps illustrate an idea or your work to the user. Communicate complex concepts in a clear and cohesive manner, and calibrate your writing to the level of background knowledge assumed from the user's prompt and context.
ลดการกองศัพท์เทคนิค อ้างถึงรายละเอียดทางเทคนิคเฉพาะเมื่อช่วยอธิบายได้จริง และปรับความลึกของการเขียนตามพื้นความรู้ของผู้ใช้

อยากลดคำสำเร็จรูปและศัพท์ “กลิ่น AI” เริ่มจากข้อนี้:

PROMPT 
Avoid using slop words or phrases like "Bottom Line:" in conclusions, "delve," "foster," "leverage," "it's worth noting," "importantly," "Question? Answer." or "This isn't about X. It's about Y.", "genuinely" or hyphenated compound descriptions and adjectives. Do not use concluding summary statements such as "In short:..", "The simplest mental model is:...".

State the intended action directly. Avoid adding what you won't do, what will remain unchanged, or how you'll separate or categorize results. Do not use contrastive framing such as "X, not Y" or "X—not Y" that introduces an unprompted alternative that the user didn't ask about. Avoid invented compound labels like "exact-head checks" and "editorial-row layouts", vague qualifiers, and canned transitions; use plain verbs and prepositions to state the actual relationship directly.
“บัญชีดำวลี AI” หนึ่งชุด: ห้ามใช้คำเกร่อ ๆ อย่าง "delve" "leverage" "it's worth noting" ห้ามสรุปแบบ "In short:" ห้ามกรอบเปรียบเทียบแบบ “ไม่ใช่ X แต่เป็น Y” ห้ามป้ายกำกับประสมที่แต่งขึ้นเองและคำเชื่อมกลวง ๆ ให้บอกการกระทำที่จะทำตรง ๆ ใช้กริยาและบุพบทธรรมดาบอกความสัมพันธ์ที่แท้จริง

★คาถาที่สี่: ปรับระดับการมอบหมายงานให้ subagent SUBAGENT DELEGATION

Astra ถูกฝึกให้ “แบ่งงานแล้วมอบหมายให้ subagent ทำแบบขนาน” ถ้า harness ของคุณมีระบบหลายเอเจนต์ ใช้ข้อนี้ปรับความเข้มของการมอบหมาย:

PROMPT 
If at any point you can parallelize work by delegating tasks to another agent (no matter if you are the root or subagent), you should do so using collaboration tools if it could save time or improve quality.
ไม่ว่าโมเดลจะเป็นเอเจนต์หลักหรือ subagent ถ้าการมอบหมายช่วยให้ทำงานแบบขนาน ประหยัดเวลา หรือเพิ่มคุณภาพได้ ก็ควรใช้เครื่องมือทำงานร่วมกันมอบหมายไป โมเดลตอบสนองต่อ prompt เรื่อง “เมื่อไหร่และอย่างไรที่ควรมอบหมาย” ได้ดี ปรับจูนตามระบบหลายเอเจนต์ของคุณได้เลย

ข้อความระหว่างเอเจนต์อาจมีไวยากรณ์หรือการเว้นวรรคผิดพลาด ข้อนี้ช่วยให้ข้อความระหว่างเอเจนต์อ่านง่ายขึ้น:

PROMPT 
Messages that you send to other agents and your final answer may be read by a human, so ensure they are legible. Always put proper spaces between words and/or numbers.
เตือนโมเดลว่า ข้อความที่ส่งให้เอเจนต์อื่นและคำตอบสุดท้ายอาจมีคนอ่าน ต้องเว้นวรรคระหว่างคำและตัวเลขให้ถูกต้อง เพื่อให้อ่านเข้าใจได้ชัดเจน

★คาถาที่ห้า: ปรับความเข้มของการทดสอบ TESTING & VERIFICATION

ในงานเขียนโค้ด การปรับว่า “การแก้หนึ่งจุดต้องทดสอบและตรวจสอบมากแค่ไหน” ช่วยเลี่ยงการทดสอบที่ไม่จำเป็นหรือตรวจซ้ำซ้อนสำหรับการแก้เล็ก ๆ:

PROMPT 
Do not write tests for reversible, low-impact changes that mirror the implementation. If you do choose to verify your work with tests, make sure that the tests are meaningful and necessary to verify implementation.

Run tests appropriate to the change and complete required checks. Once those pass, broaden or repeat testing only when new changes, failures, or unresolved concerns justify it; otherwise, continue toward completing the task.
การแก้ที่ย้อนกลับได้และผลกระทบต่ำ อย่าเขียนเทสต์ที่แค่ “ทวนการ implement” ถ้าจะเขียนต้องมีความหมายจริง ให้รันเทสต์ที่สมกับขนาดการแก้และการตรวจที่จำเป็นก่อน พอผ่านแล้ว นอกจากจะมีการแก้ใหม่ ความล้มเหลว หรือข้อสงสัยที่ยังค้าง ให้เดินหน้าทำงานต่อ อย่าขยายขอบเขตการทดสอบไม่รู้จบ

ตารางสรุปการย้ายโมเดลMIGRATION QUICKSTART

ย้ายด้วย Codex คลิกเดียว

Codex นำการเปลี่ยนแปลงที่แนะนำในคู่มือนี้ไปใช้ได้ผ่าน OpenAI Docs skill:

$openai-docs migrate this project to GPT-6 Astra

ถ้าอยากใช้ skill นี้ในเอเจนต์เขียนโค้ดตัวอื่น ดาวน์โหลดได้จากคลัง skills ของ OpenAI

ย้ายด้วยตนเอง: ตั้ง model เป็น gpt-6-astra แล้วไล่ตรวจทีละข้อ:

  • ระดับ reasoning: ถ้าตอนนี้ใช้ none หรือ minimal ให้เริ่มจาก low แล้วเปรียบเทียบผลก่อน ไม่อย่างนั้นคงระดับ reasoning ที่ใช้ได้ผลอยู่เดิมไว้ Responses ใช้ reasoning.effort ส่วน Chat Completions ใช้ reasoning_effort
  • การเรียกใช้เครื่องมือ: ใช้ Responses API แม้ Astra จะรองรับ Chat Completions แต่การเรียกใช้เครื่องมือต้องผ่าน Responses เท่านั้น
  • พารามิเตอร์ที่ไม่รองรับ: ลบ temperature, top_p, top_logprobs ออก Chat Completions ต้องลบ logprobs เพิ่มด้วย ส่วน Responses ต้องเอา message.output_text.logprobs ออกจาก include
  • โหมด Fast: ถ้าจัดเก็บข้อมูลในเขต EU ให้ใช้การประมวลผลแบบ Standard Astra ไม่รองรับ service_tier: "fast" หรือ "priority" ภายใต้ EU data residency และโหมด Fast ของ Astra ไม่มี SLA ด้านความหน่วง
  • การเปลี่ยนระดับ reasoning: ถ้าแอปต้องปรับระดับระหว่างคำตอบ ให้ใช้รายการอินพุต configuration_update ในคำขอเอเจนต์เดี่ยวแบบมาตรฐาน คง reasoning.effort ระดับคำขอไว้เท่าเดิม เพื่อรักษา prefix ของ prompt สำหรับแคช ก่อนนำไปใช้ให้ตรวจข้อจำกัดด้านความเข้ากันได้ก่อน
  • Prompt caching: เมื่อย้ายจาก GPT-5.5 หรือเก่ากว่า ให้แทน prompt_cache_retention ด้วย prompt_cache_options.ttl และตั้งเป็น "30m" อย่าลืมดูการเปลี่ยนแปลงเรื่องขอบเขตแคชและการคิดค่าใช้จ่ายการเขียนแคชด้วย
  • การหยุดขออนุมัติที่ไม่จำเป็น: ถ้าโมเดลขออนุมัติซ้ำ ๆ ก่อนจะเดินหน้าอยู่เรื่อย ให้ใช้คำแนะนำเรื่องความคิดริเริ่มจาก “คาถาที่หนึ่ง” เพื่อเพิ่มระดับการทำงานเองของมัน
💡 สรุปในหนึ่งประโยค: Astra ฉลาดขึ้นแต่ก็ “ระวังตัว” มากขึ้น ถ้าอยากให้มันปล่อยของเต็มที่ ต้องใช้ prompt บอกให้ชัดว่า: ให้ทำเองแค่ไหน ใครเป็นคนตัดสิน เขียนยังไง มอบหมายงานเมื่อไหร่ ทดสอบมากเท่าไหร่
