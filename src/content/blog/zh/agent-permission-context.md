这一年多，agent 产品换样子换得很快。先是终端和 IDE 里的编程助手，接着是桌面应用、聊天软件里的机器人，再往后，有人给 agent 配了一台云电脑，有人把它拉进团队频道，还有人给它配了自己的邮箱和手机号。

乍一看，像是每家都在折腾新壳子。我自己用两个问题来理清这些变化：

- **权限**：agent 被允许对什么动手？
- **上下文**：agent 知道什么、能留住什么？

agent 只有在这两样重合的地方才干得成活。光知道情况却动不了手，它只能当顾问；能动手却不知道情况，它就是个拿着你钥匙的陌生人。所以我的看法是：**agent 的形态，就是权限和上下文重合的那个地方**。产品每换一次形态，都是把这块重合区往外推一圈：一条轴先冲出去，另一条再追上来。

## 先看一张图

![权限 × 上下文二维图：横轴是权限范围，纵轴是上下文范围，七组产品落在图上](/assets/blog/agent-permission-context/map.svg)

*图注：横轴越往右，agent 能动的东西越多，出了错也越难收回。每个产品放在哪个位置，都是我的判断，不是厂商的说法。*

这张图只看两件事：谁落在对角线上，两条轴一起往前走；谁偏离了对角线，有一条轴先跑了出去。下面一节接一节往下推，每一节都是从上一节推出来的。

## 编程为什么最先跑出来

在聊天框里，agent 知道你说了什么，但它能做的只有回答，活还得你自己干。

仓库不一样，它把两条轴装进了同一个目录。代码、提交历史、测试，就是 agent 需要的上下文；改文件、跑命令，就是它的权限。更关键的是，这些权限收得回来：改坏了 git 能回退，改没改对测试能验收。动作能撤销，权限给大一点也不怕。

2025 年 5 月，OpenAI 发布 Codex，在隔离环境里并行做工程任务；几天后 Claude Code 正式可用，改动直接出现在你 VS Code 或 JetBrains 里的文件上。两家不约而同都从仓库下手。

![对比图：聊天框里上下文和权限几乎不重合；仓库里两者大面积重合](/assets/blog/agent-permission-context/repo.svg)

*图注：仓库是第一个「情况都在、做错能撤」的地方。*

所以，想判断一个领域什么时候能交给 agent，先看那里有没有这样一个地方：上下文齐全，动作还能撤销。

## 离开仓库，路分成两条

一离开仓库，事情就难了。你的上下文散在聊天记录、文件和各种账号里；能动手的地方散在一堆没有 API 的网站和应用里。找不到一个现成的地方能把两样同时装下，路线就分了叉。

一条路先把上下文做厚：把 agent 放进你已经在用的聊天软件，让记忆和会话留在你自己这边。OpenClaw 用一个 gateway 接进 WhatsApp、Telegram、Slack 这些渠道，工作区、记忆文件、会话、密钥都在用户手里；Hermes 的命令行、桌面应用和消息网关共用同一套会话和配置。

另一条路先把权限做宽：直接给 agent 一台电脑。图形界面加一个登录好的浏览器，是碰到「没有 API 的东西」最通用的办法。Grok Bot 在一台持久的云电脑上干活，有浏览器、文件系统和终端，会登录你已有的工具和网站；Muse 给每个人一台带浏览器的安全虚拟机，你关掉 app，它还在接着做。

![分叉图：离开仓库后，一条路先把上下文做厚，一条路先把权限做宽，最后都要补另一条轴](/assets/blog/agent-permission-context/fork.svg)

*图注：哪条轴先跑出去，另一条就是接下来要还的账。*

## 审批，是人在补上下文

先走权限这条路，马上会撞上一个问题。一台登录了你账号的电脑，什么按钮都点得了，可它不知道哪些动作你会认：你的预算是多少，你和收件人是什么关系，你的底线在哪。

这时候弹出来的每一个批准提示，其实都是 agent 在向你要它缺的那块上下文。提前写好规则，就是把这块上下文一次性交给它。Dots 的做法是让你把动作分成三档：允许、要批准、禁止。Muse 在发信、购物之前会先问你，还会留下记录。

![示意图：权限比上下文长出一截，差距靠弹窗批准、事先写规则、攒下记忆和偏好来补](/assets/blog/agent-permission-context/approval.svg)

*图注：批准弹得多，说明两条轴之间差得远。*

所以，「每做一件事要你批几次」可以当成一个读数，量的是权限和上下文之间差多远。想让它降下来，该做的是补上下文：规则、记忆、偏好，不是把闸门拆掉。

有一块上下文是故意不给的，那就是密码。Muse 把凭据放进安全存储，模型看不见你的密码和支付方式。agent 可以用，但看不见。

## 上下文攒在哪儿，入口就往哪儿收

回头看先长上下文的那条路，它说明了另一件事。

入口是终端、聊天软件、桌面还是 WhatsApp，并不改变 agent 能碰什么、知道什么，所以入口可以随便开，也可以随便合。真正一点点攒下来的是上下文：记忆、技能、会话、线程。你换产品时，丢掉的也正是这些。

于是厂商把入口往上下文攒下来的地方收拢，真正干活的执行环境退到后面，变成随时能换的后端。新版 ChatGPT 桌面把 Chat、Work、Codex 收进了一个壳；Dots 去 Codex 或 Work 里发起任务，那些任务照原来的方式计用量。Hermes 的 Bot Mode 只是一个桌面插件，关掉它，profile 和会话都还在：界面可以拆，状态一直留着。

所以 agent 真正的护城河，是它替你攒下的状态。导出、忘掉、重置、隔离，这几件事得当成产品的核心来做。

## 团队的活：频道把两条轴切在一起

一旦上下文属于好几个人，新问题就来了。团队的情况分散在每个人身上，单人用的 agent 只看得到一个人的上下文，也只能用一个人的权限。

频道一次解决了两头。Claude Tag 是 Slack 里的团队 Claude：管理员按频道给它开放工具、数据和代码库，频道里谁都能 @ 它派活；一个频道一个 Claude，它做的事整个频道都看得见，管理员还能设花费上限、看操作日志。权限的边界和上下文的边界，落在了同一个频道上。这就是它在图上能站到右上角的原因。

对比一下 Hermes 的 Bot Mode：几个有名字的 bot，各有自己的角色、模型、记忆和技能，能群聊、互相发消息，但都属于同一个用户。这是把一个人的上下文分成了几份，还没碰到别人的上下文。

所以做团队 agent，先找团队的上下文已经攒在哪儿（频道、项目、仓库），把权限挂在那儿，别挂在某一个人身上。

## 身份：让权限切得和上下文一样细

最后一圈，问题出在「agent 登录成你」这件事上。它用你的身份去操作，拿到的就是你的全部权限：切不小，也没法单独收回，要收就得连你一起收。

agent 一多，这个问题就被放大了。Grok Bot 是个很好的例子：几个 Bot 共用一台云电脑，各有各的屏幕；对话和学到的东西按 Bot 分开，文件和浏览器登录态却是共用的。上下文按 Bot 切开了，权限还是整个账号一份。

![示意图：几个 Bot 各有自己的上下文却共用整个账号的权限；换成每个 agent 有自己的身份后，上下文和权限都按 agent 切开](/assets/blog/agent-permission-context/identity.svg)

*图注：每个 Bot 都拿着全部权限，却只知道局部情况。*

给 agent 一个它自己的身份，是把权限切得和上下文一样细最直接的办法。Cue 给每个 agent 配了自己的邮箱、电话号码、钱包和电脑，只能在你设的预算里付款；Dots 的专员 dot 有自己的身份和 IT 配好的硬件，能接公司系统，不过目前还是 preview。这样一来，权限就成了一个能单独发放、设额度、吊销的东西，不再是借给 agent 的一段登录态。

有人会问，身份算不算第三条轴。我的看法是，与其说它在横轴上又往右走了一格，不如说它在问另一个问题：这份权限归谁。

## 最后

每一次形态变化，说到底都是同一件事：一条轴先冲出去，另一条追上来，重合的地方就长出新产品。下次看到一个新 agent，先别急着看入口长什么样，问它两个问题就够了：它能碰什么，它知道什么。
