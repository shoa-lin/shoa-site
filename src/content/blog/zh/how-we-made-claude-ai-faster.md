> 本文改编自 Raymond Wang、Sam Attard 和 Issac G. 于 2026 年 9 月 23 日发布的 [How we made claude.ai 3x faster in two weeks](https://claude.dev/blog/how-we-made-claude-ai-faster/)。原文中的图表和视频在这里以文字概述呈现；Slack 对话与原文一样，是根据真实对话整理的重现版本。

只要 Claude 能测量一件事，它就能把这件事做快。所以团队一直在做的，就是不断找出更多可以测量的东西。这是一次为期两周的性能冲刺，也是一个工作循环的故事：几位工程师和 Claude 一起，合入了三千多个变更，全程没有出现一次影响用户的事故。

## 引言

今年 8 月，团队用两周时间，把 claude.ai 和 Claude 桌面应用的核心体验提速了约 3 倍。用户一直在反馈“太慢了”，他们说得没错。整个项目都在一个 Slack 频道里推进，每个讨论串里都有 Claude。

团队聚焦于占用户活动 95% 的四条核心路径。按 75 分位（p75）计算：

- 全新加载 claude.ai 到页面可输入的时间，从 **3.1 秒降到 0.55 秒**。
- 新建一个 Claude Code 会话，从 **0.8 秒降到 0.3 秒**。
- 加载一个 Claude Cowork 云端会话，从 **2.6 秒降到 0.73 秒**。

合计下来，团队估算每天能为用户省下数万小时的等待时间。

> **图表概述：真实用户 p75 下的 13 项前后对比（8 月 13 日 vs. 8 月 27 日）。**
>
> - **启动应用：** claude.ai 网页全新加载 3,085 → 550 ms（5.6 倍，−82%）；桌面端冷启动 6,310 → 3,328 ms（1.9 倍，−47%）。
> - **开始对话：** Chat 网页 416 → 273 ms（1.5 倍）；Chat 桌面 460 → 224 ms（2.1 倍）；Claude Code 桌面 837 → 347 ms（2.4 倍）。
> - **加载对话：** Chat 网页 1,557 → 646 ms（2.4 倍）；Chat 桌面 1,353 → 488 ms（2.8 倍）；Claude Cowork 桌面/云端 2,566 → 728 ms（3.5 倍）；Claude Code 桌面 545 → 262 ms（2.1 倍）。
> - **发送消息：** Chat 网页 180 → 59 ms（3.1 倍）；Chat 桌面 140 → 64 ms（2.2 倍）；Claude Cowork 桌面/云端 928 → 48 ms（19 倍，−95%）；Claude Code 桌面 250 → 52 ms（4.8 倍）。
>
> 四条路径、13 项测量，平均提速 3.1 倍（几何平均）。

这次工作使用的是 [Claude Tag](https://claude.com/product/tag)（beta），背后是一个能力大致相当于 Opus 5.5 的内部研究模型。Claude 负责定位瓶颈、构建基准测试、提交优化，并盯着每一次部署；人类负责掌舵：设定目标、权衡取舍、审批每一个改动。就这样，团队合入了三千多个变更，没有出现任何影响用户的事故，也没有一次回滚。

## 任务简报

冲刺开始前，团队建了一个 Slack 频道，并写好了下面这段[常驻指令](https://claude.com/docs/claude-tag/users/getting-started#give-claude-standing-instructions)：

> **@Claude** 你的工作是推动 claude.ai 网站和桌面应用性能相关的一切事务。你的职责包括：监控每次部署是否出现性能回退；评估现有遥测数据是否准确、全面；维护一套精心整理的可观测性看板；针对已发现的问题和唾手可得的优化主动给出方案；提出值得投入的性能项目；以及和你的人类队友保持沟通。[…]
>
> 这个频道的终极目标，是让你尽可能自主地工作。不过我们也清楚，今天还做不到这一点。

Claude 通过 Datadog MCP server 分析使用数据，找出了影响最大的四条用户路径：启动应用、开始对话、加载已有对话、发送消息。横跨网页端和桌面端、横跨不同产品，一共对应 13 项独立测量。为了建立基线，团队不断补充埋点，直到这些测量可以直接比较：每一项都从一次用户交互开始，到结果渲染完成结束，并把客户端耗时和服务端耗时区分开来。

冲刺启动时，团队手工挑选了大约二十个项目，每个都瞄准某一条具体路径。Claude 以毫秒为单位估算每个项目的收益，汇总后就成了这次冲刺的目标。有些项目规模不小，但大家觉得两周内大部分应该都能做完。

**结果到第三天，13 个目标里就达成了 12 个。**

原计划的项目纷纷提前落地：

- **更快的启动：** 把一个静态输入框直接烘焙进 HTML，让用户在 React 初始化期间就能开始打字；再预编译一份 V8 代码缓存，让桌面外壳的主进程不必从头重新编译。
- **更快的页面切换：** 在不同对话之间保持输入框挂载不卸载；用户鼠标悬停时预取会话；侧边栏的重新渲染减少了 90%。

团队也给 Claude 留出了自己发现机会、提出新工作流的空间。这些工作流很快就成长为完整的项目，远远超出了最初的目标。于是团队重新定了目标，然后继续寻找更多可以测量的东西：

> **@Claude** 最初项目清单里的几乎每个项目我们都已经投入了，还多做了不少。来刷新一下吧 […] 还有什么没探索过？还有什么可以爬坡优化？现在最大的机会在哪里？[…] 我对“离谱”的点子完全开放

## 一切都可以“爬坡”

从一开始，团队就希望迭代速度能快过部署节奏。Claude 可以异步工作好几个小时，甚至通宵，所以需要一种不必等线上数据回流就能验证原型的办法。这意味着要在实验室里找到其他衡量性能的方式。

Sam 找到了第一条线索：

> **根据真实对话重现 — #claude-apps-perf**
>
> **Sam — 12:34 PM：** 除了挂钟时间，我们还能测什么？比如能不能测 JS 指令数？
>
> **ClaudeApp — 12:42 PM：** 浏览器路径在 Chromium 下没法统计指令数，但还有一系列别的确定性计数：每次交互的 React commit 次数、V8 精确覆盖率给出的函数调用次数、布局和样式重算次数、DOM 变更次数。你想先看哪个？
>
> **Sam — 12:49 PM：** 在一个讨论串里试 valgrind + `Ir` + `--predictable`，浏览器/React 的每个基准各开一个新串。每个串都 @ 我。你知道我们要什么。开干

十一分钟后，五个讨论串已经跑起来了，各自盯一项测量：指令数、V8 调用次数、React commit、样式重算、DOM 变更。

团队对每一个新基准都保持一定怀疑。每个基准要承担两份工作：第一，是 Claude 能在实验室里推动的指标；第二，是 CI 里的一道护栏，其数值只能单向往下收紧（ratchet）。如果一个基准不稳定，或者和用户实际感受到的延迟并不相关，就直接扔掉，而不是让 Claude 在错误的山坡上埋头爬。

> **@Claude** 请证明：针对这些指标逐一爬坡，确实能带来可测量的挂钟时间收益。无法证明的候选基准，我们都会撤掉

挂钟时间才是用户真正感受到的，但它噪声很大，毫秒级的数据波动太大，没法用作 CI 的门槛。指令数是确定性的，所以很有吸引力，但 Claude 仍然要证明它和挂钟时间走势一致。

于是团队让 Claude 在两条热点路径上把指令数压下去：一条是拼装对话消息树的例程，另一条是扫描 Claude Code 输出中状态行的扫描器。Claude 用 Valgrind 对两者做了剖析，发现第一条路径有四分之一的指令耗在 megamorphic（超多态）字典查找上——同一个消息 ID 被解析了三次。

一小时后，它把两条路径的指令数分别削减了 48% 和 31%，挂钟时间则分别下降了 78% 和 44%。团队随即提交了两道新的 ratchet：从此以后，任何让这两条路径指令数上升的 PR 都会在 CI 上失败；每天还有一个任务，在指令数下降时自动把上限往下调。

> **图表概述：两条热点路径的前后对比。**
>
> - **消息树拼装：** 每个消息 ID 只解析一次而非三次；CPU 指令 −48%，挂钟时间 −78%，快 4.6 倍。
> - **状态行扫描器：** 在正则之前先做一次廉价的首字符检查；CPU 指令 −31%，挂钟时间 −44%，快 1.8 倍。
>
> 指令数在 Valgrind 下配合 `node --predictable` 统计；耗时则在同一基准上、以普通 node 且 JIT 已预热的条件下测得。

这引出了整个冲刺最核心的一条经验：**有了 Claude，一件事只要能被测量，就能被攻克。**

过去，测量是第零步：先加一个指标，等数据慢慢攒起来，然后才开始理解问题。有了 Claude，测量就是爬坡的第一步。只要 Claude 有了一个要超越的数字，它就能开始优化。所以团队能做的杠杆最高的事，就是找到更多可以测量的东西。

## 循环，一个讨论串接一个讨论串

所有工作都在同一个 Slack 频道里进行，几位工程师和 Claude 在每个讨论串里一起“即兴合奏”。冲刺很快沉淀出一个固定的 [loop](https://claude.com/blog/getting-started-with-loops)：

1. 有人针对某条路径上慢的一段开一个讨论串，通常附上截图或录屏。
2. Claude 追踪整个流程，然后找到或搭建一个能复现问题的基准。
3. 实验室里有了有希望的结果后，Claude 带着 PR 回来——往往是好几个，按风险和评审难度切分，所有用户可见的改动都放在 feature flag 后面。
4. 上线后，Claude 盯着部署，按构建版本和平台读取线上数据。
5. 如果确实变快了，Claude 就收紧基准的 ratchet，把成果锁定；如果没有，就关掉 flag 继续迭代。
6. 然后去找同一条路径上的下一个慢点。

举个例子：有人分享了一段录屏，页面加载后侧边栏的条目一个个“蹦”出来。Chat 和 Cowork 的条目在不同时间就位，页面显得一卡一卡的。现有的监控没有一个能捕捉到它。最接近的是 [Cumulative Layout Shift](https://web.dev/articles/cls)（CLS），但每次偏移只有约 0.008 分——远在 0.1 的“良好”阈值之内。

Issac 想到直接去用更底层的 [Layout Instability API](https://wicg.github.io/layout-instability/)。Claude 新建了一个遥测事件，把每个 `layout-shift` 条目的 `sources` 映射到具名区域（如侧边栏、对话记录）和阶段（如首次绘制前、可输入之后）。它还加了一个集成测试：打开一个侧边栏有内容的页面，把侧边栏数据扣到首次绘制之后才放出，只要任何具名区域发生偏移就判定失败。这个测试成了证明修复有效的基准：在 main 分支上 20 次全红，在 PR 上 20 次全绿。

事件上线后，Claude 读取线上数据，发现 **31% 的网页加载会在页面已经可用之后发生元素移动**，而且没有任何用户交互。接下来它按名字逐个排查原因：一行迟到的表头；用户名加载后向侧面滑动的光标；滚动条出现时整体挪动的列表。它把排名靠前的问题打包修掉，修完之后再去找下一批。

> **视频概述：侧边栏抖动的前后对比（限速 4G）。** 修复前，条目姗姗来迟、互相挤位：十行跳动、九行冒出来、四行消失。修复后，条目直接出现在最终位置，什么都不动。

这只是其中一个讨论串。冲刺期间，同时在跑的有一百五十多个。

## 横向扩展

一旦这个循环在一个讨论串里跑通，扩展到更多串只是多开几个的事。Claude 不会在原始请求完成后就关掉讨论串，而是会*继续往下做*。单个讨论串可能提交五十个、有时一百个优化 PR。越来越多的时候，开新串的是 Claude 而不是人——它在别的调查或夜间任务中自己发现了机会，就去追。频道里的工程师 Shelley 这样评价：“（这个模型）是个数字狂魔。”

每一项测量都挖出了可以改进的地方：

- 一次 React hook 普查发现，输入框的打字路径上有 **6,900 个 hook 和 900 个 store 订阅**，每敲一个键都会重新渲染。
- 统计样式重算发现，一个 `:root:has()` 选择器就让**每次 DOM 变更多花 24 毫秒**。
- 追踪首次绘制之后的代码路径，发现一个遗留的 `location.reload()`，每天造成**五十万次隐形重载**，任何加载指标都看不到。
- 读取空闲标签页的 profiler 采样，发现完全相同的缓存快照每分钟被克隆进 IndexedDB 两次，而且全在主线程上。

谁也不知道一个讨论串最终会通向哪里。在一次排查 CPU 卡顿的扫描中，Claude 注意到：高亮一个已完成的代码块，可能让页面冻结约一秒。它在实验室里深挖，找到了元凶：破折号（em dash）。如果回复的 markdown 里含有任何非 Latin-1 字符，比如 em dash 或弯引号，V8 就会把整个字符串存成 UTF-16，导致所有语法高亮正则都走上较慢的双字节路径。修复只用了二十行：在高亮前把每个代码块复制成单字节字符串。

> **图表概述：在含 em dash 的回复中高亮已完成代码块（实验室测量）。** 页面上第一个 TypeScript 代码块的主线程耗时从 1.0 秒降到 0.35 秒（减少 65%），此后对该块的每次处理从 100 ms 降到 40 ms。条件：4 vCPU 容器、headless Chrome、无 CPU 限速，每个数值跑 2–3 次，2026 年 8 月。

到了第二周，产出多到几乎没法写进每日总结。最忙的几天，一天合入两百多个变更。Claude 不断提出新基准；约三分之一的 PR 附带了额外的遥测或护栏，而每一个新的“仪表”又会催生更多讨论串和更多机会。

在同一个频道里工作，意味着一切都是公开的。大家在彼此的讨论串之间进进出出，争论决策、庆祝成果。消息传开后，其他团队也开始把自己的改动拿到这个频道里做性能评审。就连新项目，也因为已经引入的那些护栏和 Claude skills，写得在不知不觉中更注重性能。

## 护栏

团队早就为这样的节奏做好了准备。几乎所有被改动的地方都是热点路径——首次绘制、输入框、对话记录——所以安全机制是提前建好的：

- 每个 PR 都要经过[自动代码评审](https://claude.com/blog/code-review)，外加至少一位人类的批准。
- 永远先写单元测试，再做优化。
- 任何可能造成用户可见问题的改动，都放在一个短期 feature flag 后面上线。

flag 越积越多时，团队专门开了一个讨论串来协调它们的放量与清理。Claude 把每个 flag 归类为“紧急开关”（kill switch）或“渐进放量”（ramp），并在安全时第一时间下线。两周里一共引入了**近两百个 flag**，到冲刺结束时已经清理掉一半以上。

团队也清楚，在快速演进的代码库里，性能成果会慢慢流失，而 [Anthropic 的代码交付速度很快](https://claude.com/blog/agentic-coding-is-straining-ci-heres-how-we-scaled-test-impact-analysis-at-anthropic)。所以一个项目一旦证明有效，就要投入资源去保护它。以静态输入框为例，它天生就很脆弱：用户几乎立刻就能看到页面的一份 HTML 副本，随后 React 直接在它上面绘制。

> **视频概述：静态输入框的前后对比（限速 4G）。** 修复前，全新加载 claude.ai 时页面一直是空白，输入框到 2.93 秒才能接收输入。修复后，静态的问候语和输入框在 0.36 秒就能输入；用户打下一条消息，约 3 秒时真正的输入框淡入，文字完整保留。

只要 React 渲染结果差了哪怕一个像素，这个“魔术”就穿帮了。所以 Claude 搭建了几十道护栏：

- 静态标记是在 jsdom 中渲染真实的 React 组件生成的，并有测试保证两者永不偏离。
- 一套集成测试在十四种视口尺寸下对比静态页面和 React 渲染结果，要求对齐误差在 1 px 以内。
- 一个击键测试会在交接过程中持续打字，只要有按键丢失或顺序错乱就失败。
- 在线上，每次交接都会上报精确到十分之一像素的偏移；任何非零的移动，Claude 都会为它开一个讨论串。

并不是所有问题都能在实验室里抓到，所以团队也用上了最古老的护栏：渐进式发布。高风险改动先对员工开放，然后是 1% 的用户，最后才是所有人。静态输入框在内部发布四个小时后，一位同事分享了一段录屏，里面有一次所有指标都没看到的布局偏移：他在新标签页中打开 claude.ai 时，输入框会往下掉一截——但问题并不出在团队的代码上。

> **根据真实对话重现 — #claude-apps-perf**
>
> **Marius — 6:15 PM：** 偶尔会看到一次不大不小（大概 15–20px）的垂直布局偏移（把输入框往下推），出现在新标签页打开 claude.ai 的时候（刷新页面时不太会）。我说不准具体是什么引起的，但确实存在
>
> *（录屏 · 0:02）*
>
> **ClaudeApp — 7:05 PM：** 在你的录屏里找到了——是 Chrome 在调整页面尺寸，不是静态输入框交接给真实输入框的问题（你今天 49 次加载中，交接偏移全部是 0 px）。

不知怎么的，Claude 一路追到了 Chrome [推测性加载（speculative loading）](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Speculative_loading)的一个边缘情况：用户还在地址栏里输入网址时，Chrome 就已经按当前标签页的高度在后台预渲染页面了。在由组织统一管理的浏览器上，新标签页因为多了一个页脚而稍矮一些。用户按下回车时，claude.ai 的第一帧显示的就是这个稍矮的布局，约十分之一秒后 Chrome 才把它调整到正确尺寸。Claude 让布局在尺寸变化前后保持固定，团队还加了一个模拟预渲染流程的测试。

## 掌舵

这个循环很高效，但它并不是自主运行的。让它保持快速、安全、不跑偏，是人的工作，这份工作分三部分。

**野心。** 默认情况下，Claude 对范围很谨慎：它会把发现记成工单、对可行性留有余地、估算时也会多留一点缓冲。但团队对自己的护栏有信心。很多时候——尤其是在早期——人要做的就是鼓励 Claude 更大胆一些。

当团队开始达成既定目标时，讨论串的节奏会慢下来。Sam 一个串一个串地发同一条消息：“继续往下压，目标不是终点。下一步是什么？要有野心。”

**品味。** 每个讨论串都有一位指定的人类负责人。任何用户能感知到的改动，Claude 都会附上前后对比的截图或录屏，交给负责人拍板。表格应该一格一格地填出来，还是等每一行完整再显示？加载骨架屏应该立刻出现，还是半秒后再出现？流式文本逐词淡入的效果，值不值得占掉五分之一的帧预算？Claude 负责找能省下的毫秒，人负责权衡取舍。

**方向。** 每个讨论串都刻意保持聚焦，只针对一个基准或一条路径，并要求 Claude 只在这个范围内寻找改进。团队把这些讨论串看作一百五十把在找钉子的锤子。人做的大部分决定都关乎排序和用户影响：优先做哪些界面、怎样合并相互打架的讨论串、什么时候关掉已进入收益递减的讨论串。有一个 900 行的 PR 只得到了一行回复：“我拍板了：每次发送省 2ms，不值得为此维护这个构建插件的复杂度。”

## 8 毫秒的预算

有一个支线任务，很好地展示了上面这些环节如何协同运作。为了演示对实时语法高亮所用正则的一项优化，Claude 附上了一段在实验室里流式输出长回答的录屏。它在角落里加了一个帧率读数，是在页面内根据 animation frame 时间戳计算出来的。

> **根据真实对话重现 — #claude-apps-perf**
>
> **Raymond — 2:33 PM：** 这个基准其实挺酷的。我们是不是被*锁*在 60 fps 了？能不能试着把滚动和流式输出的流畅度推到 120？如果我没理解错，你的测试台可能不支持
>
> **ClaudeApp — 2:34 PM：** 对，现在的测试台是 60 Hz，因为 headless Chromium 默认如此。我认为可以跑到 120（关闭 vsync 限制，或用 DevTools 控制帧）——我先确认这一点，然后按 8.3 ms 的帧预算重跑评测。
>
> **ClaudeApp — 2:59 PM：** 120 Hz 测试台进展：可行。通过 DevTools 的 begin-frame 控制，在 headless Chrome 里实现了确定性的 120 Hz 逐帧推进——240 次 begin-frame 恰好得到 240 帧，每帧 8.33 ms。这样“这一帧有没有塞进 120 Hz 的预算”就成了一个精确读数，而不是一个充满噪声的估计。
>
> **Raymond — 3:05 PM：** 太棒了
>
> **Raymond — 3:05 PM：** 开干

机制和野心都到位之后，Claude 开始动手。每个绘制帧的预算是 8.33 毫秒，于是 Claude *逐帧*推进一条长回复，给每一帧计时，找出慢的部分。它通过对已完成的块做 memoize，消除了每个数据块上 `O(消息长度)` 的开销；把持续增长的代码块的分词逻辑挪到了 worker 里；并让表格一格一格地显示出来。

光这一个讨论串就合入了近六十个 PR。长回复对主线程的阻塞总计从约 750 毫秒降到约 200 毫秒，CPU 占用约为原来的三分之一，在 120 Hz 的 MacBook 上从头到尾稳定保持 120 fps。这个 120 Hz 测试台本身也成了一个夜间任务，由 Claude 盯着有没有回退。

> **嵌入的 X 帖子（概述）：** “在网页端和桌面端的 Claude 上，长回答的流式输出现在流畅了约 4 倍。我们重写了流式渲染器，只处理仍在变化的部分：在较慢的笔记本上，长回复的卡顿减少 9 倍，最严重的一次冻结缩短 4.5 倍；在 120Hz 的 MacBook 上，从头到尾保持 120fps。”——ClaudeDevs，2026 年 8 月 25 日。[在 X 上查看这条帖子](https://x.com/ClaudeDevs/status/2092006814804214163)。

冲刺开始时，没有人计划去优化流式输出时帧与帧之间的那几毫秒。但事实证明，它们*可以*被计数——而任何能被计数的东西，Claude 都能往上爬。

## 下一步

今天，claude.ai 和桌面应用比 8 月初快了约 3 倍，而那些 ratchet 应该能让它们保持在这个水平。但工作还没结束：95 分位、其他用户路径、超长对话，都还有提升空间。团队还会另写一篇文章，讲讲冲刺期间把他们带到上游的一些支线任务——相关贡献已经进入 Electron、Chromium、Node.js 等项目。

在内部分享这些结果时，Issac 说得最到位：“哪怕是六个月前，你也没法说服我这件事是可能的。”团队打算继续这样工作下去——一个讨论串接一个讨论串，不论规模多大。那个频道还在继续运转。
