## 先说结论

Prompt 只是模型输入中的一小部分。真正决定 Agent 能否稳定交付的，是整个上下文系统：它在当前任务里看见哪些事实，如何筛选与压缩历史，怎样隔离子任务，以及是否有独立的验证关卡。

这篇文章把两个相互衔接的视角放在一起：Andrej Karpathy 将上下文窗口视为新的编程界面；Boris Cherny 则把这种界面放进持续运行、会验证、会积累经验的工程循环中。两者合起来，不是“写一个更长的提示词”，而是设计一套能反复做对事的工作系统。

- **上下文工程**解决“模型此刻应该知道什么”。
- **循环工程**解决“这套上下文如何持续运行、校验和改进”。
- **验证器**决定系统是否真的在进步，而不是更快地产生未经检查的输出。
- **持久化状态**让每次执行能够继承已验证的经验，而非从零开始。

## Prompt 之后：上下文才是工作环境

同一个模型、同一道题，因上下文不同而得出明显不同的结果，这并不令人意外：模型并非只执行一句指令，而是在有限的工作记忆里理解任务、读取文件、调用工具、处理历史结果并作出下一步判断。

因此，问题不应只是“这句话怎么写得更好”，而应变成：

1. 当前步骤真正需要哪些事实、文件和约束？
2. 哪些旧信息已经过时、重复或会制造噪音？
3. 哪些子问题必须与主任务隔离，避免把不相关的推理带回来？
4. 输出如何被独立检查，而不是由同一个 Agent 自证正确？

这篇文章把这种转变概括为三层演进：**Prompt engineering** 是写好一次指令；**Context engineering** 是设计模型看见的整个环境；**Loop engineering** 则把这种环境设计放入自动、重复的执行循环。

![从 Prompt Engineering 到 Context Engineering，再到 Loop Engineering 的三层演进](/assets/blog/context-engineering-karpathy-cherny/three-layers.png)

*图：三层演进图。每一层建立在前一层之上，而非彼此替代（vartekx，英文图片）。*

这三层不是替代关系。模糊的任务说明放进再精巧的循环，仍会更快地产生模糊结果；但当任务与上下文都足够清晰时，循环才会放大正确的做法。

## 上下文窗口是一块需要编排的工作内存

Karpathy 的核心比喻很有用：模型像处理器，上下文窗口像工作内存。关键不在于把所有资料塞进去，而在于在恰当的时刻放入恰当的信息。

![连续多轮交互如何持续占用有限上下文窗口](/assets/blog/context-engineering-karpathy-cherny/context-window-program.jpg)

*图：多轮输入、输出与有限上下文窗口，说明“上下文窗口就是程序”（vartekx，英文图片）。*

围绕这个目标，可以把上下文工程拆成四项操作。

![上下文窗口由系统提示、规则、记忆、工具描述、工具结果、历史与示例等共同组成](/assets/blog/context-engineering-karpathy-cherny/context-operations.png)

*图：用户实际写下的 Prompt 往往只占整个上下文的一小部分（vartekx，英文图片）。*

**写入：把可复用事实放到窗口之外。**

项目约定、命令、架构决定、排错结论和可复用脚本，不应该只存在于一次对话里。把它们沉淀为短小、可检索的文件，让 Agent 在需要时读回，才能避免每个新会话重新猜测。

这类资料的价值不在篇幅，而在可执行性。例如：测试命令是什么、哪些路径不能动、某个接口的关键不变量、一次真实故障的根因。它们应是经过验证的项目事实，而不是泛泛的“请写高质量代码”。

**选择：只取当前步骤需要的那一部分。**

更多上下文不等于更好上下文。将所有文档、聊天记录和工具输出一次性装入窗口，往往会让关键信号被噪音淹没。

选择的目标是按任务取证：修复一个接口时，优先加载该接口的入口、调用方、测试、契约和最近错误；不相关的目录、过期讨论与冗长日志应留在窗口外。真正的难点是建立可靠的检索边界，而非扩大输入长度。

**压缩：让历史服务于下一步。**

长任务必然积累历史。压缩并不是把一切粗暴总结，而是保留仍会影响决策的结论、约束、失败原因和下一步状态，同时让最新的源码、测试结果和工具输出拥有更高优先级。

若跳过这一步，模型会出现常被称为“上下文腐化”的现象：窗口容量看似没有变化，但不相关 token 越来越多，判断质量逐步下降。

**隔离：给子任务一扇上下文防火墙。**

复杂任务往往需要并行探索，但每条探索线都不该污染主任务。让子 Agent 在独立上下文中完成明确子任务，只返回结构化、可审查的结果，可以减少目标漂移和错误扩散。

隔离不是为了“多开几个 Agent”，而是为了让每个执行单元只携带完成当前工作所需的上下文。主控层负责决定任务边界、汇总证据与处理冲突。

## 循环工程：把四项操作变成持续工作的机制

文章引用 Claude Code 负责人 Boris Cherny 的观点：人的工作不应停在反复提示 Agent，而应转向设计让 Agent 自己运行的循环。这个视角把问题从单次回答提升到一个系统：每轮任务如何读取状态、执行、检查、记录结果，并在下一轮变得更好。

一个健康的循环会重复执行前述四项操作：

- 将本轮结果和关键状态写入持久层；
- 下一轮只选择与任务有关的状态；
- 总结过期或冗长的执行记录；
- 把互不依赖的子任务交给独立上下文。

换言之，上下文工程是配方，循环工程是厨房。没有好的配方，自动化只会稳定地放大问题；有了正确的上下文选择与验证，循环才会累积复利。

## 一个可落地的最小循环

不必从“全自动团队”开始。一个面向工程任务的最小循环，可以由五个部件构成：

1. **节拍与停止条件**：明确何时运行、何时才算完成，避免无限重试或过早结束。
2. **项目知识**：用简短的项目说明记录真实约束、命令和已知陷阱；只保留被实践证明有用的内容。
3. **任务隔离**：把实现与审查、信息收集与决策等角色拆开，限制每个角色的输入与输出。
4. **真实连接器**：让系统能够读取必要的代码、测试、工单或 CI 状态，但权限应与任务匹配。
5. **独立验证器**：用测试、类型检查、构建、契约检查或人工审批作为出口闸门。

其中最容易被忽略的是第五项。没有验证器，循环很可能只是让 Agent 在自身结论上不断点头。验证必须尽可能来自模型之外，或至少来自与实现阶段不同的上下文、标准和角色。

## 将“提示词”升级为规格

一次性提示通常像愿望："重构认证系统"。可执行规格则应清晰描述目标、范围、输出、冲突处理和停止条件。

例如，一个迁移任务至少应说清：哪些目录在范围内、哪些必须保持不动、需要新增或修改哪些测试、遇到冲突时是停止上报还是自行决定，以及必须通过哪些检查才可结束。Agent 因此不必靠猜测补齐缺失约束，验证器也有可据以判断的标准。

这种写法并不意味着把项目说明膨胀成百科全书。文章建议将持久规则保持精炼；更实用的原则是：每一条长期指令都应来自真实的项目约束、真实的失败或可复现的验证需求。

## 让系统积累经验，而不是积累聊天记录

完成任务后，可以把少量、行动导向的结论写入学习记录：什么做法成功，哪里失败，下一次应在何处提前检查。重复出现的失败，再提升为项目级规则或自动化检查。

这个过程形成一个闭环：执行产生证据，证据沉淀为状态，状态被下一轮有选择地读取，验证器继续过滤错误。经验由此成为可运行的上下文，而不是散落在冗长对话中的回忆。

## 结语

上下文工程不是万能药：它不能消除模型幻觉、替代领域判断、用更多资料替代更好的资料，也不能让未经验证的自动化可靠。最值得保留的不是某个命令或某款工具，而是一种工程视角：上下文窗口是程序的一部分，Agent 的输出质量取决于这部分程序如何被编排；循环让这种编排能够重复执行；验证让重复执行不至于把错误规模化。

先设计上下文，再建立循环，最后用独立证据验证结果。这样，Prompt 才不再是一次性的请求，而会成为一套可持续运行的工作系统。
