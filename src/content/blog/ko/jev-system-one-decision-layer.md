## 결론부터

Jev를 다룰 가치가 있는 이유는 조금 더 빠르고 조금 더 싸서가 아니다. 업계가 오랫동안 "LLM을 한 번 더 호출하면 되지" 속에 뭉뚱그려 온 문제를 따로 떼어냈기 때문이다. **에이전트와 자동화 워크플로 안의 수많은 고빈도 판단은 사실 글쓰기 작업이 아니라, 제약된 시맨틱 의사결정이다.**

TypeSafe AI가 2026년 9월 공개한 Jev는 이 회사의 첫 **System One Model**이다. 프로그램 상태와 구조화된 질문을 입력하면, 미리 정의된 선택지·점수·확률을 돌려주고, 소프트웨어는 이를 근거로 바로 분기할 수 있다. 자연어를 생성하지 않으며, 플래너나 강력한 추론 모델을 대체하려 하지도 않는다.

하지만 먼저 못 박아 두자.

> **Jev는 결정성(determinism)을 해결하지 않았다. 여전히 추측하고 있을 뿐이다. 제로샷 조건에서 더 빠르고, 더 싸고, 종종 더 잘 보정된(calibrated) 추측을 할 뿐이다. 출력은 0–1 사이의 확률이지, 0/1의 보증이 아니다.**

그래서 Jev의 주 무대는 좁고, 동시에 분명하다. **고빈도, 저복잡도, 시맨틱 판단, 그리고 결과를 프로그램이 바로 소비할 수 있는 경우.** "정확히 계산해야" 하거나 "왜 그런지 설명해야" 하거나 선택지를 다 나열할 수 없는 상황이라면, Jev는 최종 답이 아니다. 기껏해야 파이프라인에서 가장 저렴한 한 단계일 뿐이고, 반드시 임계값과 사람의 백업이 있어야 한다.

한 단계 위에서 업계 차원의 의미를 보면, 차세대의 신뢰할 수 있는 에이전트는 아마 "더 큰 모델 하나가 모든 것을 떠맡는" 형태가 아닐 것이다. 오히려 이렇다.

> **강력한 모델은 복잡한 추론과 생성을, 소형 의사결정 모델은 고빈도 분기를, 결정적(deterministic) 코드는 권한·실행·검증을 맡는다.**

Jev는 이 계층 구조에서 "의사결정 계층"의 초기 제품 형태다. 장기적으로 정말 가치 있는 것은 의사결정 계층을 교체 가능하고, 관측 가능하며, 폴백할 수 있는 엔지니어링 역량으로 만드는 일이다. "더 빠른 추측"을 "더 참된 앎"으로 오독하지 않는 것이다.

## Jev란 무엇인가

한 문장으로 말하면, **Jev는 소프트웨어 자동화를 위한 확률적 시맨틱 의사결정 엔진이다.**

주류 대규모 언어 모델과는 역할 분담이 꽤 다르다.

| 항목 | 일반적인 LLM | Jev (System One) |
| --- | --- | --- |
| 목표 | 텍스트, 코드, 계획, 설명 생성 | 유효한 선택지 안에서 선택 / 점수 매기기 / 확률 산출 |
| 출력 | 문자열. 이후 파싱과 검증 필요 | 타입 안전한 구조화된 의사결정 |
| 샘플링 | 자기회귀, 토큰 단위 | 벤더 설명상 병렬 sampler로 여러 질문의 결과를 한 번에 반환 |
| 지연 시간과 비용 형태 | "가끔 하는 무거운 추론"에 적합 | "핫 패스 위의 가벼운 판단"에 적합 |
| 불확실성 | 사실을 지어내거나 유효하지 않은 필드를 낼 수 있음 | 출력은 후보 공간 안으로 제한됨. **판단 자체는 여전히 틀릴 수 있음** |

더 솔직하게 말하면, Jev는 채팅 모델보다는 **제로샷 조건의 랭킹/분류 모델**에 가깝고, 충실도를 보장하는 엔진도 아니다. 애플리케이션이 먼저 유효한 의사결정 공간을 정의하고, Jev는 그 공간 안에서 확률적인 시맨틱 판단을 내놓는다. 그다음 임계값을 적용할지, 폴백할지, 실행할지는 코드가 결정한다.

TypeSafe는 자사의 학습 방향을 **RLCD(Reinforcement Learning for Calibrated Decisions)** 라고 부른다. 최적화하는 대상은 "사람이 읽기 좋아하는 답변"도, 단순히 "프로그램으로 검증 가능한 답"도 아닌, 의사결정 작업을 위한 보정된 확률이다. 공개된 자료만으로는 외부에서 전체 학습 과정을 독립적으로 재현하기 어렵기 때문에, 이는 재현 가능한 학술적 결론이 아니라 벤더의 기술 공개로 보는 것이 맞다.

이름에서도 제품 철학이 드러난다.

- **System One**: Kahneman의 『생각에 관한 생각(Thinking, Fast and Slow)』에 나오는 빠른 시스템에서 따왔다. 직관적이고 빠르며, 패턴화된 판단에 적합하다.
- **Jev**: Jevons에서 따왔다. TypeSafe의 비유는 이렇다. 지능이 충분히 싸지면 수요는 줄지 않고 오히려 폭발적으로 늘어난다.

이는 "대화를 더 잘하는 모델을 하나 더 만드는" 것과 같은 제품 곡선이 아니다. 하지만 바로 그렇기 때문에 System One을 "빠른 시스템 신화"로 포장하는 것을 더욱 경계해야 한다. 빠르다고 해서 자동으로 옳은 것은 아니다.

## 실제로 무엇을 해결하는가

지난 2년간 에이전트 엔지니어링에는 흔한 낭비가 하나 있었다.

**"다음에 어떤 버튼을 누를까", "이 메일은 긴급한가", "삭제 도구를 호출해야 할까", "더 비싼 모델로 올려야 할까"** 같은 질문을 전부 프런티어 LLM에 던져 버리는 것이다.

이 질문들에는 공통된 모양이 있다.

1. **후보 공간을 나열할 수 있다** (도구 목록, 위험 등급, 라우팅 대상).
2. **발생 빈도가 극도로 높다** (거의 모든 턴, 모든 도구 호출에서 나타날 수 있다).
3. **틀려도 임계값과 폴백으로 흡수할 수 있다.** 하지만 매번 "짧은 에세이 한 편 쓰기"의 비용을 치를 이유는 없다.
4. **정말 어려운 부분은 대개 생성이 아니라, 모호한 의미 속에서 경계가 있는 판단을 한 번 내리는 것이다.**

규칙 시스템은 너무 취약하다. 의도가 조금만 바뀌어도 `if-else`가 무너진다.  
전용 분류기는 안정적이지만, 레이블 체계가 바뀔 때마다 재학습과 재배포가 필요하다.  
대형 모델의 구조화된 출력은 쓸 만하지만, 에이전트의 핫 패스에 들어가는 순간 지연 시간, 비용, 불확실성이 함께 커진다.

Jev가 겨냥하는 곳은 바로 "규칙은 너무 딱딱하고, 소형 모델은 너무 경직되고, 대형 모델은 너무 무거운" 이 중간 지대다. **상태는 모델에 넘기고, 유효한 의사결정 공간은 애플리케이션이 정의하고, 실행은 여전히 코드가 맡는다.**

벤더가 공개한 수치는 대략 이렇다. 입력은 약 **$0.042 / 백만 토큰**, 출력은 과금하지 않는다. 엔드투엔드 지연 시간은 약 **70–500ms**로 홍보된다. Workflow evals에서는 최대 약 **193.6배 빠르고 444.6배 저렴하다**는 수치도 내세운다. 이 수치들에는 분명한 전제가 있다. 주로 미국 서부에서 측정했고, 유리한 쪽에 치우쳐 있으며, 일부 평가는 대형 외부 모델의 확률 판단을 기준으로 삼았다. **이를 여러분 업무의 정확도나 글로벌 SLA로 그대로 받아들여서는 안 된다.**

더 중요한 점은, 설령 이 수치들이 여러분의 워크로드에서 성립하더라도 증명되는 것은 단 하나라는 것이다. **똑같이 추측이지만, 이 방식의 추측이 더 싸고 더 빠르다.** 결정성이 해결되었다는 증명은 아니다. 도입을 검토할 때는 여전히 자사의 비식별화된 트래픽으로 규칙, 전용 분류기, 소형 모델의 구조화된 출력, 그리고 현재 구현과 같은 조건에서 비교해야 한다.

## 적용 범위: 어디가 주 무대이고, 어디서는 부품일 뿐인가

### 주 무대

- **Tool / Skill 라우팅**: 모델이 도구 이름을 마음대로 지어내게 두지 않고, 현재 사용 가능한 도구 중에서 다음 행동을 고른다.
- **의도 분류와 요청 등급 분류**: 고객지원 티켓, 이메일, 알림, 작업 큐의 긴급도 / 유형 / 대기열.
- **모델 라우팅**: 단순한 질의는 소형 모델로, 복잡한 디버깅은 강력한 모델로. LangChain은 이미 이런 harness 패턴을 middleware로 공개했다.
- **관련성과 우선순위 점수화**: RAG 문서 1차 선별, 리드 품질, 변경 위험 등급.
- **보안 및 정책 1차 필터링**: 도구 호출 전 위험 게이트, 사람의 확인이 필요한지, 루프에서 헛돌고 있는지.
- **폴백할지 / 격상할지**: 신뢰도가 낮으면 강력한 모델이나 사람에게 넘긴다. 완료된 것처럼 보이면 독립적인 인수 검증에 맡긴다.

이 상황들의 공통점은 고빈도, 저복잡도, 시맨틱 판단이며 결과를 프로그램이 바로 소비할 수 있다는 것이다. 한 번 틀린 대가는 임계값, 재시도, 사람의 검토로 흡수할 수 있다.

Browser Use의 오픈소스 실험 `jev-ultrafast`는 아주 깔끔한 엔지니어링 사례다. 런타임이 먼저 페이지를 인덱스가 붙은 제약된 행동 공간으로 압축하고, Jev는 operation + target 선택만 맡는다. 텍스트 입력이 필요할 때만 소형 생성 모델을 호출하고, 작업 완료 여부는 여전히 결정적 검사가 판정한다. 신뢰성은 **"제약 + 의사결정 모델 + 검증"** 에서 나오지, 단일 모델 신화에서 나오지 않는다.

### 최종 답이 아닌 곳

- 결제, DB 삭제, 권한 부여, 외부 발송 같은 고위험 행동의 **최종 승인**
- "계산"이 필요한 문제: 정밀 계산, 엄밀한 논리, 재현 가능한 수치 결과
- "왜 그런지 설명"이 필요한 문제: 감사, 의료, 대출 심사, 컴플라이언스 기록
- 선택지를 나열할 수 없는 경우, 개방형 리서치, 다단계 계획, 긴 문서 작성
- 작업 성공 여부의 **유일한 인수 검증기**

한 문장으로:

> **Jev는 게이트와 분배기로는 적합하지만, 판사나 계산기나 작가로는 적합하지 않다.**  
> 후자의 상황에서는 기껏해야 파이프라인에서 가장 저렴한 한 단계이며, 반드시 임계값과 사람의 백업이 있어야 한다.

## 에이전트의 어느 계층에 두어야 하는가

지난 1년간의 에이전트 harness / loop engineering 실무를 종합하면, 더 안정적인 파이프라인은 다음과 같다.

```text
결정적 코드 (권한 / 예산 / 사용 가능한 도구)
  → 상태 압축과 유효 후보 구성
  → Jev (분류 / 선택 / 점수화)
  → 코드 (임계값 / 판정 보류 / 충돌 검사 / fallback)
  → Tool 또는 강력한 모델
  → 독립적인 결과 검증과 trace
```

여기서 놓치기 쉬운 설계 포인트가 세 가지 있다.

1. **상태를 먼저 압축하고, 그다음에 질문하라.** Jev가 답하는 것은 여러분이 구성한 상태에 대한 경계 있는 질문이다. 원본 스크린샷을 보고 "세상 전체를 이해하는" 일을 대신해 주지 않는다.
2. **`none` / `unknown` / `fallback`은 반드시 남겨 두라.** 정보가 부족한데 셋 중 하나를 억지로 고르게 하는 것은 불확실성을 확실성으로 위장하는 일이다.
3. **여러 질문을 병렬로 묻는 것은 이득이지만, 논리적 일관성은 코드가 책임져야 한다.** 한 번의 요청으로 긴급도, 위험도, 다음 행동을 묻는 것은 괜찮다. 하지만 답이 서로 모순될 때 모델이 스스로 전체 일관성을 증명해 주리라 기대하지 마라.

이것이 "No hallucination"이 오해받기 쉬운 이유이기도 하다. 프로토콜 제약이 없애는 것은 **유효하지 않은 출력**이지, **잘못된 판단**이 아니다. 신뢰도가 높다는 것은 모델이 어떤 선택지에 더 기꺼이 걸겠다는 뜻일 뿐, 이번 업무 판단이 옳다는 뜻은 아니다. 상황 자체가 결정성을 요구한다면, 빠른 것도 싼 것도 별 의미가 없다.

## 업계의 다음 단계에 대한 내 판단

### 1. 에이전트의 병목은 "생각할 수 있는가"에서 "생각을 감당할 수 있는가, 안정적인가"로 옮겨 가고 있다

프런티어 모델은 이미 많은 복잡한 추론을 해낼 수 있다. 실제로 운영 중인 에이전트를 끌어내리는 것은 핫 패스 위에서 수백, 수천 번 일어나는 작은 판단들이다. 라우팅, 게이트, 재시도 여부, 도구 교체 여부, 멈출지 여부. 이런 판단을 계속 같은 비싼 생성 파이프라인에 밀어 넣는 것은 슈퍼컴퓨터로 병뚜껑을 따는 격이다.

Jev 같은 System One 모델은 본질적으로 이것을 인정하는 것이다. **소프트웨어 지능에는 하나의 만능 인터페이스가 아니라, 서로 다른 형태의 지능 컴포넌트가 필요하다.**

### 2. "구조화된 출력"으로는 부족하다. 다음은 "구조화된 의사결정"이다. 다만 여전히 확률적 의사결정이다

JSON mode / tool calling이 해결하는 것은 "모델이 내놓은 것을 파싱할 수 있는가"다.  
의사결정 계층이 해결하려는 것은 "애플리케이션이 정의한 유효한 공간 안에서, 임계값을 적용하고 폴백할 수 있는 확률적 판단을 내놓는 것"이다.

전자는 인터페이스 규율이고, 후자는 제어 이론에서 말하는 조절기다. 성숙한 에이전트 harness는 점점 이런 모습에 가까워질 것이다.

- Guides: 행동 전 제약 (후보 도구, 정책, 예산)
- Decision layer: 시맨틱 분기 (Jev 또는 유사 모델)
- Sensors: 행동 후 검증 (테스트, 페이지 단언, 비즈니스 규칙)

이는 "프롬프트를 한 겹 더 씌우는" 것과는 다르다. 하지만 거듭 강조해야 한다. 구조화된 의사결정도 여전히 확률적 의사결정이다. 엔지니어링은 나아졌지만, 인식론적으로 충실도 보장으로 도약한 것은 아니다.

### 3. 이것은 "대통합" 서사에 대한 교정이지, 확실성의 승리가 아니다

날카로운 비판이 하나 있다. 생성형 LLM의 목표는 원래 판별과 생성을 하나의 인터페이스로 통합하는 것이었다. Jev는 판별을 다시 떼어 내고 있으니, 빠르고 싸게 하려고 역사를 거꾸로 돌리는 것처럼 보인다는 것이다.

진보의 기준이 "하나의 모델이 모든 지능 형태를 지배하는 것"이라면, 이 비판은 옳다.

하지만 나는 다른 잣대를 쓰고 싶다. 소프트웨어 시스템의 진보는 종종 대통합이 아니라 **서로 다른 모양의 문제를 서로 다른 모양의 컴포넌트에 맡기는 것**이었다. CPU/GPU, OLTP/OLAP, 규칙 엔진과 학습 모델. 이 중 어느 것도 퇴보가 아니다. 핫 패스 위의 제어 문제가 개방형 생성과는 다른 종류의 일이라는 것을 인정한 결과다. LLM의 대통합은 제품 인터페이스 차원의 편의에 가깝지, "모든 소프트웨어 분기를 자기회귀 텍스트로 처리해야 한다"는 증명이 아니다.

그러니 더 정확한 표현은 아마 이럴 것이다.

- "정확히 계산해야 하고, 설명 가능해야 하고, 0/1 충실도가 필요한" 상황에서: Jev는 결정성을 조금도 진전시키지 않았다. 추측을 더 싸게 만들었을 뿐이다.
- "고빈도, 저복잡도, 후보를 나열할 수 있고, 결과를 프로그램이 소비하는" 상황에서: 퇴보가 아니라, LLM이 잘못 삼켜 버렸던 의사결정 계층을 다시 전문화한 것이다.
- 진짜 위험한 것은 "더 빠른 추측"을 "더 참된 앎"으로 착각하는 것이다.

> **Jev는 대통합 서사에 대한 교정이지, 불확실성의 종결이 아니다.**

### 4. 비용 하락은 청구서만이 아니라 제품의 형태를 바꾼다

한 번의 시맨틱 의사결정이 정말로 안정적으로 백 밀리초 수준에 들어오고, "기본적으로 일단 물어볼" 수 있을 만큼 싸진다면, 제품 설계는 서서히 방향을 틀게 된다.

- 예전에는 엄두를 못 냈던 실시간 라우팅, 메일 한 통 한 통의 1차 선별, 단계별 도구 게이트가 기본 아키텍처가 된다.
- 에이전트는 "가끔 부르는 컨설턴트"보다 "항상 켜져 있는 제어 시스템"에 가까워진다.
- 평가의 초점은 단일 벤치마크에서 **커버리지 × 오류 비용 × fallback 비용 × P95 지연 시간**으로 옮겨 간다.

바로 여기가 Jevons 비유가 정말 위험하면서도 정말 매력적인 지점이다. 지능이 싸지면 호출 횟수는 지수적으로 늘어날 수 있다. 좋은 관측성과 예산 통제가 없다면, 비싼 혼돈을 싸지만 더 잦은 혼돈으로 바꾼 것에 불과하다.

### 5. 초기 생태계를 아키텍처의 종착점으로 착각하지 마라

Jev를 둘러싸고 이미 LangChain middleware, Browser Use 실험, 여러 coding agent의 라우팅 / 리뷰 / 가드레일 시도가 나오고 있다. 생태계가 떠들썩하다는 것은 수요가 진짜라는 뜻이지만, 동시에 인터페이스, 평가, 모범 사례가 아직 수렴 중이라는 뜻이기도 하다.

내 제안은 분명하다.

- **연구와 파일럿: 해 볼 가치가 있다.**
- **시스템의 대체 불가능한 핵심으로: 시기상조다.**
- **쌓아야 할 것은 벤더에 종속되지 않는 의사결정 계층 역량이다:** 상태 추출, 후보 제약, 불확실성 처리, 권한, 검증, trace.

Jev는 이 계층의 엔진 중 하나가 될 수는 있지만, 이 계층의 정의 그 자체가 되어서는 안 된다.

## 첫 PoC를 한다면

**저위험, 고빈도, 후보가 명확한** 지점을 하나 고르자. 예를 들어 Tool/Skill 추천이나 모델 라우팅이다.

1. 실제 요청을 비식별화해 데이터셋을 만들고, 모호함, 정보 부족, 적절한 후보 없음, 악의적 입력을 의도적으로 포함한다.
2. 베이스라인에는 최소한 현재 구현 + 규칙 / 전용 분류기 또는 구조화된 출력을 쓰는 소형 모델을 넣는다.
3. 지표: 잘못된 추천 비율, 자동 처리 커버리지, P50/P95, fallback을 포함한 총비용, 고위험 오실행 비율.
4. 먼저 Shadow Mode로, 그다음 점진적 롤아웃. 신뢰도가 낮은 결과, 서로 충돌하는 결과, 고위험 요청은 일괄 폴백한다.

기업 통합 시에는 약관의 경계도 놓치지 말자. 표준 고객 계약은 보통 API를 자사 애플리케이션에 연결하는 것은 허용하지만, 독립 서비스로 재판매하거나 서비스/출력을 증류 또는 경쟁 모델 학습에 쓰는 것은 제한한다. 또 "Customer Data로 가중치를 수정하지 않는다"가 곧 "데이터 보존 제로"를 뜻하는 것도 아니다. 운영 전에 법무와 데이터 경로를 확실히 확인하자.

## 맺으며

Jev는 "더 작은 ChatGPT"도 아니고, "드디어 결정성을 얻었다"는 뜻도 아니다. 오히려 업계 전체에 이렇게 상기시키는 쪽에 가깝다.

> **자동화에 부족한 것은 더 강한 생성만이 아니라, 소프트웨어에 내장할 수 있고, 보정되었으며, 제약된 의사결정이다.  
> 하지만 제약된 의사결정도 무엇보다 먼저 의사결정이지, 진리가 아니다.**

앞으로 에이전트 시스템이 널리 **Reasoner + Decision Model + Deterministic Runtime**으로 향한다면, Jev의 의미는 "저렴한 모델 하나"를 넘어설 것이다. 시맨틱 의사결정 계층이라는 새로운 종류의 기반 컴포넌트를 표시하는 존재가 될 수도 있다. 동시에 계산, 설명, 충실도가 필요한 상황이라면 이 계층은 1차 선별일 뿐, 최종 판정이 될 수 없다.

에이전트와 지식 시스템을 만드는 사람에게 지금 가장 레버리지가 큰 행동은 서둘러 특정 회사의 API에 올인하는 것이 아니다. 먼저 핫 패스 위의 판단을 목록으로 정리하는 것이다. 무엇이 규칙이어야 하고, 무엇이 전용 분류기여야 하며, 무엇을 System One에 맡길 가치가 있고, 무엇을 반드시 강력한 모델과 사람에게 남겨야 하는지.

계층이 분명해져야 모델은 교체 가능한 부품이 되고,  
경계가 분명해져야 빠름과 저렴함이 옳음과 안정성으로 잘못 쓰이지 않는다.
