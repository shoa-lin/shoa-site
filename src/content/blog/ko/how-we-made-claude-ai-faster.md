> 이 글은 Raymond Wang, Sam Attard, Issac G.가 2026년 9월 23일에 발표한 [How we made claude.ai 3x faster in two weeks](https://claude.dev/blog/how-we-made-claude-ai-faster/)를 옮기고 다듬은 것이다. 원문의 차트와 영상은 본문에서 글로 요약했고, Slack 대화는 원문과 마찬가지로 실제 대화를 재구성한 것이다.

Claude는 측정할 수 있는 것이라면 빠르게 만들 수 있다. 그래서 팀은 측정할 거리를 계속 찾아냈다. 이 글은 2주간의 성능 스프린트에 관한 이야기이자, 엔지니어 몇 명과 Claude가 사용자에게 영향을 주는 장애 한 번 없이 3,000건이 넘는 변경을 배포할 수 있게 해 준 작업 루프에 관한 이야기다.

## 들어가며

올해 8월, 팀은 2주짜리 스프린트로 claude.ai와 Claude 데스크톱 앱의 핵심 사용 경험을 약 3배 빠르게 만들었다. 사용자들은 느리다고 말해 왔고, 그 말은 옳았다. 모든 작업은 하나의 Slack 채널에서 진행됐고, 모든 스레드에 Claude가 함께했다.

팀은 전체 사용자 활동의 95%를 차지하는 네 가지 여정에 집중했다. 75번째 백분위수(p75) 기준으로 보면 다음과 같다.

- claude.ai를 새로 불러와 입력 가능한 상태가 되기까지의 시간: **3.1초에서 0.55초로**.
- 새 Claude Code 세션 시작: **0.8초에서 0.3초로**.
- Claude Cowork 클라우드 세션 불러오기: **2.6초에서 0.73초로**.

이를 모두 합치면 사용자들이 기다리는 시간을 매일 수만 시간씩 줄이고 있다고 팀은 추정한다.

> **차트 요약: 실제 사용자 p75 기준 13개 항목의 전후 비교(8월 13일 vs. 8월 27일).**
>
> - **앱 실행:** claude.ai 웹 새로 불러오기 3,085 → 550 ms(5.6배, −82%), 데스크톱 콜드 스타트 6,310 → 3,328 ms(1.9배, −47%).
> - **대화 시작:** Chat 웹 416 → 273 ms(1.5배), Chat 데스크톱 460 → 224 ms(2.1배), Claude Code 데스크톱 837 → 347 ms(2.4배).
> - **대화 불러오기:** Chat 웹 1,557 → 646 ms(2.4배), Chat 데스크톱 1,353 → 488 ms(2.8배), Claude Cowork 데스크톱/클라우드 2,566 → 728 ms(3.5배), Claude Code 데스크톱 545 → 262 ms(2.1배).
> - **메시지 전송:** Chat 웹 180 → 59 ms(3.1배), Chat 데스크톱 140 → 64 ms(2.2배), Claude Cowork 데스크톱/클라우드 928 → 48 ms(19배, −95%), Claude Code 데스크톱 250 → 52 ms(4.8배).
>
> 네 가지 여정, 13개 측정 항목에서 평균 3.1배 빨라졌다(기하평균).

작업에는 [Claude Tag](https://claude.com/product/tag)(베타)를 사용했고, 그 뒤에서는 Opus 5.5와 대략 비슷한 수준의 내부 연구용 모델이 돌아갔다. Claude는 병목을 찾고, 벤치마크를 만들고, 개선 사항을 배포하고, 모든 배포를 지켜봤다. 사람은 방향을 잡았다. 목표를 정하고, 트레이드오프를 판단하고, 모든 변경을 승인했다. 이렇게 해서 사용자에게 영향을 준 장애도, 롤백도 한 번 없이 3,000건이 넘는 변경이 머지됐다.

## 브리프

스프린트에 앞서 팀은 Slack 채널을 만들고 다음과 같은 [상시 지침(standing instructions)](https://claude.com/docs/claude-tag/users/getting-started#give-claude-standing-instructions)을 걸어 두었다.

> **@Claude** 너의 일은 claude.ai 웹사이트와 데스크톱 앱의 성능과 관련된 모든 일을 이끄는 것이다. 여기에는 배포마다 성능 회귀가 없는지 모니터링하기, 기존 텔레메트리가 정확하고 충분한지 평가하기, 잘 정돈된 옵저버빌리티 대시보드를 유지하기, 관찰된 문제와 쉽게 딸 수 있는 열매에 대해 선제적으로 해결책을 구현하기, 성능 프로젝트 기회를 제안하기, 그리고 사람 동료들과 소통하기가 포함된다. […]
>
> 이 채널의 궁극적인 목표는 네가 최대한 자율적으로 일하게 되는 것이다. 하지만 오늘은 아직 그게 불가능하다는 것도 알고 있다.

Claude는 Datadog MCP 서버로 사용 데이터를 분석해 영향이 가장 큰 네 가지 사용자 여정을 찾아냈다. 앱 실행, 대화 시작, 기존 대화 불러오기, 메시지 전송이다. 웹과 데스크톱, 그리고 여러 제품에 걸쳐 보니 이 여정들은 13개의 개별 측정 항목이 됐다. 기준선을 잡기 위해 팀은 측정값을 서로 직접 비교할 수 있을 때까지 계측을 추가했다. 모든 측정은 사용자 상호작용에서 시작해 결과가 렌더링되면 끝나고, 클라이언트 작업과 서버 작업을 구분하도록 했다.

스프린트는 직접 고른 20여 개 프로젝트 목록으로 시작했다. 각 프로젝트는 특정 여정을 겨냥했다. Claude가 프로젝트마다 효과를 밀리초 단위로 추정했고, 이를 합산해 스프린트 목표를 정했다. 규모가 꽤 큰 프로젝트도 있었지만, 2주면 대부분 해낼 수 있으리라 봤다.

**그런데 사흘째에 13개 목표 중 12개를 달성했다.**

계획했던 프로젝트들은 일찍 마무리됐다.

- **더 빠른 실행:** 정적인 컴포저(입력창)를 HTML에 미리 구워 넣어 React가 초기화되는 동안에도 사용자가 입력할 수 있게 했다. 또 V8 코드 캐시를 미리 컴파일해 데스크톱 셸의 메인 프로세스가 처음부터 다시 컴파일하지 않게 했다.
- **더 빠른 화면 전환:** 대화를 오가도 컴포저가 마운트된 상태를 유지하고, 사용자가 마우스를 올리면 세션을 미리 가져오며, 사이드바 재렌더링을 90% 줄였다.

팀은 Claude가 스스로 기회를 찾아 새로운 작업 흐름을 제안할 여지도 남겨 두었다. 그 작업 흐름들은 금세 온전한 프로젝트로 커졌고, 처음 목표를 훌쩍 넘어섰다. 그래서 새 목표를 세우고, 측정할 거리를 더 찾아 나섰다.

> **@Claude** 원래 프로젝트 목록에 있던 건 거의 다 투자했고 그 이상도 했어. 한번 새로 정리해 보자 […] 아직 안 건드린 건 뭐지? 어디서 힐 클라이밍을 할 수 있을까? 지금 기회가 가장 큰 곳은 어디야? […] 엉뚱한 아이디어도 대환영

## 무엇이든 힐 클라이밍할 수 있다

팀은 처음부터 배포 주기보다 빠르게 반복하고 싶었다. Claude는 몇 시간씩, 심지어 밤새도록 비동기로 일할 수 있었고, 팀은 실서비스 데이터를 기다리지 않고도 Claude가 프로토타입을 검증할 수 있기를 원했다. 그러려면 랩(로컬 검증 환경)에서 성능을 측정할 다른 방법이 필요했다.

첫 실마리는 Sam이 찾았다.

> **실제 대화 재구성 — #claude-apps-perf**
>
> **Sam — 오후 12:34:** 벽시계 시간 말고 뭘 측정할 수 있을까? 예를 들어 JS 명령어 수를 잴 수 있나?
>
> **ClaudeApp — 오후 12:42:** 브라우저 경로는 Chromium에서 명령어 수를 셀 수 없지만, 다른 결정론적 카운트가 여러 단계로 있습니다. 상호작용당 React 커밋 수, V8 precise coverage로 얻는 함수 호출 수, 레이아웃과 스타일 재계산 횟수, DOM 변경 횟수 같은 것들요. 어떤 것부터 할까요?
>
> **Sam — 오후 12:49:** valgrind + `Ir` + `--predictable`은 스레드 하나에서, 브라우저/React 벤치는 각각 새 스레드에서 해 보자. 전부 나 멘션해 줘. 우리가 뭘 원하는지 알잖아. 가자

11분 뒤, 스레드 다섯 개가 돌아가고 있었다. 명령어 수, V8 호출 수, React 커밋, 스타일 재계산, DOM 변경을 각각 맡은 스레드였다.

팀은 새 벤치마크마다 어느 정도 의심의 눈길을 보냈다. 벤치마크에는 두 가지 역할이 있었다. 첫째, Claude가 랩에서 움직일 수 있는 지표여야 한다. 둘째, 숫자가 내려가는 방향으로만 조여지는(래칫) CI 가드레일이 되어야 한다. 벤치마크가 불안정하거나 실제 사용자 지연 시간과 상관관계가 없다면, Claude가 엉뚱한 언덕을 오르게 두느니 버렸다.

> **@Claude** 이 지표들 각각에 대해 힐 클라이밍을 하면 실제로 측정 가능한 벽시계 시간 개선이 나온다는 걸 증명해 줘. 증명하지 못하는 후보는 벤치를 내릴 거야

사용자가 체감하는 건 벽시계 시간이지만, 이 값은 노이즈가 크고 밀리초 단위 수치는 CI 관문으로 쓰기엔 너무 흔들린다. 명령어 수는 결정론적이라 매력적이었지만, 그래도 벽시계 시간과 함께 움직인다는 걸 Claude가 증명해야 했다.

그래서 Claude에게 두 핫 패스에서 명령어 수를 줄여 보라고 했다. 하나는 대화의 메시지 트리를 조립하는 루틴이고, 다른 하나는 Claude Code 출력에서 상태 줄을 찾는 스캐너였다. Claude는 두 경로를 Valgrind로 프로파일링했고, 첫 번째 경로의 명령어 중 4분의 1이 메가모픽(megamorphic) 딕셔너리 조회이며, 같은 메시지 ID를 세 번이나 따로 조회하고 있다는 사실을 찾아냈다.

한 시간 뒤, Claude는 두 경로의 명령어 수를 각각 48%, 31% 줄였고 벽시계 시간은 78%, 44% 줄어들었다. 팀은 새 래칫 두 개를 체크인했다. 이후로는 이 경로들의 명령어 수를 늘리는 PR은 모두 CI에서 실패했고, 명령어 수가 줄어들 때마다 매일 도는 작업이 상한선을 낮췄다.

> **차트 요약: 두 핫 패스의 전후 비교.**
>
> - **메시지 트리 조립:** 메시지 ID를 세 번이 아니라 한 번만 조회. CPU 명령어 −48%, 벽시계 시간 −78%, 4.6배 빨라짐.
> - **상태 줄 스캐너:** 정규식 앞에 가벼운 첫 글자 검사 추가. CPU 명령어 −31%, 벽시계 시간 −44%, 1.8배 빨라짐.
>
> 명령어 수는 Valgrind에서 `node --predictable`로, 시간은 같은 벤치마크를 일반 node에서 JIT가 예열된 상태로 측정했다.

여기서 이번 스프린트의 핵심 교훈이 나왔다. **Claude와 함께라면, 측정할 수 있는 것은 다룰 수 있다.**

예전에는 측정이 0단계였다. 지표를 추가하고, 데이터가 쌓이길 기다린 뒤에야 문제를 이해하기 시작했다. Claude와 함께라면 측정은 오르막의 1단계다. 넘어야 할 숫자만 있으면 Claude는 곧바로 최적화를 시작할 수 있다. 그러니 팀이 할 수 있는 가장 레버리지 높은 일은 측정할 거리를 더 찾는 것이었다.

## 스레드마다 도는 루프

이 모든 일은 같은 Slack 채널에서 벌어졌고, 스레드마다 여러 엔지니어와 Claude가 함께 합을 맞췄다. 스프린트는 곧 다음과 같은 [루프](https://claude.com/blog/getting-started-with-loops)로 자리 잡았다.

1. 누군가 어떤 여정의 느린 구간에 대해 스레드를 연다. 스크린숏이나 화면 녹화를 곁들이는 경우가 많다.
2. Claude가 흐름을 추적한 뒤, 문제를 드러내는 벤치마크를 찾거나 만든다.
3. 랩에서 유망한 결과가 나오면 Claude가 PR을 들고 돌아온다. 위험도와 리뷰 부담에 맞춰 여러 개로 나누는 경우가 많고, 사용자 눈에 보이는 변경은 모두 플래그 뒤에 둔다.
4. 배포되고 나면 Claude가 배포를 지켜보고, 빌드와 플랫폼별로 실서비스 데이터를 읽는다.
5. 빨라졌다면 벤치마크의 래칫을 조여 성과를 고정한다. 아니라면 플래그를 끄고 다시 반복한다.
6. 그런 다음 같은 여정의 다음 느린 지점을 찾아 나선다.

예를 하나 들어 보자. 누군가 페이지가 로드된 뒤 사이드바 항목들이 툭툭 튀어나오는 화면 녹화를 공유했다. Chat 항목과 Cowork 항목이 서로 다른 시점에 확정되다 보니 페이지가 덜컹거리는 느낌이었다. 기존 모니터링은 어느 것도 이를 잡아내지 못했다. 가장 가까운 것은 [Cumulative Layout Shift](https://web.dev/articles/cls)(CLS)였지만, 각 이동의 점수는 약 0.008에 불과해 '좋음' 기준인 0.1보다 한참 낮았다.

Issac은 그 밑에 있는 [Layout Instability API](https://wicg.github.io/layout-instability/)를 직접 참조하자는 아이디어를 냈다. Claude는 각 `layout-shift` 항목의 `sources`를 이름 붙은 영역(사이드바, 대화 기록 등)과 단계(첫 페인트 이전, 입력 가능 이후 등)에 매핑하는 텔레메트리 이벤트를 만들었다. 그리고 사이드바에 데이터가 채워진 페이지를 열되 사이드바 데이터를 첫 페인트 이후까지 붙잡아 두고, 이름 붙은 영역 어디에서든 이동이 생기면 실패하는 통합 테스트를 추가했다. 이 테스트가 수정을 증명하는 벤치마크가 됐다. main에서는 20번 중 20번 빨간불, PR에서는 20번 중 20번 초록불이었다.

이벤트가 배포되자 Claude는 실서비스 데이터를 읽고, **웹 페이지 로드의 31%에서 페이지가 이미 사용 가능해진 뒤에 무언가가 움직인다**는 사실을 발견했다. 사용자가 아무것도 하지 않았는데도 말이다. 거기서부터 Claude는 원인을 하나씩 짚어 가며 해결했다. 늦게 도착하는 헤더 행, 사용자 이름이 로드된 뒤 옆으로 밀리는 캐럿, 스크롤바가 나타나면서 움직이는 목록. 상위 원인들을 한꺼번에 고쳤고, 그것들이 사라지자 다음 묶음을 찾아냈다.

> **영상 요약: 사이드바 덜컹거림, 전후 비교(4G 속도 제한).** 수정 전에는 항목이 늦게 도착하며 자리를 바꾼다. 열 줄이 튀고, 아홉 줄이 나타나고, 네 줄이 사라진다. 수정 후에는 항목이 처음부터 최종 위치에 채워지고, 아무것도 움직이지 않는다.

이건 스레드 하나의 이야기일 뿐이다. 스프린트 기간에는 150개가 넘는 스레드가 동시에 돌아갔다.

## 수평으로 확장하기

루프가 스레드 하나에서 잘 돌아가자, 더 많은 스레드로 넓히는 건 그저 스레드를 더 여는 문제였다. Claude는 원래 요청을 끝낸 뒤에도 스레드를 닫지 않고 *계속 나아갔다*. 스레드 하나에서 최적화 PR이 50개, 때로는 100개씩 나왔다. 새 스레드를 여는 쪽이 사람이 아니라 Claude인 경우도 점점 늘었다. 다른 조사나 야간 작업 중에 스스로 발견한 기회를 쫓기 위해서였다. 채널에 있던 엔지니어 Shelley는 이렇게 말했다. "[이 모델은] 숫자 귀신이야."

측정할 때마다 개선할 거리가 나왔다.

- React 훅 전수 조사를 해 보니, 컴포저의 타이핑 경로에 **훅 6,900개와 스토어 구독 900개**가 있었고, 키를 누를 때마다 재렌더링되고 있었다.
- 스타일 재계산 횟수를 세어 보니, `:root:has()` 선택자 하나가 **DOM이 바뀔 때마다 24밀리초**를 더하고 있었다.
- 첫 페인트 이후의 코드 경로를 추적해 보니, 남아 있던 `location.reload()` 하나가 **하루 50만 번의 숨은 새로고침**을 일으키고 있었다. 어떤 로드 지표에도 잡히지 않던 것이다.
- 유휴 탭의 프로파일러 샘플을 읽어 보니, 똑같은 캐시 스냅숏이 1분에 두 번씩 IndexedDB로 복제되고 있었다. 그것도 전부 메인 스레드에서.

스레드가 어디로 이어질지는 거의 알 수 없었다. CPU 끊김을 훑던 중, Claude는 완성된 코드 블록을 하이라이팅하는 과정에서 페이지가 1초 가까이 멈출 수 있다는 걸 알아챘다. 랩에서 파고들어 보니 범인은 엠 대시(em dash)였다. 답변의 마크다운에 엠 대시나 둥근 따옴표 같은 Latin-1 밖의 문자가 하나라도 있으면, V8은 문자열 전체를 UTF-16으로 저장했다. 그 탓에 모든 구문 강조 정규식이 느린 2바이트 경로로 빠졌다. Claude는 하이라이팅 전에 각 코드 블록을 1바이트 문자열로 복사하는 20줄짜리 변경으로 이를 고쳤다.

> **차트 요약: 엠 대시가 들어간 답변에서 완성된 코드 블록 하이라이팅(랩 측정).** 페이지의 첫 TypeScript 블록은 메인 스레드 시간이 1.0초에서 0.35초로(65% 감소), 같은 블록에 대한 이후 처리는 매번 100 ms에서 40 ms로 줄었다. 조건: 4 vCPU 컨테이너, 헤드리스 Chrome, CPU 스로틀링 없음, 값마다 2~3회 실행, 2026년 8월.

둘째 주가 되자 결과물이 너무 많아 일일 업데이트로 정리하기도 버거울 정도였다. 가장 바쁜 날에는 하루에 200건이 넘는 변경이 머지됐다. Claude는 계속 새 벤치마크를 제안했다. PR의 약 3분의 1에는 텔레메트리나 가드레일이 추가로 포함됐고, 새 계측이 생길 때마다 더 많은 기회를 품은 스레드가 더 생겨났다.

하나의 채널에서 일한다는 건 모든 것이 공개적으로 이뤄진다는 뜻이었다. 사람들은 서로의 스레드를 드나들며 결정을 두고 토론하고 성과를 축하했다. 소문이 퍼지자 다른 팀들도 자기 변경을 이 채널로 가져와 성능 리뷰를 받기 시작했다. 그동안 도입된 가드레일과 Claude 스킬 덕분에, 새 프로젝트들조차 은근히 성능을 더 챙기는 방식으로 작성됐다.

## 가드레일

팀은 이런 속도에 미리 대비해 두었다. 손대는 곳이 거의 전부 핫 패스(첫 페인트, 컴포저, 대화 기록)였기 때문에 안전장치를 처음부터 마련했다.

- 모든 PR은 [자동 코드 리뷰](https://claude.com/blog/code-review)를 거치고, 최소 한 명의 사람 승인을 받는다.
- 최적화보다 단위 테스트가 항상 먼저다.
- 사용자 눈에 보이는 문제를 일으킬 수 있는 것은 모두 수명이 짧은 기능 플래그 뒤에서 배포한다.

플래그가 쌓이기 시작하자 롤아웃과 정리를 조율하는 스레드를 따로 열었다. Claude는 모든 플래그를 킬 스위치와 램프(점진 배포)로 분류했고, 안전해지는 즉시 하나씩 걷어냈다. 2주 동안 **200개 가까운 플래그**가 도입됐고, 스프린트가 끝날 무렵엔 그 절반 이상이 이미 정리돼 있었다.

빠르게 변하는 코드베이스에서는 성능 개선도 시간이 지나면 깎여 나간다. 게다가 [Anthropic에서는 코드가 빠르게 배포된다](https://claude.com/blog/agentic-coding-is-straining-ci-heres-how-we-scaled-test-impact-analysis-at-anthropic). 그래서 어떤 프로젝트가 효과를 입증하면, 팀은 그 성과를 지키는 데 투자했다. 예컨대 정적 컴포저는 구조상 깨지기 쉽다. 사용자에게 페이지의 HTML 사본을 거의 즉시 보여 주고, 그 위에 React가 곧장 그리는 방식이기 때문이다.

> **영상 요약: 정적 컴포저, 전후 비교(4G 속도 제한).** 수정 전에는 claude.ai를 새로 불러오면 페이지가 한동안 비어 있고, 컴포저는 2.93초가 되어서야 입력을 받는다. 수정 후에는 정적인 인사말과 컴포저가 0.36초 만에 입력을 받는다. 사용자가 메시지를 입력하고, 약 3초에 진짜 컴포저가 페이드인해도 입력한 텍스트는 그대로 남는다.

React 렌더링이 단 1픽셀이라도 어긋나면 마법은 깨진다. 그래서 Claude는 수십 개의 가드레일을 만들었다.

- 정적 마크업은 실제 React 컴포넌트를 jsdom에서 렌더링해 생성하고, 둘이 절대 어긋나지 않도록 테스트로 보장한다.
- 통합 테스트 묶음이 14가지 뷰포트 크기에서 정적 페이지와 React 렌더링을 비교하고, 1 px 이내로 맞는지 확인한다.
- 키 입력 테스트가 전환 과정 내내 계속 타이핑하며, 키가 하나라도 사라지거나 순서가 바뀌면 실패한다.
- 실서비스에서는 전환이 일어날 때마다 0.1픽셀 단위로 이동을 보고하고, 움직임이 0이 아닌 이벤트가 있으면 Claude가 스레드를 연다.

모든 것을 랩에서 잡을 수는 없기에, 팀은 가장 오래된 가드레일도 활용했다. 바로 점진적 롤아웃이다. 위험도가 높은 변경은 먼저 직원에게, 다음엔 사용자 1%에게, 마지막으로 모두에게 배포했다. 정적 컴포저를 사내에 공개한 지 네 시간 뒤, 한 동료가 어떤 지표로도 보이지 않던 레이아웃 이동을 담은 화면 녹화를 공유했다. 새 탭에서 claude.ai를 열면 컴포저가 아래로 툭 떨어졌다. 하지만 원인은 팀의 코드가 아니었다.

Claude는 크기가 바뀌는 동안에도 레이아웃이 고정되도록 했고, 팀은 프리렌더 흐름을 재현하는 테스트를 추가했다.

메커니즘과 야심이 갖춰지자 Claude는 작업에 들어갔다. 그려지는 프레임 하나의 예산은 8.33밀리초였다. Claude는 긴 답변을 *한 프레임씩* 넘기며 프레임마다 시간을 재 느린 부분을 찾았다. 완성된 블록을 메모이제이션해 청크마다 들던 `O(메시지 길이)` 작업을 없앴고, 계속 자라나는 코드 펜스의 토큰화 로직을 워커로 옮겼으며, 표가 셀 단위로 드러나게 했다.

이 스레드 하나에서만 PR이 60개 가까이 머지됐다. 긴 답변이 메인 스레드를 막는 시간은 합계 약 750밀리초에서 약 200밀리초로 줄었고, CPU 사용량은 약 3분의 1이 됐으며, 120 Hz MacBook에서 처음부터 끝까지 120 fps를 유지했다. 120 Hz 테스트 환경 자체도 야간 작업이 되어, Claude가 회귀를 지켜보고 있다.

스프린트를 시작할 때만 해도, 스트리밍 중 프레임 사이의 몇 밀리초를 힐 클라이밍할 계획은 없었다. 하지만 그것도 *셀 수 있다*는 게 드러났다. 그리고 셀 수 있는 것이라면 Claude는 오를 수 있다.

## 앞으로

현재 claude.ai와 데스크톱 앱은 8월 초보다 약 3배 빠르고, 래칫이 그 수준을 지켜 줄 것이다. 하지만 아직 끝나지 않았다. 95번째 백분위수, 다른 여정들, 아주 긴 대화에는 여전히 개선의 여지가 있다. 스프린트 중 팀을 업스트림으로 이끈 곁가지 작업들에 대해서도 별도의 글로 소개할 예정이다. Electron, Chromium, Node.js 등에 기여한 내용이 이미 반영되고 있다.

사내에 결과를 공유했을 때, Issac의 말이 가장 정확했다. "여섯 달 전만 해도 이게 가능하다고 나를 설득할 수는 없었을 거야." 팀은 앞으로도 이렇게 일할 생각이다. 한 번에 스레드 하나씩, 어떤 규모에서든. 그 채널은 지금도 돌아가고 있다.
