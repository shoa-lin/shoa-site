この一年あまり、agent 製品は目まぐるしく姿を変えてきた。最初はターミナルや IDE の中のコーディングアシスタント、次にデスクトップアプリやチャットツールの中のボット。その後は、agent にクラウド上のコンピュータを一台与える会社が現れ、チームのチャンネルに招き入れる会社が現れ、さらには専用のメールアドレスと電話番号を持たせる会社まで出てきた。

一見すると、各社が新しい「ガワ」をいじり回しているだけに見える。私はこうした変化を、二つの問いで整理している。

- **権限**：agent は何に対して手を動かすことを許されているか。
- **コンテキスト**：agent は何を知っていて、何を手元に残せるか。

agent が仕事をやり遂げられるのは、この二つが重なる場所だけだ。状況を知っていても手を動かせなければ、ただのアドバイザーでしかない。手を動かせても状況を知らなければ、あなたの鍵を握った見知らぬ他人にすぎない。だから私の見方はこうだ。**agent の形態とは、権限とコンテキストが重なるその場所のことである**。製品が形態を変えるたびに、この重なりが一回り外側へ押し広げられる。一方の軸が先に飛び出し、もう一方があとから追いつく。

## なぜコーディングが最初に飛び出したのか

チャット欄の中では、agent はあなたが何を言ったかを知っている。だができるのは答えることだけで、作業はあなた自身がやらなければならない。

リポジトリは違う。二つの軸を同じディレクトリの中に収めている。コード、コミット履歴、テストは agent に必要なコンテキストそのものであり、ファイルの変更やコマンドの実行はそのまま agent の権限だ。さらに重要なのは、これらの権限は取り消しがきくことだ。壊してしまっても git で戻せるし、正しく直せたかはテストで受け入れ検証できる。動作を取り消せるなら、権限を多めに与えても怖くない。

2025 年 5 月、OpenAI は Codex を公開し、隔離環境でエンジニアリングタスクを並列にこなせるようにした。その数日後には Claude Code が正式に利用可能になり、変更が VS Code や JetBrains 上のファイルに直接反映されるようになった。両社は申し合わせたわけでもないのに、そろってリポジトリから手を付けた。

![対比図：チャット欄ではコンテキストと権限がほとんど重ならない。リポジトリでは両者が大きく重なる](/assets/blog/agent-permission-context/repo-ja.svg)

*図注：リポジトリは「状況がすべて揃っていて、間違えても取り消せる」最初の場所だった。*

だから、ある領域をいつ agent に任せられるかを見極めるには、まずそこにこういう場所があるかを見ればいい。コンテキストが揃っていて、しかも動作を取り消せる場所だ。

## リポジトリを離れると、道は二手に分かれる

リポジトリを一歩出ると、途端に難しくなる。あなたのコンテキストはチャット履歴、ファイル、さまざまなアカウントに散らばっている。手を動かせる場所も、API のない大量のウェブサイトやアプリに散らばっている。両方を同時に収められる既製の場所が見つからないので、ルートが分岐する。

一つの道は、まずコンテキストを厚くする。agent をあなたがすでに使っているチャットツールの中に置き、メモリとセッションをあなたの側に残す。OpenClaw は一つの gateway で WhatsApp、Telegram、Slack といったチャネルに接続し、ワークスペース、メモリファイル、セッション、シークレットはすべてユーザーの手元にある。Hermes のコマンドライン、デスクトップアプリ、メッセージゲートウェイは、同じ一組のセッションと設定を共有している。

もう一つの道は、まず権限を広げる。agent にコンピュータを一台まるごと渡す。GUI にログイン済みのブラウザを組み合わせるのは、「API のないもの」に向き合うための最も汎用的な方法だ。Grok Bot は永続的なクラウド上のコンピュータで作業し、ブラウザ、ファイルシステム、ターミナルを持ち、あなたの既存のツールやサイトにログインする。Muse は一人ひとりにブラウザ付きの安全な仮想マシンを与え、アプリを閉じても作業を続けてくれる。

![分岐図：リポジトリを離れたあと、一方はまずコンテキストを厚くし、もう一方はまず権限を広げる。最後はどちらももう一方の軸を補うことになる](/assets/blog/agent-permission-context/fork-ja.svg)

*図注：どちらの軸が先に飛び出しても、もう一方の軸が次に返すべき借りになる。*

## 承認とは、人がコンテキストを補うこと

権限の道を先に進むと、すぐに一つの問題にぶつかる。あなたのアカウントでログインしたコンピュータは、どのボタンでも押せる。だが、どの動作ならあなたが認めるのかは知らない。予算はいくらか、受信者とはどんな関係か、譲れない一線はどこか。

このとき表示される承認ダイアログの一つひとつは、実のところ agent が足りないコンテキストをあなたに求めているのだ。ルールを事前に書いておくのは、そのコンテキストを一度にまとめて渡すことにあたる。Dots のやり方は、動作を三段階に分けさせるものだ。許可、要承認、禁止。Muse は送信や購入の前にまず確認し、記録も残す。

![概念図：権限がコンテキストより一段長く伸びており、その差をダイアログでの承認、事前のルール、蓄積したメモリと好みで埋める](/assets/blog/agent-permission-context/approval-ja.svg)

*図注：承認が頻繁に出るのは、二つの軸の差が大きいということだ。*

だから「一つの仕事につき何回承認を求められるか」は、権限とコンテキストの差を測る読み取り値として使える。これを下げたいなら、やるべきはコンテキストを補うことだ。ルール、メモリ、好み。ゲートを取り外すことではない。

意図的に渡さないコンテキストが一つある。パスワードだ。Muse は認証情報を安全なストレージに置き、モデルからはあなたのパスワードも支払い方法も見えない。agent は使えるが、見ることはできない。

## コンテキストが溜まる場所へ、入口は集約される

先にコンテキストを育てた道を振り返ると、もう一つのことが見えてくる。

入口がターミナルか、チャットツールか、デスクトップか、WhatsApp かは、agent が何に触れられ、何を知っているかを変えない。だから入口は自由に開けるし、自由に閉じられる。本当に少しずつ積み上がっていくのはコンテキストのほうだ。メモリ、スキル、セッション、スレッド。製品を乗り換えるときに失うのも、まさにこれらだ。

そこでベンダーは、入口をコンテキストが溜まっている場所へ寄せていき、実際に作業する実行環境は後ろへ下がって、いつでも差し替えられるバックエンドになる。新しい ChatGPT デスクトップは Chat、Work、Codex を一つのシェルに収めた。Dots は Codex や Work の中でタスクを起動し、それらのタスクは従来どおりの方式で使用量が計上される。Hermes の Bot Mode はデスクトップのプラグインにすぎず、オフにしても profile とセッションはそのまま残る。インターフェースは取り外せるが、状態はずっと残る。

つまり agent にとって本当の堀（moat）になるのは、あなたの代わりに溜め込んだ状態だ。エクスポート、忘却、リセット、分離。これらは製品の中核として作り込むべきものだ。

## チームの仕事：チャンネルが二つの軸を同じ線で切る

コンテキストが複数の人に属するようになると、新しい問題が出てくる。チームの状況は一人ひとりに分散している。個人用の agent は一人分のコンテキストしか見えず、使えるのも一人分の権限だけだ。

チャンネルは両端を一度に解決した。Claude Tag は Slack の中のチーム用 Claude だ。管理者がチャンネル単位でツール、データ、コードベースを開放し、チャンネルにいる誰もが @ で仕事を振れる。一つのチャンネルに一つの Claude がいて、その行動はチャンネル全体から見える。管理者は支出上限を設け、操作ログも確認できる。権限の境界とコンテキストの境界が、同じチャンネルの上に重なった。これが、図で右上に立てる理由だ。

Hermes の Bot Mode と比べてみよう。名前を持つ数体の bot が、それぞれ自分の役割、モデル、メモリ、スキルを持ち、グループチャットもできればお互いにメッセージも送れる。だがすべて同じユーザーに属している。これは一人分のコンテキストをいくつかに分けただけで、他人のコンテキストにはまだ触れていない。

だからチーム用の agent を作るなら、まずチームのコンテキストがすでにどこに溜まっているか（チャンネル、プロジェクト、リポジトリ）を探し、権限はそこに掛ける。特定の一人に掛けてはいけない。

## アイデンティティ：権限をコンテキストと同じ細かさで切る

最後の一周で問題になるのは、「agent があなたとしてログインする」ことだ。あなたの身分で操作する以上、手にするのはあなたの権限の全部になる。小さく切れないし、単独で取り消すこともできない。取り消すなら、あなたごと取り消すしかない。

agent が増えると、この問題は増幅される。Grok Bot はよい例だ。複数の Bot が一台のクラウド上のコンピュータを共有し、それぞれが自分の画面を持つ。会話と学習した内容は Bot ごとに分かれているが、ファイルとブラウザのログイン状態は共有だ。コンテキストは Bot ごとに切り分けられたのに、権限はアカウント全体で一つのままだ。

![概念図：複数の Bot がそれぞれ自分のコンテキストを持ちながら、アカウント全体の権限を共有している。各 agent に自分のアイデンティティを与えると、コンテキストも権限も agent ごとに切り分けられる](/assets/blog/agent-permission-context/identity-ja.svg)

*図注：どの Bot も全権限を握りながら、知っているのは部分的な状況だけだ。*

agent に自分自身のアイデンティティを与えるのが、権限をコンテキストと同じ細かさで切る最も直接的な方法だ。Cue は各 agent に専用のメールアドレス、電話番号、ウォレット、コンピュータを与え、あなたが設定した予算の範囲内でしか支払えないようにしている。Dots の専任 dot は自分のアイデンティティと IT 部門が用意したハードウェアを持ち、社内システムに接続できる。ただし現時点ではまだ preview だ。こうなると権限は、単独で発行し、上限を設け、失効させられるものになる。agent に貸し出したログイン状態ではなくなる。

アイデンティティは第三の軸なのか、と問う人もいるだろう。私の見方では、横軸をさらに一目盛り右へ進めたというより、別の問いを立てている。この権限は誰のものか、という問いだ。

## おわりに

形態の変化はどれも、突き詰めれば同じ一つのことだ。一方の軸が先に飛び出し、もう一方が追いつき、重なった場所に新しい製品が育つ。次に新しい agent を見かけたら、入口がどんな見た目かを急いで見るより、二つの問いを投げれば十分だ。それは何に触れられるのか、そして何を知っているのか。
