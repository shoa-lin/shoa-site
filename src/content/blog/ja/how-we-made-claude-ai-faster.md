> 原文は Raymond Wang、Sam Attard、Issac G. による [How we made claude.ai 3x faster in two weeks](https://claude.dev/blog/how-we-made-claude-ai-faster/)（2026 年 9 月 23 日公開）。原文のグラフや動画は本文中で文章として要約している。Slack のやり取りは原文と同じく、実際の会話を再構成したものだ。

Claude は、測れるものなら速くできる。だからチームは、測れるものを次々と探し続けた。これは 2 週間のパフォーマンス・スプリントの記録であり、数人のエンジニアと Claude が、ユーザーに影響するインシデントを一度も起こさずに 3,000 件以上の変更を出荷した「作業ループ」の話でもある。

## はじめに

今年 8 月、チームは 2 週間のスプリントで、claude.ai と Claude デスクトップアプリの中核となる体験を約 3 倍速くした。ユーザーからは「遅い」という声が届いていて、実際その通りだった。すべては 1 つの Slack チャンネルで進められ、どのスレッドにも Claude がいた。

対象にしたのは、ユーザー行動の 95% を占める 4 つの導線だ。75 パーセンタイル（p75）で見ると：

- claude.ai を新規に読み込んでから入力可能になるまでの時間は **3.1 秒から 0.55 秒** に。
- 新しい Claude Code セッションの開始は **0.8 秒から 0.3 秒** に。
- Claude Cowork のクラウドセッションの読み込みは **2.6 秒から 0.73 秒** に。

合計すると、ユーザーの待ち時間を毎日数万時間分削減できているとチームは見積もっている。

> **グラフの要約：実ユーザーの p75 における 13 項目のビフォー／アフター（8 月 13 日 vs. 8 月 27 日）。**
>
> - **アプリの起動：** claude.ai Web の新規読み込み 3,085 → 550 ms（5.6 倍、−82%）、デスクトップのコールドスタート 6,310 → 3,328 ms（1.9 倍、−47%）。
> - **会話の開始：** Chat Web 416 → 273 ms（1.5 倍）、Chat デスクトップ 460 → 224 ms（2.1 倍）、Claude Code デスクトップ 837 → 347 ms（2.4 倍）。
> - **会話の読み込み：** Chat Web 1,557 → 646 ms（2.4 倍）、Chat デスクトップ 1,353 → 488 ms（2.8 倍）、Claude Cowork デスクトップ／クラウド 2,566 → 728 ms（3.5 倍）、Claude Code デスクトップ 545 → 262 ms（2.1 倍）。
> - **メッセージの送信：** Chat Web 180 → 59 ms（3.1 倍）、Chat デスクトップ 140 → 64 ms（2.2 倍）、Claude Cowork デスクトップ／クラウド 928 → 48 ms（19 倍、−95%）、Claude Code デスクトップ 250 → 52 ms（4.8 倍）。
>
> 4 つの導線・13 項目の計測で、平均 3.1 倍の高速化（幾何平均）。

作業には [Claude Tag](https://claude.com/product/tag)（ベータ）を使い、その裏では Opus 5.5 とおおむね同等の社内研究用モデルが動いていた。Claude はボトルネックを見つけ、ベンチマークを作り、改善を出荷し、すべてのデプロイを見守った。人間はハンドルを握る側に回り、目標を決め、トレードオフを判断し、すべての変更を承認した。このやり方で、ユーザーに影響するインシデントもロールバックも一度もなく、3,000 件を超える変更がマージされた。

## ブリーフ

スプリントの前に、チームは Slack チャンネルを作り、次のような[常設の指示（standing instructions）](https://claude.com/docs/claude-tag/users/getting-started#give-claude-standing-instructions)を設定した。

> **@Claude** あなたの仕事は、claude.ai の Web サイトとデスクトップアプリのパフォーマンスに関わるあらゆることを推進することです。責務には、デプロイごとの性能劣化の監視、既存テレメトリの正確さと網羅性の評価、よく整理されたオブザーバビリティ・ダッシュボードの維持、観測された問題やすぐに取れる改善への先回りした対応、パフォーマンス改善プロジェクトの提案、そして人間のチームメイトとのコミュニケーションが含まれます。[…]
>
> このチャンネルの最終目標は、あなたができる限り自律的に動けるようになることです。ただ、今日の時点ではまだそれが無理なこともわかっています。

Claude は Datadog MCP サーバー経由で利用データを分析し、影響の大きい 4 つの導線を特定した。アプリの起動、会話の開始、既存の会話の読み込み、メッセージの送信だ。Web とデスクトップ、そして各プロダクトにまたがって、計測項目は 13 個になった。ベースラインを作るため、チームは計測が直接比較できるようになるまで計装を追加した。どの計測もユーザー操作で始まり、結果の描画で終わり、クライアント側とサーバー側の処理を切り分けられるようにした。

スプリントは、厳選した約 20 のプロジェクトのリストから始まった。どれも特定の導線を狙ったものだ。Claude が各プロジェクトの効果をミリ秒単位で見積もり、その合計をスプリントの目標にした。大きめのプロジェクトもあったが、2 週間あれば大半はこなせるだろうと考えていた。

**ところが 3 日目には、13 の目標のうち 12 を達成していた。**

計画していたプロジェクトは前倒しで着地した。

- **起動の高速化：** 静的なコンポーザー（入力欄）を HTML に焼き込み、React の初期化中でもユーザーが入力できるようにした。さらに V8 のコードキャッシュを事前コンパイルし、デスクトップシェルのメインプロセスがゼロから再コンパイルしなくて済むようにした。
- **画面遷移の高速化：** 会話を切り替えてもコンポーザーをマウントしたままにし、ユーザーがホバーした時点でセッションをプリフェッチし、サイドバーの再レンダリングを 90% 削減した。

Claude が自分で機会を見つけ、新しいワークストリームを提案する余地も残してあった。それらはすぐに独立したプロジェクトへと育ち、当初の目標を大きく上回った。そこで新しい目標を立て、さらに測れるものを探しにいった。

> **@Claude** 当初のプロジェクトリストはほぼ全部やり切って、それ以上のこともやった。いったん見直そう […] まだ手をつけていないのは何？ どこならヒルクライムできる？ いま一番チャンスがあるのはどこ？ […] ぶっ飛んだアイデアも大歓迎

## 何でもヒルクライムできる

チームは最初から、デプロイのサイクルより速く反復したいと考えていた。Claude は何時間も、ときには夜通し非同期で作業できる。だから本番のデータを待たずにプロトタイプを検証できるようにしたかった。そのためには、ラボ（手元の検証環境）でパフォーマンスを測る別の方法が必要だった。

最初の手がかりを見つけたのは Sam だった。

> **実際の会話を再構成 — #claude-apps-perf**
>
> **Sam — 12:34 PM：** 実時間（ウォールクロック）の代わりに何が測れる？ たとえば JS の命令数とか？
>
> **ClaudeApp — 12:42 PM：** ブラウザ側のパスは Chromium だと命令数を数えられませんが、決定論的なカウントなら段階的にいくつもあります。操作ごとの React コミット数、V8 の precise coverage による関数呼び出し回数、レイアウトとスタイル再計算の回数、DOM ミューテーション数。どれから行きますか？
>
> **Sam — 12:49 PM：** valgrind + `Ir` + `--predictable` を 1 つのスレッドで、ブラウザ／React の各ベンチはそれぞれ新しいスレッドで試そう。全部で僕をメンションして。何がほしいかはわかってるよね。行こう

11 分後には 5 つのスレッドが動いていた。命令数、V8 の呼び出し回数、React のコミット、スタイル再計算、DOM ミューテーション——それぞれ別の計測に取り組むスレッドだ。

新しいベンチマークには、どれもある程度の疑いの目を向けた。ベンチマークには 2 つの役割がある。1 つはラボで Claude が動かせる指標であること。もう 1 つは、数値が下がる方向にしか動かない（ラチェットする）CI のガードレールになることだ。不安定なベンチマークや、ユーザーが感じる遅延と実は相関していないベンチマークは、Claude に間違った山を登らせるくらいなら捨てた。

> **@Claude** それぞれの指標でヒルクライムすると、実時間で計測可能な改善が本当に出ることを証明してほしい。証明できない候補のベンチは取り下げる

ユーザーが体感するのは実時間だが、実時間はノイズが大きく、ミリ秒単位の数字は CI のゲートにするには揺れすぎる。命令数は決定論的なので魅力的だったが、それが実時間と連動することは Claude に証明してもらう必要があった。

そこで Claude に、2 つのホットパスで命令数を減らすよう頼んだ。会話のメッセージツリーを組み立てるルーチンと、Claude Code の出力からステータス行を探すスキャナーだ。Claude は両方を Valgrind でプロファイルし、1 つ目のパスでは命令の 4 分の 1 がメガモーフィックな辞書ルックアップで、同じメッセージ ID を 3 回も別々に解決していることを突き止めた。

1 時間後には、2 つのパスの命令数をそれぞれ 48% と 31% 削減し、実時間は 78% と 44% 短くなっていた。チームは新しいラチェットを 2 つ追加した。以後、これらのパスの命令数を増やす PR は CI で失敗し、命令数が下がるたびに日次ジョブが上限を引き下げる。

> **グラフの要約：2 つのホットパスのビフォー／アフター。**
>
> - **メッセージツリーの組み立て：** 各メッセージ ID の解決を 3 回から 1 回に。CPU 命令数 −48%、実時間 −78%、4.6 倍高速。
> - **ステータス行スキャナー：** 正規表現の前に先頭文字の安価なチェックを追加。CPU 命令数 −31%、実時間 −44%、1.8 倍高速。
>
> 命令数は Valgrind 上で `node --predictable` を使って計測。時間は同じベンチマークを通常の node で、JIT がウォームアップした状態で計測。

ここから、このスプリントの中心的な教訓が生まれた。**Claude と一緒なら、測れるものは攻略できる。**

これまで計測は「ステップ 0」だった。指標を追加し、データが集まるのを待ち、それからようやく問題を理解し始める。Claude と一緒なら、計測は登攀の「ステップ 1」になる。超えるべき数字さえあれば、Claude はすぐに最適化を始められる。つまり、チームにとって最もレバレッジの効く仕事は、測れるものをもっと見つけることだった。

## スレッドごとに回すループ

すべては同じ Slack チャンネルで進み、どのスレッドでも複数のエンジニアと Claude がセッションを繰り広げていた。スプリントはやがて、次のような[ループ](https://claude.com/blog/getting-started-with-loops)に落ち着いた。

1. 誰かが、ある導線の遅い区間についてスレッドを立てる。スクリーンショットや画面録画が添えられることが多い。
2. Claude がフローをトレースし、問題を再現するベンチマークを見つけるか作る。
3. ラボで有望な結果が出たら、Claude が PR を持って戻ってくる。多くの場合はリスクとレビューのしやすさに合わせて複数に分け、ユーザーの目に見える変更はすべてフラグの裏に置く。
4. 出荷後、Claude はデプロイを見守り、ビルドとプラットフォームごとに本番データを読む。
5. 速くなっていれば、ベンチマークのラチェットを締めて成果を固定する。そうでなければフラグをオフにして反復する。
6. そして同じ導線の次の遅い箇所を探しにいく。

一例を挙げよう。ある人が、ページ読み込み後にサイドバーの行がポコポコと現れる画面録画を共有した。Chat と Cowork の行が別々のタイミングで確定するので、ページがガタついて見える。既存の監視はどれもこれを検知していなかった。いちばん近いのは [Cumulative Layout Shift](https://web.dev/articles/cls)（CLS）だったが、1 回のシフトのスコアは約 0.008 にすぎず、「良好」のしきい値 0.1 を余裕で下回っていた。

Issac は、その土台にある [Layout Instability API](https://wicg.github.io/layout-instability/) を直接使うことを思いついた。Claude は、各 `layout-shift` エントリの `sources` を名前付きの領域（サイドバー、トランスクリプトなど）とフェーズ（初回描画前、入力可能後など）に対応づけるテレメトリイベントを作った。さらに、サイドバーにデータが入った状態でページを開き、サイドバーのデータを初回描画後まで保留し、名前付き領域のどこかでシフトが起きたら失敗する統合テストを追加した。これが修正を証明するベンチマークになった。main では 20 回中 20 回が赤、PR では 20 回中 20 回が緑だった。

イベントがデプロイされると、Claude は本番データを読み、**Web のページ読み込みの 31% で、ページが使える状態になった後に何かが動いている**ことを見つけた。ユーザーは何も操作していないのに、だ。そこから Claude は原因を一つずつ名指しで潰していった。遅れて届くヘッダー行、ユーザー名の読み込み後に横へずれるキャレット、スクロールバーの出現で動くリスト。上位の原因をまとめて修正し、それが片づくと次のまとまりを見つけた。

> **動画の要約：サイドバーのガタつき、ビフォー／アフター（低速 4G）。** 修正前は、行が遅れて届いて並び替わる。10 行が跳ね、9 行が現れ、4 行が消える。修正後は、行が最終的な位置に最初から埋まり、何も動かない。

これが 1 つのスレッドの話だ。スプリント中は、同時に 150 以上のスレッドが走っていた。

## 横にスケールする

ループが 1 つのスレッドで回るようになれば、あとはスレッドを増やすだけだった。Claude は元の依頼を果たしてもスレッドを閉じず、*そのまま続けた*。1 つのスレッドから 50 件、ときには 100 件もの最適化 PR が出た。新しいスレッドを立てるのが人間ではなく Claude であることも増えていった。別の調査や夜間ジョブの中で自ら見つけたチャンスを追いかけるためだ。チャンネルにいたエンジニアの Shelley は「［このモデルは］数字の鬼だ」と評した。

どの計測からも、改善の種が見つかった。

- React フックの一斉調査で、コンポーザーの入力パスに **6,900 個のフックと 900 個のストア購読** があり、キーを打つたびに再レンダリングしていることがわかった。
- スタイル再計算を数えると、たった 1 つの `:root:has()` セレクターが **DOM の変更のたびに 24 ミリ秒** を上乗せしていた。
- 初回描画後のコードパスをトレースすると、消し忘れの `location.reload()` が **1 日 50 万回の隠れたリロード** を引き起こしていた。どの読み込み指標にも表れないものだ。
- アイドル中のタブのプロファイラーサンプルを読むと、同一のキャッシュスナップショットが 1 分に 2 回 IndexedDB に複製されていた。しかもすべてメインスレッド上で。

スレッドがどこへ向かうかは、ほとんど予想できなかった。CPU の引っかかりを洗い出していたとき、Claude は完了したコードブロックのハイライト処理でページが約 1 秒固まることに気づいた。ラボで掘り下げると、犯人は em ダッシュだった。返信の Markdown に em ダッシュや曲がった引用符のような Latin-1 以外の文字が 1 つでも含まれると、V8 は文字列全体を UTF-16 で保持する。その結果、構文ハイライトの正規表現がすべて遅い 2 バイト経路に回されていた。修正は 20 行ほどの変更で、ハイライトの前に各コードブロックを 1 バイト文字列にコピーするだけだった。

> **グラフの要約：em ダッシュを含む返信で完了済みコードブロックをハイライトする処理（ラボ計測）。** ページ内最初の TypeScript ブロックのメインスレッド時間は 1.0 秒から 0.35 秒に（65% 減）、同じブロックへの 2 回目以降の処理は 100 ms から 40 ms に。条件：4 vCPU のコンテナ、ヘッドレス Chrome、CPU スロットリングなし、各値 2〜3 回計測、2026 年 8 月。

2 週目には、成果が多すぎて日次のまとめに収まらないほどになった。最も忙しい日には 200 件を超える変更がマージされた。Claude は新しいベンチマークを提案し続け、PR の約 3 分の 1 にはテレメトリやガードレールの追加が含まれていた。新しい計器が増えるたびに、新しいスレッドと新しいチャンスが生まれた。

1 つのチャンネルで作業するということは、すべてがオープンに進むということだ。エンジニアたちは互いのスレッドを出入りして、判断を議論し、成果を祝った。噂は広まり、他のチームも自分たちの変更をこのチャンネルに持ち込んでパフォーマンスレビューを受けるようになった。導入されたガードレールや Claude のスキルのおかげで、新しいプロジェクトまでもが、さりげなくパフォーマンスを意識した書き方になっていった。

## ガードレール

このペースへの備えはできていた。手を入れる場所のほとんどが、初回描画、コンポーザー、トランスクリプトといったホットパスだったので、安全装置は最初に整えておいた。

- すべての PR は[自動コードレビュー](https://claude.com/blog/code-review)を通り、さらに最低 1 人の人間の承認を得る。
- 最適化の前には必ずユニットテストを書く。
- ユーザーの目に見える問題を起こしうる変更は、すべて短命のフィーチャーフラグの裏で出荷する。

フラグが積み上がってくると、その展開と後片付けを調整する専用スレッドを立てた。Claude はすべてのフラグを「キルスイッチ」か「段階展開（ランプ）」に分類し、安全になり次第すぐに廃止した。2 週間で**約 200 個のフラグ**を導入し、スプリントの終わりにはその半分以上がすでに片づいていた。

変化の速いコードベースでは、パフォーマンスの成果は放っておくと目減りする。しかも [Anthropic ではコードの出荷が速い](https://claude.com/blog/agentic-coding-is-straining-ci-heres-how-we-scaled-test-impact-analysis-at-anthropic)。だから、あるプロジェクトの効果が証明されたら、それを守る仕組みに投資した。たとえば静的コンポーザーは、構造上どうしても壊れやすい。ユーザーにはほぼ即座にページの HTML コピーを見せ、その上に React が直接描画するからだ。

> **動画の要約：静的コンポーザー、ビフォー／アフター（低速 4G）。** 修正前は、claude.ai を新規に読み込むとページが真っ白なままで、コンポーザーが入力を受け付けるのは 2.93 秒後。修正後は、静的なあいさつ文とコンポーザーが 0.36 秒で入力可能になる。ユーザーがメッセージを打ち込み、約 3 秒後に本物のコンポーザーがフェードインしても、入力したテキストはそのまま残る。

React の描画が 1 ピクセルでもずれれば、このマジックは台無しになる。そこで Claude は数十のガードレールを作った。

- 静的マークアップは本物の React コンポーネントを jsdom でレンダリングして生成し、両者が決してずれないことをテストで保証する。
- 統合テストスイートで、静的ページと React の描画結果を 14 種類のビューポートサイズで比較し、1 px 以内で揃っていることを確認する。
- キーストロークテストで、切り替えの最中もそのまま入力を続け、キーが 1 つでも失われたり順序が入れ替わったりしたら失敗させる。
- 本番では、切り替えのたびに 0.1 ピクセル単位でシフトを報告する。ゼロでない動きがあれば、Claude がスレッドを立てる。

すべてをラボで捕まえられるわけではない。だから、昔ながらのガードレールも使った。段階的なロールアウトだ。リスクの高い変更は、まず社員に、次に 1% のユーザーに、最後に全員へと展開した。静的コンポーザーを社内公開して 4 時間後、同僚の 1 人が、どの指標にも表れないレイアウトシフトの画面録画を共有した。新しいタブで claude.ai を開くと、コンポーザーが下にずれる——だが、原因はチームのコードではなかった。

> **実際の会話を再構成 — #claude-apps-perf**
>
> **Marius — 6:15 PM：** たまに、新しいタブで claude.ai を開いたとき（リロードではあまり起きない）、ちょっとした（15〜20px くらいの）縦方向のレイアウトシフトが起きて、コンポーザーが押し下げられる。何が原因かははっきりしないけど、確かに起きてる
>
> *（画面録画・0:02）*
>
> **ClaudeApp — 7:05 PM：** 録画から見つけました。Chrome がページをリサイズしているのが原因で、静的コンポーザーから本物への切り替えではありません（そちらは今日のあなたの 49 回の読み込みすべてで 0 px でした）。

どうやったのか、Claude はこれを Chrome の[投機的読み込み（speculative loading）](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Speculative_loading)のエッジケースまで突き止めた。ユーザーがアドレスバーに URL を打ち込んでいる間に、Chrome は現在のタブの高さでページをバックグラウンドでプリレンダリングする。組織が管理しているブラウザでは、新しいタブのページがフッターのぶんだけ少し低い。ユーザーが Enter を押すと、claude.ai の最初のフレームはその少し低いレイアウトで表示され、約 0.1 秒後に Chrome がリサイズしていたのだ。Claude はリサイズの前後でレイアウトを固定し、チームはプリレンダリングの流れを再現するテストを追加した。

## 舵取り

ループは生産的だったが、自律的ではなかった。速く、安全に、軌道を外れずに回し続けるのは人間の仕事で、その仕事には 3 つの側面があった。

**野心。** Claude はデフォルトでは作業範囲に慎重だ。発見したことをチケットにし、実現可能性には予防線を張り、見積もりには余裕を持たせる。しかしチームはガードレールに自信があった。特に序盤は、Claude にもっと大胆になるよう背中を押すことが仕事の大部分だった。

>
> **ClaudeApp — 3:32 PM：** はい、Chat と Cowork にはすでにあるタイミングマークを Code にも入れる小さな PR を 1 本。今週中に出します。現実的には、マージ、デプロイ、ベースライン期間を待つので、Code の数字が出るのは数日後ですね。
>
> **Raymond — 3:32 PM：** 今すぐ出してくれたら、マージもデプロイもすぐやる。僕らには何だってできる力がある。もっと勇敢になって
>
> **ClaudeApp — 3:33 PM：** 了解です。1 時間以内に PR を出します。

設定した目標を達成し始めると、スレッドの勢いが落ちることにチームは気づいた。Sam はスレッドを一つずつ回り、同じメッセージを送った。「このまま下げ続けよう。目標はゴールじゃない。次は何？ 野心的にいこう」

**センス。** どのスレッドにも名前のある人間のオーナーがいて、ユーザーが体感できる変更については、Claude がビフォー／アフターのスクリーンショットや録画を添えてオーナーの判断を仰いだ。表はセルごとに埋めていくべきか、行がそろうまで待つべきか。ローディングのスケルトンはすぐ出すべきか、0.5 秒経ってからにすべきか。ストリーミング中のテキストを単語ごとにフェードインさせる演出は、フレーム予算の 5 分の 1 を使うだけの価値があるか。Claude はミリ秒を削る方法を探し、人間がトレードオフを量った。

**方向づけ。** 各スレッドは意図的にスコープを狭くし、1 つのベンチマークか導線だけに集中させ、Claude にはその範囲内でのみ改善を探すよう求めた。チームはスレッドを「釘を探す 150 本のハンマー」と捉えていた。人間の判断の大半は、順序とユーザーへの影響に関するものだった。どの画面を優先するか、互いに干渉し合うスレッドをどうまとめるか、収穫逓減に入ったスレッドをいつ閉じるか。900 行のある PR には、たった 1 行の返信がついた。「裁定：送信 1 回あたり 2ms のために、このビルドプラグインを保守する複雑さを抱える価値はない」

## 8 ミリ秒の予算

ある寄り道が、これらすべてがかみ合う様子をよく表している。ライブの構文ハイライトで使う正規表現の最適化を示すため、Claude はラボで長い回答がストリーミングされる画面録画を添付した。画面の隅には、アニメーションフレームのタイムスタンプからページ内で計算したフレームレート表示を加えていた。

> **実際の会話を再構成 — #claude-apps-perf**
>
> **Raymond — 2:33 PM：** これ、実はかなりイケてるベンチだね。60 fps で*頭打ち*になってる？ スクロールとストリーミングの滑らかさを 120 まで上げられる？ 僕の理解が正しければ、今の環境だと対応してないかもだけど
>
> **ClaudeApp — 2:34 PM：** そうです。今の環境はヘッドレス Chromium のデフォルトどおり 60 Hz で動いています。120 でも動かせるはずです（vsync の上限解除か DevTools のフレーム制御）。まずそれを確認してから、8.3 ms のフレーム予算で評価をやり直します。
>
> **ClaudeApp — 2:59 PM：** 120 Hz 環境の進捗：動きました。DevTools の begin-frame 制御で、ヘッドレス Chrome 上で決定論的に 120 Hz のフレーム送りができます。8.33 ms 間隔の begin-frame 240 回に対してちょうど 240 フレーム。これで「このフレームは 120 Hz の予算に収まったか」が、ノイズまじりの推定ではなく正確な読み値になります。
>
> **Raymond — 3:05 PM：** 最高
>
> **Raymond — 3:05 PM：** やっちゃって

仕組みと野心がそろうと、Claude は作業に取りかかった。描画される 1 フレームの予算は 8.33 ミリ秒。Claude は長い返信を*1 フレームずつ*進め、各フレームの時間を測って遅い箇所を探した。完了したブロックをメモ化してチャンクごとの `O(メッセージ長)` の処理をなくし、伸び続けるコードフェンスのトークナイズ処理をワーカーに移し、表をセル単位で表示するようにした。

この 1 つのスレッドだけで、60 件近くの PR がマージされた。長い返信がメインスレッドをブロックする時間は合計で約 750 ミリ秒から約 200 ミリ秒に減り、CPU 使用量は約 3 分の 1 になり、120 Hz の MacBook では最初から最後まで 120 fps を維持するようになった。120 Hz の検証環境そのものも夜間ジョブになり、Claude が性能劣化を見張っている。

> **埋め込まれた X の投稿（要約）：** 「Web とデスクトップの Claude で、長い回答のストリーミングが約 4 倍なめらかになりました。まだ変化している部分だけを触るようにストリーミングレンダラーを作り直したので、遅めのノート PC では長い返信の引っかかりが 9 分の 1 に、最悪のフリーズは 4.5 分の 1 に短縮され、120Hz の MacBook では最初から最後まで 120fps を保ちます。」——ClaudeDevs、2026 年 8 月 25 日。[X で投稿を見る](https://x.com/ClaudeDevs/status/2092006814804214163)。

スプリントを始めたとき、ストリーミング中のフレーム間の数ミリ秒をヒルクライムするつもりは誰にもなかった。だが、それも数えられることがわかった——そして数えられるものなら、Claude は登っていける。

## 次に向けて

いま、claude.ai とデスクトップアプリは 8 月初めと比べて約 3 倍速く、ラチェットがその水準を守ってくれるはずだ。とはいえ、まだ終わりではない。95 パーセンタイル、ほかの導線、非常に長い会話には、まだ改善の余地がある。スプリント中にチームを上流へと導いた寄り道についても、別の記事で紹介する予定だ。Electron、Chromium、Node.js などへの貢献がすでにマージされている。

社内で結果を共有したとき、Issac の言葉がいちばん的を射ていた。「たとえ半年前でも、これが可能だなんて誰にも説得できなかったと思う」。チームはこれからもこのやり方を続けるつもりだ。1 スレッドずつ、どんな規模でも。チャンネルはいまも動き続けている。
