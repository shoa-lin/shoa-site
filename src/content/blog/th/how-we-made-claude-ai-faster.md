> บทความนี้เรียบเรียงจาก [How we made claude.ai 3x faster in two weeks](https://claude.dev/blog/how-we-made-claude-ai-faster/) โดย Raymond Wang, Sam Attard และ Issac G. เผยแพร่เมื่อวันที่ 23 กันยายน 2026 กราฟและวิดีโอในต้นฉบับถูกสรุปเป็นข้อความไว้ในบทความนี้ ส่วนบทสนทนาใน Slack เป็นการจำลองจากบทสนทนาจริงเช่นเดียวกับในต้นฉบับ

เมื่อ Claude วัดอะไรได้ มันก็ทำให้สิ่งนั้นเร็วขึ้นได้ ทีมจึงคอยหาสิ่งใหม่ ๆ มาวัดอยู่เรื่อย ๆ นี่คือเรื่องราวของสปรินต์ด้านประสิทธิภาพสองสัปดาห์ และของวงจรการทำงานที่ทำให้วิศวกรไม่กี่คนกับ Claude ส่งการเปลี่ยนแปลงได้มากกว่าสามพันรายการ โดยไม่มีเหตุขัดข้องที่กระทบผู้ใช้เลยแม้แต่ครั้งเดียว

## บทนำ

เดือนสิงหาคมที่ผ่านมา ทีมใช้สปรินต์สองสัปดาห์ทำให้ประสบการณ์หลักของ claude.ai และแอป Claude บนเดสก์ท็อปเร็วขึ้นราว 3 เท่า ผู้ใช้บอกมาตลอดว่ามันช้า และพวกเขาก็พูดถูก งานทั้งหมดดำเนินจากช่อง Slack ช่องเดียว และมี Claude อยู่ในทุกเธรด

ทีมโฟกัสที่เส้นทางการใช้งานสี่แบบ ซึ่งคิดเป็น 95% ของกิจกรรมผู้ใช้ทั้งหมด ที่เปอร์เซ็นไทล์ที่ 75 (p75):

- เวลาตั้งแต่โหลด claude.ai ใหม่จนหน้าเว็บพร้อมให้พิมพ์ ลดจาก **3.1 วินาทีเหลือ 0.55 วินาที**
- การเริ่มเซสชัน Claude Code ใหม่ ลดจาก **0.8 วินาทีเหลือ 0.3 วินาที**
- การโหลดเซสชันคลาวด์ของ Claude Cowork ลดจาก **2.6 วินาทีเหลือ 0.73 วินาที**

รวม ๆ แล้ว ทีมประเมินว่าช่วยประหยัดเวลารอของผู้ใช้ได้หลายหมื่นชั่วโมงต่อวัน

> **สรุปกราฟ: การจับเวลาก่อน–หลัง 13 รายการ ที่ p75 ของผู้ใช้จริง (13 สิงหาคม เทียบกับ 27 สิงหาคม)**
>
> - **เปิดแอป:** โหลด claude.ai บนเว็บใหม่ 3,085 → 550 ms (5.6 เท่า, −82%); เปิดแอปเดสก์ท็อปแบบ cold start 6,310 → 3,328 ms (1.9 เท่า, −47%)
> - **เริ่มบทสนทนา:** Chat บนเว็บ 416 → 273 ms (1.5 เท่า); Chat บนเดสก์ท็อป 460 → 224 ms (2.1 เท่า); Claude Code บนเดสก์ท็อป 837 → 347 ms (2.4 เท่า)
> - **โหลดบทสนทนา:** Chat บนเว็บ 1,557 → 646 ms (2.4 เท่า); Chat บนเดสก์ท็อป 1,353 → 488 ms (2.8 เท่า); Claude Cowork เดสก์ท็อป/คลาวด์ 2,566 → 728 ms (3.5 เท่า); Claude Code บนเดสก์ท็อป 545 → 262 ms (2.1 เท่า)
> - **ส่งข้อความ:** Chat บนเว็บ 180 → 59 ms (3.1 เท่า); Chat บนเดสก์ท็อป 140 → 64 ms (2.2 เท่า); Claude Cowork เดสก์ท็อป/คลาวด์ 928 → 48 ms (19 เท่า, −95%); Claude Code บนเดสก์ท็อป 250 → 52 ms (4.8 เท่า)
>
> จากการวัด 13 รายการในสี่เส้นทาง เร็วขึ้นเฉลี่ย 3.1 เท่า (ค่าเฉลี่ยเรขาคณิต)

งานนี้ใช้ [Claude Tag](https://claude.com/product/tag) (เบต้า) ซึ่งทำงานด้วยโมเดลวิจัยภายในที่มีความสามารถใกล้เคียงกับ Opus 5.5 Claude เป็นผู้หาคอขวด สร้างเบนช์มาร์ก ส่งการปรับปรุง และเฝ้าดูทุกการ deploy ส่วนมนุษย์ทำหน้าที่กุมพวงมาลัย คือกำหนดเป้าหมาย ชั่งน้ำหนักข้อแลกเปลี่ยน และอนุมัติทุกการเปลี่ยนแปลง ด้วยวิธีนี้ ทีมจึง merge การเปลี่ยนแปลงไปได้มากกว่าสามพันรายการ โดยไม่มีเหตุขัดข้องที่กระทบลูกค้าหรือการ rollback เลยสักครั้ง

## โจทย์ตั้งต้น

ก่อนเริ่มสปรินต์ ทีมสร้างช่อง Slack พร้อม[คำสั่งประจำ (standing instructions)](https://claude.com/docs/claude-tag/users/getting-started#give-claude-standing-instructions) ดังนี้

> **@Claude** หน้าที่ของคุณคือดูแลทุกเรื่องที่เกี่ยวกับประสิทธิภาพของเว็บไซต์ claude.ai และแอปเดสก์ท็อป ความรับผิดชอบของคุณได้แก่ เฝ้าดูว่าการ deploy แต่ละครั้งทำให้ประสิทธิภาพถดถอยหรือไม่ ประเมินว่า telemetry ที่มีอยู่แม่นยำและครอบคลุมเพียงใด ดูแลแดชบอร์ด observability ให้เป็นระเบียบ ลงมือแก้ปัญหาที่พบและงานง่าย ๆ ที่ได้ผลเร็วเชิงรุก เสนอโปรเจกต์ด้านประสิทธิภาพที่น่าลงทุน และสื่อสารกับเพื่อนร่วมทีมที่เป็นมนุษย์ […]
>
> เป้าหมายสูงสุดของช่องนี้คือให้คุณทำงานได้อย่างอิสระมากที่สุดเท่าที่จะทำได้ แต่วันนี้เรารู้ดีว่ายังไปไม่ถึงจุดนั้น

Claude วิเคราะห์ข้อมูลการใช้งานผ่าน Datadog MCP server และระบุเส้นทางผู้ใช้สี่แบบที่ส่งผลมากที่สุด ได้แก่ เปิดแอป เริ่มบทสนทนา โหลดบทสนทนาเดิม และส่งข้อความ เมื่อนับรวมทั้งเว็บและเดสก์ท็อป และครอบคลุมหลายผลิตภัณฑ์ ก็ได้การวัดที่แยกจากกัน 13 รายการ เพื่อสร้าง baseline ทีมเพิ่มการเก็บข้อมูล (instrumentation) จนการวัดทั้งหมดเปรียบเทียบกันได้โดยตรง ทุกการวัดเริ่มจากการกระทำของผู้ใช้ จบเมื่อผลลัพธ์ถูกเรนเดอร์ และแยกงานฝั่งไคลเอนต์ออกจากฝั่งเซิร์ฟเวอร์

สปรินต์เริ่มต้นด้วยรายการโปรเจกต์ราวยี่สิบรายการที่คัดมาเอง แต่ละโปรเจกต์มุ่งไปที่เส้นทางใดเส้นทางหนึ่ง Claude ประเมินผลของแต่ละโปรเจกต์เป็นมิลลิวินาที แล้วทีมรวมตัวเลขเหล่านั้นมาตั้งเป็นเป้าหมายของสปรินต์ บางโปรเจกต์ค่อนข้างใหญ่ แต่ทีมคิดว่าน่าจะทำส่วนใหญ่เสร็จภายในสองสัปดาห์

**ปรากฏว่าถึงวันที่สาม ทีมก็ทำได้ตามเป้าแล้ว 12 จาก 13 ข้อ**

โปรเจกต์ที่วางแผนไว้เสร็จเร็วกว่ากำหนด

- **เปิดแอปเร็วขึ้น:** ฝังช่องพิมพ์ข้อความ (composer) แบบ static ไว้ใน HTML เลย ผู้ใช้จึงพิมพ์ได้ระหว่างที่ React กำลังเริ่มต้นทำงาน และคอมไพล์ V8 code cache ไว้ล่วงหน้า เพื่อไม่ให้ main process ของเชลล์เดสก์ท็อปต้องคอมไพล์ใหม่ตั้งแต่ต้น
- **สลับหน้าเร็วขึ้น:** ให้ composer ยัง mount อยู่ระหว่างสลับบทสนทนา prefetch เซสชันตั้งแต่ตอนที่ผู้ใช้เอาเมาส์ไปชี้ และลดการ re-render ของแถบด้านข้างลง 90%

ทีมยังเว้นที่ไว้ให้ Claude หาโอกาสและเสนองานใหม่ ๆ ด้วย งานเหล่านั้นเติบโตกลายเป็นโปรเจกต์เต็มตัวอย่างรวดเร็ว และทำได้เกินเป้าเดิมไปไกล ทีมจึงตั้งเป้าใหม่ แล้วออกตามหาสิ่งที่จะวัดเพิ่ม

> **@Claude** เราลงทุนไปแทบทุกโปรเจกต์ในรายการเดิมแล้ว แถมทำเกินไปอีก มาทบทวนกันใหม่ […] อะไรที่เรายังไม่ได้สำรวจ อะไรที่เรา hill climb ได้ ตอนนี้โอกาสใหญ่ที่สุดอยู่ตรงไหน? […] ไอเดียแปลก ๆ ก็ยินดีรับ

## ทุกอย่าง hill climb ได้

ตั้งแต่แรก ทีมอยากวนรอบการพัฒนาให้เร็วกว่ารอบการ deploy Claude ทำงานแบบ asynchronous ได้นานหลายชั่วโมง หรือแม้แต่ข้ามคืน ทีมจึงอยากให้มันตรวจสอบต้นแบบได้เองโดยไม่ต้องรอข้อมูลจากผู้ใช้จริง ซึ่งหมายความว่าต้องหาวิธีวัดประสิทธิภาพแบบอื่นในแล็บ

Sam เป็นคนเจอเบาะแสแรก

> **จำลองจากบทสนทนาจริง — #claude-apps-perf**
>
> **Sam — 12:34 PM:** ถ้าไม่ใช้เวลาจริง (wall-clock) เราจะวัดอะไรแทนได้บ้าง? วัดจำนวนคำสั่ง JS ได้ไหม?
>
> **ClaudeApp — 12:42 PM:** สำหรับเส้นทางในเบราว์เซอร์ Chromium นับจำนวนคำสั่งไม่ได้ แต่มีตัวนับแบบ deterministic อื่น ๆ ไล่เป็นขั้น ๆ ได้ เช่น จำนวน React commit ต่อการโต้ตอบ จำนวนการเรียกฟังก์ชันจาก precise coverage ของ V8 จำนวนครั้งที่คำนวณเลย์เอาต์และสไตล์ใหม่ และจำนวน DOM mutation อยากเริ่มจากอันไหนก่อนครับ?
>
> **Sam — 12:49 PM:** ลอง valgrind + `Ir` + `--predictable` ในเธรดหนึ่ง แล้วแยกเบนช์ของเบราว์เซอร์/React แต่ละตัวไปเปิดเธรดใหม่ แท็กผมทุกเธรด รู้อยู่แล้วว่าเราต้องการอะไร ลุยเลย

สิบเอ็ดนาทีต่อมา มีห้าเธรดกำลังทำงาน แต่ละเธรดโฟกัสการวัดคนละแบบ ได้แก่ จำนวนคำสั่ง จำนวนการเรียกใน V8 React commit การคำนวณสไตล์ใหม่ และ DOM mutation

ทีมมองเบนช์มาร์กใหม่ทุกตัวด้วยความสงสัยอยู่บ้าง เบนช์มาร์กแต่ละตัวมีสองหน้าที่ หนึ่ง เป็นตัวชี้วัดที่ Claude ขยับได้ในแล็บ สอง เป็นราวกันตกใน CI ที่ตัวเลขขยับลงได้ทางเดียว (ratchet) ถ้าเบนช์มาร์กไหนผลไม่นิ่ง หรือไม่ได้สัมพันธ์กับความหน่วงที่ผู้ใช้รู้สึกจริง ทีมก็ทิ้งไปเลย ดีกว่าปล่อยให้ Claude ปีนผิดเนิน

> **@Claude** ช่วยพิสูจน์ว่าการ hill climb กับแต่ละตัวนี้ทำให้เวลาจริงดีขึ้นอย่างวัดได้ ตัวไหนพิสูจน์ไม่ได้ เราจะถอดเบนช์ตัวนั้นออก

เวลาจริงคือสิ่งที่ผู้ใช้รู้สึก แต่มันมีสัญญาณรบกวนมาก และตัวเลขระดับมิลลิวินาทีก็แกว่งเกินกว่าจะใช้เป็นด่านใน CI จำนวนคำสั่งน่าสนใจเพราะเป็นค่า deterministic แต่ Claude ก็ยังต้องพิสูจน์ว่ามันไปทางเดียวกับเวลาจริง

ทีมจึงให้ Claude ลดจำนวนคำสั่งบน hot path สองจุด คือ รูทีนที่ประกอบโครงสร้างต้นไม้ข้อความของบทสนทนา และตัวสแกนหาบรรทัดสถานะในเอาต์พุตของ Claude Code Claude ใช้ Valgrind โปรไฟล์ทั้งสองจุด แล้วพบว่าหนึ่งในสี่ของคำสั่งในเส้นทางแรกคือการค้นดิกชันนารีแบบ megamorphic ที่ resolve ID ข้อความเดิมซ้ำถึงสามครั้ง

หนึ่งชั่วโมงต่อมา มันลดจำนวนคำสั่งของสองเส้นทางลงได้ 48% และ 31% ส่วนเวลาจริงลดลง 78% และ 44% ทีมเพิ่ม ratchet ใหม่สองตัว นับจากนั้น PR ใดที่ทำให้จำนวนคำสั่งของสองเส้นทางนี้เพิ่มขึ้นจะไม่ผ่าน CI และมีงานรายวันคอยลดเพดานลงทุกครั้งที่จำนวนคำสั่งลดลง

> **สรุปกราฟ: hot path สองจุด ก่อนและหลัง**
>
> - **การประกอบต้นไม้ข้อความ:** resolve ID ข้อความแต่ละตัวครั้งเดียวแทนสามครั้ง คำสั่ง CPU −48% เวลาจริง −78% เร็วขึ้น 4.6 เท่า
> - **ตัวสแกนบรรทัดสถานะ:** เช็กตัวอักษรตัวแรกแบบเบา ๆ ก่อนรัน regex คำสั่ง CPU −31% เวลาจริง −44% เร็วขึ้น 1.8 เท่า
>
> นับจำนวนคำสั่งภายใต้ Valgrind ด้วย `node --predictable` ส่วนเวลาวัดจากเบนช์มาร์กเดียวกันบน node ปกติที่ JIT อุ่นเครื่องแล้ว

นี่นำไปสู่บทเรียนหัวใจของสปรินต์นี้: **เมื่อมี Claude อะไรที่วัดได้ก็จัดการได้**

แต่ก่อน การวัดคือขั้นที่ศูนย์ คือเพิ่มตัวชี้วัด รอข้อมูลไหลเข้ามา แล้วจึงเริ่มเข้าใจปัญหา แต่เมื่อมี Claude การวัดคือก้าวแรกของการไต่ขึ้น ทันทีที่ Claude มีตัวเลขให้เอาชนะ มันก็เริ่มปรับปรุงได้ทันที สิ่งที่ได้ผลคุ้มค่าที่สุดที่ทีมทำได้ จึงเป็นการหาสิ่งที่จะวัดให้มากขึ้น

## วงจรการทำงาน ทีละเธรด

งานทั้งหมดเกิดขึ้นในช่อง Slack เดียวกัน วิศวกรหลายคนกับ Claude ช่วยกันแจมอยู่ในทุกเธรด ไม่นานสปรินต์ก็ลงตัวเป็น[วงจร (loop)](https://claude.com/blog/getting-started-with-loops) แบบนี้

1. มีคนเปิดเธรดเกี่ยวกับช่วงที่ช้าในเส้นทางใดเส้นทางหนึ่ง มักแนบภาพหน้าจอหรือคลิปบันทึกหน้าจอมาด้วย
2. Claude ไล่ตามโฟลว์ แล้วหาหรือสร้างเบนช์มาร์กที่แสดงปัญหาให้เห็น
3. เมื่อได้ผลลัพธ์ที่น่าสนใจในแล็บ Claude ก็กลับมาพร้อม PR ซึ่งมักแบ่งเป็นหลายตัวตามระดับความเสี่ยงและความง่ายในการรีวิว และทุกอย่างที่ผู้ใช้มองเห็นได้จะซ่อนอยู่หลัง feature flag
4. หลังปล่อยจริง Claude เฝ้าดูการ deploy และอ่านข้อมูลจากผู้ใช้จริงแยกตาม build และแพลตฟอร์ม
5. ถ้าเร็วขึ้น Claude จะล็อกผลงานไว้ด้วยการขันเบนช์มาร์กให้แน่นขึ้น ถ้าไม่ มันจะปิด flag แล้ววนทำใหม่
6. จากนั้นก็ออกไปหาจุดที่ช้าถัดไปในเส้นทางเดิม

ตัวอย่างหนึ่ง: มีคนแชร์คลิปหน้าจอที่แถวในแถบด้านข้างโผล่ขึ้นมาทีละแถวหลังหน้าโหลดเสร็จ แถวของ Chat กับ Cowork มาไม่พร้อมกัน ทำให้หน้าดูกระตุก ไม่มีระบบมอนิเตอร์ใดที่มีอยู่จับได้เลย ตัวที่ใกล้ที่สุดคือ [Cumulative Layout Shift](https://web.dev/articles/cls) (CLS) แต่การขยับแต่ละครั้งได้คะแนนแค่ราว 0.008 ต่ำกว่าเกณฑ์ "ดี" ที่ 0.1 อยู่มาก

Issac มีไอเดียให้อ้างอิง [Layout Instability API](https://wicg.github.io/layout-instability/) ที่อยู่เบื้องหลังโดยตรง Claude สร้างอีเวนต์ telemetry ที่จับคู่ `sources` ของแต่ละรายการ `layout-shift` เข้ากับพื้นที่ที่ตั้งชื่อไว้ (เช่น แถบด้านข้าง ส่วนบทสนทนา) และช่วงเวลา (เช่น ก่อน first paint หลังพร้อมให้พิมพ์) มันเพิ่ม integration test ที่เปิดหน้าซึ่งแถบด้านข้างมีข้อมูล หน่วงข้อมูลของแถบด้านข้างไว้จนหลัง first paint และจะล้มเหลวทันทีถ้ามีการขยับในพื้นที่ใดก็ตามที่ตั้งชื่อไว้ เทสต์นี้กลายเป็นเบนช์มาร์กที่พิสูจน์การแก้ไข บน main ขึ้นแดง 20 จาก 20 รอบ บน PR ขึ้นเขียว 20 จาก 20 รอบ

หลัง deploy อีเวนต์นี้ Claude อ่านข้อมูลจริงแล้วพบว่า **31% ของการโหลดหน้าเว็บ มีบางอย่างขยับหลังหน้าพร้อมใช้งานแล้ว** ทั้งที่ผู้ใช้ไม่ได้ทำอะไรเลย จากนั้น Claude ไล่แก้สาเหตุทีละตัว: แถวหัวตารางที่มาช้า เคอร์เซอร์ที่เลื่อนไปด้านข้างเมื่อชื่อผู้ใช้โหลดเสร็จ รายการที่ขยับเมื่อแถบเลื่อนโผล่ขึ้นมา มันแก้ตัวการหลัก ๆ ไปเป็นชุด และเมื่อชุดนั้นหมดไป ก็หาชุดถัดไปต่อ

> **สรุปวิดีโอ: แถบด้านข้างกระตุก ก่อนและหลัง (จำลองเน็ต 4G ช้า)** ก่อนแก้ แถวมาช้าและสลับตำแหน่งกันวุ่นวาย สิบแถวกระโดด เก้าแถวโผล่ขึ้นมา และสี่แถวหายไป หลังแก้ แถวเติมเข้ามาในตำแหน่งสุดท้ายเลย และไม่มีอะไรขยับ

นั่นเป็นแค่เธรดเดียว ระหว่างสปรินต์ มีเธรดทำงานพร้อมกันมากกว่าหนึ่งร้อยห้าสิบเธรด

## ขยายออกทางแนวนอน

เมื่อวงจรนี้ใช้ได้ผลในเธรดเดียว การขยายไปหลายเธรดก็แค่เปิดเธรดเพิ่ม แทนที่จะปิดเธรดเมื่อทำตามคำขอเดิมเสร็จ Claude *ทำต่อไปเรื่อย ๆ* เธรดเดียวอาจส่ง PR ปรับประสิทธิภาพออกมาห้าสิบ บางทีก็เป็นร้อยตัว และบ่อยขึ้นเรื่อย ๆ ที่ผู้เปิดเธรดใหม่คือ Claude ไม่ใช่มนุษย์ เพื่อไล่ตามโอกาสที่มันค้นพบเองระหว่างการสืบสวนเรื่องอื่นหรืองานที่รันตอนกลางคืน Shelley หนึ่งในวิศวกรในช่องให้ความเห็นว่า "[โมเดลนี้] คือปีศาจแห่งตัวเลข"

การวัดทุกครั้งเจอสิ่งที่ปรับปรุงได้

- การสำรวจ React hook ทั้งหมดพบว่าเส้นทางการพิมพ์ใน composer มี **hook 6,900 ตัวและการ subscribe store 900 จุด** ที่ re-render ทุกครั้งที่กดแป้น
- การนับการคำนวณสไตล์ใหม่พบว่า selector `:root:has()` เพียงตัวเดียว **เพิ่มเวลา 24 มิลลิวินาทีให้ทุกการเปลี่ยนแปลงของ DOM**
- การไล่โค้ดหลัง first paint พบ `location.reload()` ที่หลงเหลืออยู่ ซึ่งทำให้เกิด **การรีโหลดแบบมองไม่เห็นวันละครึ่งล้านครั้ง** ที่ไม่มีตัวชี้วัดการโหลดใดมองเห็น
- การอ่านตัวอย่างจาก profiler ของแท็บที่ไม่ได้ใช้งาน พบว่า snapshot แคชที่เหมือนกันทุกประการถูกคัดลอกลง IndexedDB นาทีละสองครั้ง และทั้งหมดทำบน main thread

ทีมแทบไม่รู้เลยว่าแต่ละเธรดจะพาไปเจออะไร ระหว่างกวาดหาอาการ CPU สะดุด Claude สังเกตว่าการไฮไลต์บล็อกโค้ดที่เสร็จแล้วอาจทำให้หน้าค้างไปราวหนึ่งวินาที มันขุดลึกในแล็บแล้วเจอตัวการ: เครื่องหมาย em dash ถ้า markdown ของคำตอบมีอักขระนอกชุด Latin-1 แม้แต่ตัวเดียว เช่น em dash หรือเครื่องหมายคำพูดแบบโค้ง V8 จะเก็บทั้งสตริงเป็น UTF-16 ซึ่งทำให้ regex สำหรับไฮไลต์ไวยากรณ์ทุกตัวต้องวิ่งบนเส้นทางแบบสองไบต์ที่ช้ากว่า Claude แก้ด้วยการเปลี่ยนโค้ดยี่สิบบรรทัด ให้คัดลอกบล็อกโค้ดแต่ละบล็อกเป็นสตริงแบบหนึ่งไบต์ก่อนไฮไลต์

> **สรุปกราฟ: การไฮไลต์บล็อกโค้ดที่เสร็จแล้วในคำตอบที่มี em dash (วัดในแล็บ)** บล็อก TypeScript แรกในหน้าใช้เวลา main thread ลดจาก 1.0 วินาทีเหลือ 0.35 วินาที (ลดลง 65%) และการประมวลผลบล็อกนั้นในรอบถัด ๆ ไปลดจาก 100 ms เหลือ 40 ms เงื่อนไข: คอนเทนเนอร์ 4 vCPU, headless Chrome, ไม่จำกัดความเร็ว CPU, รัน 2–3 รอบต่อค่า, สิงหาคม 2026

พอถึงสัปดาห์ที่สอง ผลงานมีมากจนแทบสรุปลงอัปเดตรายวันไม่ไหว วันที่ยุ่งที่สุดมีการเปลี่ยนแปลงถูก merge มากกว่าสองร้อยรายการ Claude เสนอเบนช์มาร์กใหม่อยู่เรื่อย ๆ ราวหนึ่งในสามของ PR มี telemetry หรือราวกันตกเพิ่มเติม และเครื่องมือวัดใหม่แต่ละตัวก็สร้างเธรดใหม่พร้อมโอกาสใหม่ ๆ ตามมา

การทำงานในช่องเดียวหมายความว่าทุกอย่างเกิดขึ้นอย่างเปิดเผย ทุกคนเข้า ๆ ออก ๆ เธรดของกันและกันเพื่อถกเถียงการตัดสินใจและฉลองความสำเร็จ ข่าวแพร่ออกไป ทีมอื่น ๆ เริ่มนำการเปลี่ยนแปลงของตัวเองมาให้รีวิวด้านประสิทธิภาพในช่องนี้ โปรเจกต์ใหม่ ๆ ก็ถูกเขียนขึ้นในแบบที่ใส่ใจประสิทธิภาพมากขึ้นอย่างแนบเนียน ด้วยราวกันตกและ Claude skills ทั้งหลายที่ถูกนำมาใช้

## ราวกันตก

ทีมเตรียมรับมือกับความเร็วระดับนี้ไว้แล้ว เพราะเกือบทุกจุดที่แตะคือ hot path ทั้ง first paint, composer และส่วนบทสนทนา กลไกความปลอดภัยจึงถูกวางไว้ตั้งแต่ต้น

- ทุก PR ต้องผ่าน[การรีวิวโค้ดอัตโนมัติ](https://claude.com/blog/code-review) และได้รับอนุมัติจากมนุษย์อย่างน้อยหนึ่งคน
- เขียน unit test ก่อนปรับประสิทธิภาพเสมอ
- อะไรก็ตามที่อาจก่อปัญหาที่ผู้ใช้มองเห็นได้ ต้องปล่อยหลัง feature flag อายุสั้น

เมื่อ flag เริ่มกองพะเนิน ทีมเปิดเธรดเฉพาะเพื่อประสานการทยอยเปิดใช้และการเก็บกวาด Claude จัดประเภททุก flag ว่าเป็น kill switch หรือ ramp แล้วปลดแต่ละตัวออกทันทีที่ปลอดภัย ตลอดสองสัปดาห์ มีการเพิ่ม **flag เกือบสองร้อยตัว** และกว่าครึ่งถูกเก็บกวาดไปแล้วเมื่อจบสปรินต์

ทีมยังรู้ดีว่าผลงานด้านประสิทธิภาพจะค่อย ๆ เสื่อมลงในโค้ดเบสที่เปลี่ยนแปลงเร็ว และ[ที่ Anthropic โค้ดถูกส่งออกไปอย่างรวดเร็ว](https://claude.com/blog/agentic-coding-is-straining-ci-heres-how-we-scaled-test-impact-analysis-at-anthropic) เมื่อโปรเจกต์ใดพิสูจน์ได้ว่าได้ผล ทีมจึงลงทุนปกป้องมันไว้ ตัวอย่างเช่น static composer ที่เปราะบางโดยการออกแบบ ผู้ใช้จะเห็นสำเนา HTML ของหน้าแทบจะทันที แล้ว React ก็วาดทับลงไปตรง ๆ

> **สรุปวิดีโอ: static composer ก่อนและหลัง (จำลองเน็ต 4G ช้า)** ก่อนแก้ การโหลด claude.ai ใหม่ทำให้หน้าว่างเปล่าอยู่นาน และ composer รับข้อความได้ที่ 2.93 วินาที หลังแก้ ข้อความทักทายและ composer แบบ static รับข้อความได้ตั้งแต่ 0.36 วินาที ผู้ใช้พิมพ์ข้อความลงไป และข้อความยังอยู่ครบเมื่อ composer ตัวจริงค่อย ๆ ปรากฏขึ้นที่ราว 3 วินาที

ถ้าการเรนเดอร์ของ React คลาดไปแม้แต่หนึ่งพิกเซล ความมหัศจรรย์นี้ก็พัง Claude จึงสร้างราวกันตกหลายสิบชั้น

- markup แบบ static สร้างจากการเรนเดอร์คอมโพเนนต์ React ตัวจริงใน jsdom และมีเทสต์รับประกันว่าทั้งสองจะไม่มีวันเพี้ยนจากกัน
- ชุด integration test เปรียบเทียบหน้า static กับผลเรนเดอร์ของ React ในขนาด viewport สิบสี่แบบ และยืนยันว่าตรงกันภายใน 1 px
- เทสต์การกดแป้นพิมพ์ต่อเนื่องตลอดช่วงส่งต่อ และจะล้มเหลวถ้ามีแป้นใดหายหรือลำดับสลับ
- ในการใช้งานจริง การส่งต่อทุกครั้งจะรายงานการขยับละเอียดถึงหนึ่งในสิบพิกเซล และ Claude จะเปิดเธรดให้ทุกอีเวนต์ที่มีการขยับไม่เป็นศูนย์

ไม่ใช่ทุกอย่างที่จับได้ในแล็บ ทีมจึงใช้ราวกันตกที่เก่าแก่ที่สุดด้วย นั่นคือการทยอยปล่อย การเปลี่ยนแปลงที่เสี่ยงสูงจะปล่อยให้พนักงานก่อน จากนั้นผู้ใช้ 1% แล้วจึงทุกคน สี่ชั่วโมงหลังปล่อย static composer ภายในองค์กร เพื่อนร่วมทีมคนหนึ่งแชร์คลิปหน้าจอที่มีเลย์เอาต์ขยับ ซึ่งไม่มีตัวชี้วัดใดมองเห็น เมื่อเขาเปิด claude.ai ในแท็บใหม่ composer จะตกลงไป แต่ต้นเหตุไม่ใช่โค้ดของทีม

## ก้าวต่อไป

วันนี้ claude.ai และแอปเดสก์ท็อปเร็วกว่าต้นเดือนสิงหาคมราว 3 เท่า และ ratchet ต่าง ๆ น่าจะรักษาระดับนี้ไว้ได้ แต่งานยังไม่จบ เปอร์เซ็นไทล์ที่ 95 เส้นทางการใช้งานอื่น ๆ และบทสนทนาที่ยาวมาก ๆ ยังมีช่องให้ปรับปรุง ทีมจะเขียนอีกบทความหนึ่งเกี่ยวกับภารกิจเสริมบางส่วนที่พาทีมขึ้นไปถึงต้นน้ำระหว่างสปรินต์ ซึ่งมีผลงานเข้าไปอยู่ใน Electron, Chromium, Node.js และอื่น ๆ แล้ว
