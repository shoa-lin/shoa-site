กว่าหนึ่งปีที่ผ่านมา ผลิตภัณฑ์ agent เปลี่ยนหน้าตาเร็วมาก เริ่มจากผู้ช่วยเขียนโค้ดในเทอร์มินัลและ IDE ตามด้วยแอปเดสก์ท็อปและบอตในโปรแกรมแชต ถัดมาบางเจ้าให้ agent มีคอมพิวเตอร์บนคลาวด์ของตัวเองหนึ่งเครื่อง บางเจ้าดึงมันเข้าไปอยู่ในช่องทางของทีม และบางเจ้าถึงกับให้มันมีอีเมลและเบอร์โทรศัพท์เป็นของตัวเอง

มองผ่าน ๆ เหมือนทุกเจ้ากำลังวุ่นอยู่กับการทำเปลือกใหม่ ผมเองใช้คำถามสองข้อมาจัดระเบียบความเปลี่ยนแปลงเหล่านี้:

- **สิทธิ์**: agent ได้รับอนุญาตให้ลงมือกับอะไร
- **บริบท**: agent รู้อะไร และเก็บอะไรไว้ได้

agent ทำงานให้สำเร็จได้ก็ต่อเมื่อสองสิ่งนี้ซ้อนทับกันเท่านั้น รู้สถานการณ์แต่ลงมือไม่ได้ มันก็เป็นได้แค่ที่ปรึกษา ลงมือได้แต่ไม่รู้สถานการณ์ มันก็คือคนแปลกหน้าที่ถือกุญแจของคุณอยู่ มุมมองของผมจึงเป็นแบบนี้: **รูปแบบของ agent ก็คือจุดที่สิทธิ์กับบริบทซ้อนทับกันนั่นเอง** ทุกครั้งที่ผลิตภัณฑ์เปลี่ยนรูปแบบ คือการดันพื้นที่ซ้อนทับนี้ออกไปอีกหนึ่งวง: แกนหนึ่งพุ่งออกไปก่อน อีกแกนค่อยตามไปให้ทัน

## ดูภาพกันก่อน

![แผนภาพสองมิติ สิทธิ์ × บริบท: แกนนอนคือขอบเขตสิทธิ์ แกนตั้งคือขอบเขตบริบท ผลิตภัณฑ์เจ็ดกลุ่มวางอยู่บนภาพ](/assets/blog/agent-permission-context/map-th.svg)

*คำอธิบายภาพ: แกนนอนยิ่งไปทางขวา agent ยิ่งลงมือกับสิ่งต่าง ๆ ได้มากขึ้น และเมื่อพลาดก็ยิ่งกู้คืนได้ยาก ตำแหน่งของแต่ละผลิตภัณฑ์เป็นการตัดสินของผมเอง ไม่ใช่คำกล่าวของผู้ผลิต*

ภาพนี้ดูแค่สองเรื่อง: ใครอยู่บนเส้นทแยงมุม คือสองแกนเดินหน้าไปพร้อมกัน ใครเบี่ยงออกจากเส้นทแยงมุม คือมีแกนหนึ่งวิ่งออกไปก่อน ส่วนถัดจากนี้จะไล่ต่อทีละส่วน และแต่ละส่วนล้วนต่อยอดมาจากส่วนก่อนหน้า

## ทำไมงานเขียนโค้ดถึงออกตัวได้ก่อนใคร

ในกล่องแชต agent รู้ว่าคุณพูดอะไร แต่สิ่งที่มันทำได้มีแค่ตอบ ส่วนงานคุณก็ยังต้องลงมือทำเอง

repository ต่างออกไป มันบรรจุสองแกนไว้ในไดเรกทอรีเดียวกัน โค้ด ประวัติ commit และเทสต์ คือบริบทที่ agent ต้องการ การแก้ไฟล์และรันคำสั่ง คือสิทธิ์ของมัน ที่สำคัญกว่านั้นคือสิทธิ์เหล่านี้เรียกคืนได้: แก้พังก็ใช้ git ย้อนกลับ แก้ถูกหรือไม่ก็ให้เทสต์เป็นคนตรวจรับ เมื่อการกระทำยกเลิกได้ จะให้สิทธิ์กว้างขึ้นสักหน่อยก็ไม่น่ากลัว

เดือนพฤษภาคม 2025 OpenAI เปิดตัว Codex ที่ทำงานวิศวกรรมหลายงานขนานกันในสภาพแวดล้อมแยกส่วน ไม่กี่วันถัดมา Claude Code ก็เปิดให้ใช้งานอย่างเป็นทางการ โดยการแก้ไขปรากฏบนไฟล์ใน VS Code หรือ JetBrains ของคุณโดยตรง ทั้งสองเจ้าเริ่มจาก repository เหมือนกันโดยไม่ได้นัดหมาย

![ภาพเปรียบเทียบ: ในกล่องแชต บริบทกับสิทธิ์แทบไม่ซ้อนทับกัน ใน repository ทั้งสองซ้อนทับกันเป็นบริเวณกว้าง](/assets/blog/agent-permission-context/repo-th.svg)

*คำอธิบายภาพ: repository คือที่แรกที่ "สถานการณ์อยู่ครบ ทำพลาดก็ย้อนได้"*

ดังนั้น ถ้าอยากรู้ว่างานด้านไหนจะมอบให้ agent ได้เมื่อไร ให้ดูก่อนว่าที่นั่นมีพื้นที่แบบนี้หรือยัง: บริบทครบถ้วน และการกระทำยังยกเลิกได้

## ออกจาก repository แล้ว ทางแยกเป็นสองสาย

พอออกจาก repository เรื่องก็ยากขึ้นทันที บริบทของคุณกระจายอยู่ในประวัติแชต ไฟล์ และบัญชีต่าง ๆ ส่วนที่ลงมือได้ก็กระจายอยู่ตามเว็บไซต์และแอปจำนวนมากที่ไม่มี API เมื่อหาที่สำเร็จรูปที่บรรจุทั้งสองอย่างพร้อมกันไม่ได้ เส้นทางจึงแยกออกจากกัน

ทางหนึ่งสร้างบริบทให้หนาก่อน: วาง agent ลงในโปรแกรมแชตที่คุณใช้อยู่แล้ว ให้หน่วยความจำและเซสชันอยู่ฝั่งคุณเอง OpenClaw ใช้ gateway ตัวเดียวต่อเข้ากับช่องทางอย่าง WhatsApp, Telegram และ Slack โดย workspace ไฟล์หน่วยความจำ เซสชัน และคีย์ลับทั้งหมดอยู่ในมือผู้ใช้ ส่วน Hermes ให้ command line แอปเดสก์ท็อป และ gateway รับส่งข้อความใช้เซสชันและการตั้งค่าชุดเดียวกัน

อีกทางหนึ่งขยายสิทธิ์ให้กว้างก่อน: ให้คอมพิวเตอร์แก่ agent ไปเลยหนึ่งเครื่อง อินเทอร์เฟซกราฟิกบวกกับเบราว์เซอร์ที่ล็อกอินไว้แล้ว คือวิธีที่ใช้ได้ทั่วไปที่สุดเมื่อเจอ "ของที่ไม่มี API" Grok Bot ทำงานบนคอมพิวเตอร์คลาวด์ถาวรหนึ่งเครื่อง มีเบราว์เซอร์ ระบบไฟล์ และเทอร์มินัล และล็อกอินเข้าเครื่องมือและเว็บไซต์ที่คุณใช้อยู่แล้วได้ ส่วน Muse ให้แต่ละคนมีเครื่องเสมือนที่ปลอดภัยพร้อมเบราว์เซอร์หนึ่งเครื่อง คุณปิดแอปไปแล้ว มันก็ยังทำงานต่อ

![ภาพทางแยก: หลังออกจาก repository ทางหนึ่งสร้างบริบทให้หนาก่อน อีกทางขยายสิทธิ์ให้กว้างก่อน สุดท้ายทั้งคู่ต้องเติมอีกแกนที่ขาด](/assets/blog/agent-permission-context/fork-th.svg)

*คำอธิบายภาพ: แกนไหนวิ่งออกไปก่อน อีกแกนก็คือหนี้ที่ต้องตามใช้คืนเป็นลำดับถัดไป*

## การอนุมัติ คือคนกำลังเติมบริบทให้

ถ้าเลือกเดินสายสิทธิ์ก่อน จะชนปัญหาหนึ่งทันที คอมพิวเตอร์ที่ล็อกอินบัญชีของคุณไว้กดปุ่มได้ทุกปุ่ม แต่มันไม่รู้ว่าการกระทำไหนที่คุณจะยอมรับ: งบของคุณเท่าไร คุณกับผู้รับเป็นอะไรกัน เส้นที่คุณไม่ยอมข้ามอยู่ตรงไหน

ตอนนั้นเอง หน้าต่างขออนุมัติทุกอันที่เด้งขึ้นมา แท้จริงคือ agent กำลังขอบริบทส่วนที่มันขาดจากคุณ การเขียนกฎไว้ล่วงหน้าก็คือการส่งมอบบริบทส่วนนี้ให้มันในครั้งเดียว วิธีของ Dots คือให้คุณแบ่งการกระทำเป็นสามระดับ: อนุญาต ต้องอนุมัติ ห้าม ส่วน Muse จะถามคุณก่อนส่งอีเมลหรือซื้อของ และยังเก็บบันทึกไว้ด้วย

![ภาพแสดง: สิทธิ์ยาวเกินบริบทออกไปช่วงหนึ่ง ช่องว่างนั้นเติมด้วยหน้าต่างขออนุมัติ การเขียนกฎไว้ล่วงหน้า และการสะสมหน่วยความจำกับความชอบ](/assets/blog/agent-permission-context/approval-th.svg)

*คำอธิบายภาพ: ยิ่งต้องขออนุมัติบ่อย ยิ่งแปลว่าสองแกนห่างกันมาก*

ดังนั้น "ทำงานหนึ่งอย่างต้องให้คุณอนุมัติกี่ครั้ง" ใช้เป็นตัวเลขชี้วัดได้ตัวหนึ่ง สิ่งที่มันวัดคือสิทธิ์กับบริบทห่างกันแค่ไหน ถ้าอยากให้ค่านี้ลดลง สิ่งที่ควรทำคือเติมบริบท: กฎ หน่วยความจำ ความชอบ ไม่ใช่รื้อประตูกั้นทิ้ง

มีบริบทอยู่ส่วนหนึ่งที่จงใจไม่ให้ นั่นคือรหัสผ่าน Muse เก็บข้อมูลรับรองตัวตนไว้ในที่เก็บที่ปลอดภัย โมเดลมองไม่เห็นรหัสผ่านและวิธีชำระเงินของคุณ agent ใช้ได้ แต่มองไม่เห็น

## บริบทสะสมอยู่ที่ไหน ทางเข้าก็รวบไปที่นั่น

ย้อนกลับไปดูทางสายที่สร้างบริบทก่อน มันบอกอีกเรื่องหนึ่ง

ทางเข้าจะเป็นเทอร์มินัล โปรแกรมแชต เดสก์ท็อป หรือ WhatsApp ไม่ได้เปลี่ยนว่า agent แตะอะไรได้หรือรู้อะไรบ้าง ทางเข้าจึงเปิดเพิ่มก็ได้ ปิดลงก็ได้ตามสะดวก สิ่งที่ค่อย ๆ สะสมขึ้นมาจริง ๆ คือบริบท: หน่วยความจำ สกิล เซสชัน เธรด และเวลาคุณเปลี่ยนผลิตภัณฑ์ สิ่งที่หายไปก็คือของเหล่านี้นี่เอง

ผู้ผลิตจึงรวบทางเข้าไปไว้ที่ที่บริบทสะสมอยู่ ส่วนสภาพแวดล้อมที่ลงมือทำงานจริงถอยไปอยู่ข้างหลัง กลายเป็น backend ที่สลับได้ทุกเมื่อ ChatGPT เดสก์ท็อปรุ่นใหม่รวม Chat, Work และ Codex ไว้ในเปลือกเดียว Dots เข้าไปสั่งงานใน Codex หรือ Work โดยงานเหล่านั้นยังคิดปริมาณการใช้แบบเดิม ส่วน Bot Mode ของ Hermes เป็นเพียงปลั๊กอินเดสก์ท็อป ปิดมันไป profile และเซสชันก็ยังอยู่: อินเทอร์เฟซถอดออกได้ แต่สถานะคงอยู่ตลอด

คูเมืองที่แท้จริงของ agent จึงเป็นสถานะที่มันสะสมไว้ให้คุณ การส่งออก การลืม การรีเซ็ต การแยกส่วน เรื่องเหล่านี้ต้องทำให้เป็นแกนกลางของผลิตภัณฑ์

## งานของทีม: ช่องทางตัดสองแกนให้ลงที่เดียวกัน

ทันทีที่บริบทเป็นของคนหลายคน ปัญหาใหม่ก็ตามมา สถานการณ์ของทีมกระจายอยู่ในตัวสมาชิกแต่ละคน agent สำหรับใช้คนเดียวมองเห็นได้แค่บริบทของคนเดียว และใช้ได้แค่สิทธิ์ของคนเดียว

ช่องทางแก้ปัญหาทั้งสองด้านได้ในคราวเดียว Claude Tag คือ Claude สำหรับทีมใน Slack: ผู้ดูแลเปิดเครื่องมือ ข้อมูล และ codebase ให้มันเป็นรายช่องทาง ใครในช่องทางก็ @ มันเพื่อสั่งงานได้ หนึ่งช่องทางมี Claude หนึ่งตัว สิ่งที่มันทำทั้งช่องทางมองเห็นหมด และผู้ดูแลยังตั้งเพดานค่าใช้จ่ายและดูบันทึกการทำงานได้ ขอบเขตของสิทธิ์กับขอบเขตของบริบทจึงตกอยู่บนช่องทางเดียวกัน นี่คือเหตุผลที่มันขึ้นไปยืนอยู่มุมขวาบนของภาพได้

ลองเทียบกับ Bot Mode ของ Hermes: bot ที่มีชื่อหลายตัว ต่างมีบทบาท โมเดล หน่วยความจำ และสกิลของตัวเอง คุยเป็นกลุ่มและส่งข้อความหากันได้ แต่ทั้งหมดเป็นของผู้ใช้คนเดียวกัน นี่คือการแบ่งบริบทของคนคนเดียวออกเป็นหลายส่วน ยังไม่ได้แตะบริบทของคนอื่นเลย

ดังนั้นถ้าจะทำ agent สำหรับทีม ให้หาก่อนว่าบริบทของทีมสะสมอยู่ที่ไหนแล้ว (ช่องทาง โปรเจกต์ repository) แล้วผูกสิทธิ์ไว้ตรงนั้น อย่าผูกไว้กับคนใดคนหนึ่ง

## ตัวตน: ทำให้สิทธิ์ตัดได้ละเอียดเท่าบริบท

วงสุดท้าย ปัญหาอยู่ที่เรื่อง "agent ล็อกอินเป็นตัวคุณ" มันใช้ตัวตนของคุณไปทำงาน สิ่งที่ได้คือสิทธิ์ทั้งหมดของคุณ: ตัดให้เล็กลงไม่ได้ และเรียกคืนแยกต่างหากก็ไม่ได้ ถ้าจะเรียกคืนก็ต้องเรียกคืนพร้อมกับตัวคุณไปด้วย

พอ agent มีหลายตัว ปัญหานี้ก็ถูกขยายใหญ่ขึ้น Grok Bot เป็นตัวอย่างที่ดีมาก: Bot หลายตัวใช้คอมพิวเตอร์คลาวด์ร่วมกันหนึ่งเครื่อง แต่ละตัวมีหน้าจอของตัวเอง บทสนทนาและสิ่งที่เรียนรู้แยกตาม Bot แต่ไฟล์และสถานะล็อกอินของเบราว์เซอร์กลับใช้ร่วมกัน บริบทถูกตัดแยกตาม Bot แล้ว แต่สิทธิ์ยังเป็นของทั้งบัญชีชุดเดียว

![ภาพแสดง: Bot หลายตัวต่างมีบริบทของตัวเองแต่ใช้สิทธิ์ของทั้งบัญชีร่วมกัน เมื่อเปลี่ยนเป็นให้แต่ละ agent มีตัวตนของตัวเอง ทั้งบริบทและสิทธิ์ก็ถูกตัดแยกตาม agent](/assets/blog/agent-permission-context/identity-th.svg)

*คำอธิบายภาพ: Bot ทุกตัวถือสิทธิ์ทั้งหมดไว้ แต่รู้สถานการณ์แค่บางส่วน*

การให้ agent มีตัวตนเป็นของตัวเอง คือวิธีตรงที่สุดที่จะตัดสิทธิ์ให้ละเอียดเท่าบริบท Cue ให้ agent แต่ละตัวมีอีเมล เบอร์โทรศัพท์ กระเป๋าเงิน และคอมพิวเตอร์ของตัวเอง จ่ายเงินได้เฉพาะในงบที่คุณตั้งไว้ ส่วน dot ผู้เชี่ยวชาญของ Dots มีตัวตนของตัวเองและฮาร์ดแวร์ที่ฝ่าย IT จัดให้ เชื่อมกับระบบของบริษัทได้ แม้ตอนนี้จะยังเป็น preview อยู่ก็ตาม พอเป็นแบบนี้ สิทธิ์ก็กลายเป็นสิ่งที่ออกให้แยกต่างหาก ตั้งวงเงิน และเพิกถอนได้ ไม่ใช่สถานะล็อกอินก้อนหนึ่งที่ให้ agent ยืมไปใช้อีกต่อไป

บางคนอาจถามว่าตัวตนนับเป็นแกนที่สามไหม มุมมองของผมคือ แทนที่จะบอกว่ามันขยับไปทางขวาบนแกนนอนอีกหนึ่งช่อง น่าจะบอกว่ามันกำลังถามอีกคำถามหนึ่งมากกว่า: สิทธิ์ชุดนี้เป็นของใคร

## ส่งท้าย

การเปลี่ยนรูปแบบทุกครั้ง ถึงที่สุดแล้วก็เป็นเรื่องเดียวกัน: แกนหนึ่งพุ่งออกไปก่อน อีกแกนตามไปให้ทัน แล้วผลิตภัณฑ์ใหม่ก็งอกขึ้นตรงจุดที่ซ้อนทับกัน คราวหน้าเจอ agent ตัวใหม่ อย่าเพิ่งรีบดูว่าทางเข้าหน้าตาเป็นอย่างไร ถามมันแค่สองคำถามก็พอ: มันแตะอะไรได้ และมันรู้อะไรบ้าง
