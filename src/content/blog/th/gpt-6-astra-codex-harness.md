## สรุปก่อน

สิ่งที่ GPT-6 Astra นำมาไม่ใช่แค่โมเดลที่เก่งขึ้น แต่คือการที่โมเดลเชิงเวลา โมเดลการควบคุม และขอบเขต runtime ของ Agent ล้วนกำลังเปลี่ยนไปพร้อมกัน

การเรียกใช้เครื่องมือแบบ asynchronous ทำให้โมเดลประมวลผลงานที่เป็นอิสระต่อไปได้ระหว่างที่เครื่องมือที่ทำงานช้ายังรันอยู่ Mid-turn steering ทำให้ผู้ใช้เปลี่ยนความต้องการได้ขณะที่โมเดลยังทำไม่เสร็จ ส่วน `configuration_update` ทำให้แอปพลิเคชันปรับระดับ reasoning ของการตอบสนองถัด ๆ ไปได้โดยไม่ต้องแก้พารามิเตอร์ reasoning ระดับคำขอ และยังคง prefix ของ prompt cache ไว้ได้

การเปลี่ยนแปลงที่ใหญ่กว่านั้นมาจาก Agents API ซึ่งเปิดทดสอบสาธารณะเมื่อวันที่ 10 กันยายน 2026 มันเปิดให้ใช้ Codex Harness ที่ OpenAI เป็นผู้จัดการผ่าน API: แอปพลิเคชันจัดหาคำสั่งสำหรับโมเดล เครื่องมือทางธุรกิจ และสภาพแวดล้อมการรัน ส่วน OpenAI ดูแล session การ orchestrate การบีบอัดบริบท การกู้คืน และสตรีมเหตุการณ์

นี่หมายความว่าการพัฒนา Agent กำลังเกิดการโยกย้ายความรับผิดชอบ:

> แพลตฟอร์มดูดซับ runtime ทั่วไป โมเดลดูดซับโปรโตคอลการโต้ตอบบางส่วน ทีมแอปพลิเคชันหันกลับไปทุ่มแรงกับขีดความสามารถทางธุรกิจ ขอบเขตสิทธิ์ สภาพแวดล้อมการรัน และการตรวจสอบผลลัพธ์

## ทำไมเมื่อก่อนผมถึงต้องสร้างของพวกนี้เอง

ตอนทำ Agent ยุคแรก การเรียกใช้เครื่องมือแบบ asynchronous และ "เปลี่ยนทิศระหว่างทำ" มักไม่ใช่พารามิเตอร์ API สองตัว แต่เป็นปัญหา state machine ชุดหนึ่ง

ต้องเก็บงานที่ยังไม่เสร็จ แยกแยะ turn ของโมเดลกับงานเบื้องหลัง รับมือกับโปรเซสที่รีสตาร์ต, timeout, การยกเลิก, callback ที่มาซ้ำ และผลลัพธ์ที่มาผิดลำดับ ต้องแทรกคำสั่งใหม่ของผู้ใช้เข้าไปในโฟลว์ที่กำลังรันอยู่ แล้วยังต้องตัดสินว่าผลลัพธ์เก่าใช้ไม่ได้แล้วหรือไม่ และการกระทำที่ทำไปแล้วย้อนกลับได้หรือเปล่า การเปลี่ยนระดับ reasoning ยังกระทบโครงสร้างคำขอ อัตราการ hit cache และการ replay บริบทอีกด้วย

งานวิศวกรรมเหล่านี้ไม่ได้สร้างคุณค่าทางธุรกิจ แต่กลับเป็นตัวตัดสินว่า Agent จะทำงานได้เสถียรหรือไม่ ทีมมักต้องใช้เวลามหาศาลดูแล "ชั้นชดเชย" ที่สร้างขึ้นมารอบ ๆ ข้อจำกัดของโมเดล

Astra เริ่มเปลี่ยนบางส่วนของสิ่งเหล่านี้ให้กลายเป็นความหมายในระดับโปรโตคอล

## Astra ทำให้โมเดลไม่ต้องติดอยู่กับเครื่องมือที่ช้าอีกต่อไป

การเรียกใช้เครื่องมือแบบ asynchronous ของ Responses API กำหนดให้ตั้ง `async: true` ในนิยามของ function หรือ custom tool หลังจากโมเดลส่งคำเรียกออกไปแล้ว โมเดลทำงานที่ไม่ขึ้นกับผลลัพธ์นั้นต่อได้ ส่วนแอปพลิเคชันจะส่งผลลัพธ์กลับด้วย `call_id` เดิมเมื่องานเสร็จ

สิ่งที่ลดลงตรงนี้คือการรอฝั่งโมเดล ไม่ใช่งานฝั่งแอปพลิเคชัน OpenAI ไม่ได้รันงานเบื้องหลังแทนแอปพลิเคชัน และไม่ได้ให้คิวงานทางธุรกิจมาด้วย ระบบ production ยังต้องตัดสินเองว่างานเป็นความรับผิดชอบของใคร ให้สิทธิ์อย่างไร ลองใหม่อย่างไร เก็บผลลัพธ์ไว้นานแค่ไหน และจะแสดงความล้มเหลวอย่างไร

ถ้ามีหลายงานรันพร้อมกัน แอปพลิเคชันยังนิยามเครื่องมือธรรมดาชื่อ `wait_for_tasks` ได้ เพื่อให้โมเดลรอเฉพาะตอนที่ต้องเปรียบเทียบผลลัพธ์จริง ๆ เครื่องมือ wait ตัวนี้เป็นโปรโตคอลของแอปพลิเคชันเอง

ดังนั้นคุณค่าของความสามารถแบบ asynchronous จึงไม่ได้อยู่ที่การใส่ async ให้เครื่องมือทุกตัว แต่อยู่ที่การเริ่มงานที่เป็นอิสระจริง ๆ ให้เร็วขึ้น พร้อมกับคงกำแพงกั้นการพึ่งพา (dependency barrier) ที่ชัดเจนไว้

## Mid-turn steering เปลี่ยนผู้ใช้ให้เป็นสัญญาณควบคุมขณะรัน

Mid-turn steering ของ Astra ให้บริการผ่านโหมด WebSocket ของ Responses API แอปพลิเคชันส่ง `response.steer` แล้ว API จะจัดคิวความต้องการใหม่ของผู้ใช้เข้าไปในการตอบสนองปัจจุบัน และสร้าง continuation ถัดไปให้โดยอัตโนมัติ

มันไม่เขียนทับผลลัพธ์ที่ส่งออกไปแล้ว และไม่ยกเลิกเครื่องมือที่เริ่มทำงานไปแล้ว `accepted` หมายเพียงว่าอินพุตเข้าคิวแล้ว ส่วนโมเดลได้ลงมือตามนั้นหรือยัง ต้องอ่านเหตุการณ์ต่อไปเพื่อยืนยัน

ดังนั้น steering จึงเป็น "การเพิ่มข้อจำกัด" ไม่ใช่ "การย้อนเวลา" Harness ยังต้องดูแล:

- ความสัมพันธ์ระหว่างการตอบสนองปัจจุบันกับการตอบสนองที่เป็น successor
- ลำดับของการ steering หลายครั้ง
- ขอบเขตสิทธิ์ของผลข้างเคียงที่เกิดขึ้นไปแล้ว
- การจัดการความขัดแย้งระหว่างผลลัพธ์ของเครื่องมือกับทิศทางใหม่
- กลยุทธ์กู้คืนเมื่อการเชื่อมต่อขาดและเมื่อมีการส่งซ้ำ

วิธีนี้น่าเชื่อถือกว่าการเขียนโค้ดเองแบบ "ยกเลิกคำขอแล้วสร้างบริบทขึ้นใหม่" อย่างในอดีต เพราะโปรโตคอลได้แสดงวงจรชีวิตของ continuation ไว้แล้ว แต่มันไม่ได้นิยามความหมายของการ undo ในเชิงธุรกิจแทนแอปพลิเคชัน

## configuration_update เปลี่ยนระดับ reasoning ให้เป็นสถานะของ session

แอปพลิเคชันแทรกสิ่งนี้เข้าไปในประวัติการสนทนาได้:

```json
{
  "type": "configuration_update",
  "reasoning": { "effort": "high" }
}
```

`reasoning.effort` ระดับคำขอยังคงค่าเดิม รายการอัปเดตมีผลเฉพาะกับการตอบสนองหลังจากนั้นเท่านั้น วิธีนี้ทำให้ใช้ระดับ reasoning ต่ำกับงานทั่วไป แล้วค่อยยกระดับขึ้นเมื่อเจอการวิเคราะห์ความผิดพลาดหรือการประเมินความเสี่ยง โดยยังคง prefix เดิมของ prompt ไว้ ซึ่งเป็นผลดีต่อการนำ cache กลับมาใช้

กลไกนี้ปัจจุบันรองรับเฉพาะโหมด Agent เดี่ยวมาตรฐานของ GPT-6 Astra และเปลี่ยนได้เฉพาะ reasoning effort เท่านั้น ส่วนการอัปเดตที่อยู่ติดกัน การ compaction อัตโนมัติ และการ truncation อัตโนมัติล้วนมีข้อจำกัดที่ระบุไว้ชัดเจน

ตรงนี้ต้องแยกให้ออกสามระดับ: API รองรับโปรโตคอลนี้แล้ว ชั้นล่างของ Codex อาจมีโครงสร้างข้อมูลบางส่วนอยู่แล้ว ส่วนไคลเอนต์ Codex ปัจจุบันใช้มันอย่างถูกต้องหรือไม่เมื่อมีการเปลี่ยนการตั้งค่าตามปกติ ต้องตรวจสอบตามเวอร์ชันที่เจาะจง [Codex Issue #42996](https://github.com/openai/codex/issues/42996) ที่เปิดเป็นสาธารณะยังคงรายงานปัญหาการ hit cache หลังสลับระดับ reasoning อยู่ จึงไม่ควรใช้เอกสาร API เป็นหลักฐานโดยตรงว่าไคลเอนต์ได้ผสานกลไกนี้เสร็จสมบูรณ์แล้ว

## จาก Responses API สู่ Codex Harness แล้วสู่ Agents API

ตอนนี้ OpenAI อธิบายขอบเขต runtime สามแบบไว้ชัดเจนมาก:

| วิธี | ใครดูแล runtime | เหมาะกับอะไร |
| --- | --- | --- |
| Responses API | แอปพลิเคชันเอง | ต้องการควบคุม Agent loop อย่างเต็มที่ |
| Codex SDK / App Server | นำ runtime ของ Codex ในเครื่องมาใช้ซ้ำ | ผสาน Codex เข้ากับเครื่องมือและผลิตภัณฑ์ของตัวเอง |
| Agents API | OpenAI โฮสต์ Codex Harness ให้ | อยากให้แพลตฟอร์มดูแล session การ orchestrate การบีบอัด และการกู้คืน |

ความหมายของ Agents API อยู่ที่ว่า มันเปลี่ยน Harness ทั่วไปที่เมื่อก่อนทุกทีมต้องสร้างซ้ำ ๆ ให้กลายเป็นขีดความสามารถของแพลตฟอร์ม ความสามารถที่โฮสต์ให้ตามที่เอกสารทางการระบุ ได้แก่ sandbox, Skills, MCP, steering, การจัดการบริบท, sub-agent และการกู้คืน session

ทีมแอปพลิเคชันยังต้องจัดหาเครื่องมือและเลือกสภาพแวดล้อมการรันอยู่ แต่ไม่จำเป็นต้องสร้าง agent loop ทั่วไปทั้งหมดขึ้นมาจากศูนย์

นี่ไม่ใช่ "ยกงานทั้งหมดให้แพลตฟอร์ม" แพลตฟอร์มรับผิดชอบกลไกการรันทั่วไป แอปพลิเคชันรับผิดชอบความจริงทางธุรกิจ เช่น:

- tenant ไหนมีสิทธิ์อ่านข้อมูลชุดนี้
- การเรียกใช้เครื่องมืออนุญาตให้เกิดผลข้างเคียงภายนอกหรือไม่
- การลองใหม่จะทำให้หักเงินหรือ deploy ซ้ำหรือเปล่า
- หลักฐานแบบไหนจึงเพียงพอจะบอกว่างานเสร็จแล้ว
- ผลลัพธ์ใดบ้างที่ต้องผ่านการอนุมัติโดยคน

## ความซับซ้อนของ Harness ไม่ได้หายไป แต่ถูกแบ่งชั้นใหม่

เราแบ่งความซับซ้อนทางวิศวกรรมในอดีตออกเป็นสามประเภทได้:

1. **ความซับซ้อนจากการชดเชยโมเดล**: การรอ การสร้างบริบทขึ้นใหม่ การจำลองการขัดจังหวะ และการเขียนโปรโตคอล asynchronous เอง ซึ่ง Astra กำลังดูดซับส่วนหนึ่งของสิ่งนี้
2. **ความซับซ้อนของ runtime ทั่วไป**: session สตรีมเหตุการณ์ การบีบอัด การกู้คืน sub-agent และ sandbox ซึ่ง Codex Harness กับ Agents API กำลังดูดซับส่วนหนึ่งของสิ่งนี้
3. **ความซับซ้อนด้านความถูกต้องทางธุรกิจ**: สิทธิ์ ความสอดคล้องของข้อมูล การอนุมัติ idempotency การตรวจรับ และการตรวจสอบย้อนหลัง (audit) สิ่งเหล่านี้ยังเป็นของแอปพลิเคชันเอง

ดังนั้นการเปลี่ยนแปลงที่แท้จริงจึงไม่ใช่ "ต่อไปไม่ต้องทำงานวิศวกรรมแล้ว" แต่คือจุดศูนย์ถ่วงของงานวิศวกรรมได้ย้ายที่ไป:

```text
เมื่อก่อน: สร้าง Agent Runtime ด้วยตัวเอง
ตอนนี้: เชื่อมต่อขีดความสามารถ ประกาศขอบเขต ตรวจสอบผลลัพธ์
```

## นัยต่อ Codex

ถ้า Codex Harness พัฒนาต่อไป แกนกลางจะย้ายจากลูปแบบ turn ไปสู่ control plane:

```text
สตรีมเหตุการณ์
  ├─ การตอบสนองของโมเดล
  ├─ การเริ่มและเสร็จสิ้นของเครื่องมือ
  ├─ steering จากผู้ใช้
  ├─ การอัปเดตการตั้งค่า reasoning
  └─ continuation

Control plane
  ├─ conversation head ปัจจุบัน
  ├─ pending task registry
  ├─ สิทธิ์และการอนุมัติ
  ├─ invariant ของ cache
  ├─ การกู้คืนและ idempotency
  └─ การตรวจสอบผลลัพธ์
```

การอภิปรายในชุมชนเกี่ยวกับ LangChain, Hermes, ZeroClaw และ gateway อื่น ๆ ก็ชี้ให้เห็นว่า หลังจากโปรโตคอลปรากฏขึ้นแล้ว การปรับตัวของระบบนิเวศยังต้องใช้เวลา ปัญหาที่พบบ่อยไม่ใช่ "ส่งฟิลด์ async ได้หรือไม่" แต่คือการแปลงสตรีม การ replay ข้อความ การเสร็จสิ้นผิดลำดับ การกู้คืนหลังขาดการเชื่อมต่อ และการส่งซ้ำ ยังรักษาความหมายดั้งเดิมไว้ได้หรือเปล่า

## บทสรุปสุดท้าย

Astra และ Agents API ชี้ร่วมกันไปยังการแบ่งงานแบบใหม่ของ Agent:

> โมเดลรับผิดชอบการคิดที่ยืดหยุ่นขึ้น โปรโตคอลรับผิดชอบการแสดงการควบคุมขณะรัน Harness รับผิดชอบการ orchestrate ทั่วไป และแอปพลิเคชันรับผิดชอบข้อจำกัดที่แท้จริงในโลกธุรกิจ

สิ่งนี้จะลดต้นทุนเริ่มต้นของ Agent ใหม่ลงอย่างมาก ลูปแบบ asynchronous การกู้คืนสถานะ และการแทรกแซงกลางทาง ที่เมื่อก่อนต้องใช้เวลาสร้างหลายสัปดาห์ ในอนาคตอาจกลายเป็นแค่การตั้งค่า runtime และเชื่อมต่อเครื่องมือ

แต่สิ่งนี้ก็ยกระดับข้อเรียกร้องต่อทีมแอปพลิเคชันในเรื่อง "การนิยามปัญหา" ด้วย ยิ่งกลไกทั่วไปถูกแพลตฟอร์มรับไปดูแลมากเท่าไร ส่วนที่สร้างความแตกต่างได้จริงก็ยิ่งกระจุกตัวอยู่ที่การออกแบบเครื่องมือ โมเดลสิทธิ์ ขอบเขตของสภาพแวดล้อม ตัวตรวจสอบ และ feedback loop

คำถามหลักของการพัฒนา Agent กำลังย้ายจาก "จะทำให้โมเดลรันได้อย่างไร" ไปสู่ "จะทำให้มันถูกใช้งานได้อย่างน่าเชื่อถือในโลกจริงได้อย่างไร"
